# v0.6 Embedding 抽象与调用报告

> 本报告记录 v0.6 Embedding 抽象与调用闭环的实现结果。
> 本阶段不包含向量数据库、RAG、文件问答、真实外部 embedding API 调用或数据库持久化。

## 1. 工程效果

v0.6 完成后，北辰agent 的 RAG 前置链路推进到 embedding 阶段：

```text
文件上传
  -> 文档解析
  -> 文本切块
  -> mock embedding 向量化
  -> 前端展示 embedding 数量、维度和向量预览
```

用户侧效果：

- 上传 TXT / DOCX / PDF。
- 点击“解析”。
- 点击“切块”。
- 点击“向量化”。
- 文件状态变为“已向量化”。
- 文件列表展示 embedding 维度。
- 点击 `vectors` 可以查看前几个 chunk 的向量预览。

当前向量是 mock vector，只用于验证工程链路，不代表真实语义。

## 3. 调用链路

```text
FileCenter.handleEmbed(file)
  -> fileStore.embedFile(file.id)
  -> fileApi.embedFile(file.id, file.extension)
  -> POST /api/v1/files/{file_id}/embeddings
  -> DocumentParserService.parse_text(file_id, extension)
  -> ChunkService.create_chunks(file_id, text)
  -> EmbeddingService.embed_chunks(file_id, chunks)
  -> MockEmbeddingProvider.embed_texts(texts)
  -> EmbedFileResponse
  -> 前端状态更新为 embedded
```

## 4. 设计原因

### 4.1 为什么新增 EmbeddingProvider

Embedding 供应商未来可能变化：

- mock provider。
- OpenAI-compatible provider。
- 本地 embedding 模型。

如果 `EmbeddingService` 直接写死某个供应商，后续切换会困难。

Provider 抽象让 Service 只关心：

```text
texts -> vectors
```

不关心向量具体由谁生成。

### 4.2 为什么先做 MockEmbeddingProvider

v0.6 目标是验证工程链路，不是验证真实语义检索效果。

Mock provider 的好处：

- 不依赖外部 API。
- 不需要额外 API Key。
- 不产生费用。
- 结果稳定，便于测试。

### 4.3 为什么不保存 vectors

保存 vectors 属于 VectorStore 阶段。

v0.6 只确认：

```text
chunks 能否成功变成 vectors
```

下一阶段再处理：

```text
vectors 存在哪里、如何查询、如何做相似度检索
```

## 6. 当前限制

- 当前 embedding 是 mock vector，不代表真实语义。
- 不调用真实外部 embedding API。
- 不保存 vectors 到数据库或向量库。
- 页面刷新后 embedding 状态丢失。
- `/embeddings` 当前会重新执行 parse 和 chunk。
- 不支持向量检索。
- 不支持 RAG 文件问答。
