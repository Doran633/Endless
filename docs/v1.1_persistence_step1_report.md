# v1.1.1 数据库基础与文件元数据持久化报告

## 1. 本次完成内容

v1.1.1 完成了数据库持久化的第一步：**文件元数据持久化 + 文件列表刷新恢复**。

本次实现：

- 引入 SQLite + SQLAlchemy 作为 MVP 数据库方案。
- 新增 `backend/app/db/` 数据库基础目录。
- 新增 `backend/app/repositories/` Repository 层。
- 新增 `files` 表。
- 上传文件成功后，将文件元数据写入 SQLite。
- 新增 `GET /api/v1/files` 文件列表接口。
- 前端文件中心打开时从后端读取真实文件列表。
- 新增数据库本地文件忽略规则，避免提交本地 SQLite 数据。

本次没有实现：

- PostgreSQL。
- pgvector。
- 文件处理状态完整持久化。
- 文件删除 API。
- 聊天会话持久化。
- 聊天消息持久化。
- 多用户、企业权限、Agent。
- embeddings 入库。

## 2. 修改文件职责

### `backend/app/db/__init__.py`

标记 `db` 为后端数据库包。

### `backend/app/db/database.py`

负责数据库连接基础设施：

- 创建 SQLAlchemy `Base`。
- 创建 SQLite engine。
- 创建 `SessionLocal`。
- 提供 `get_db()` 数据库 session 依赖。
- 在创建 engine 前确保 SQLite 数据目录存在。

设计原因：

- 数据库连接属于基础设施，不应该写在 API 或 Service 中。
- 未来迁移 PostgreSQL 时，主要替换这一层配置。

### `backend/app/db/models.py`

新增 `FileRecord` ORM 模型，对应 `files` 表。

当前保存字段包括：

- `id`
- `original_name`
- `extension`
- `size_bytes`
- `storage_path`
- `status`
- `text_preview`
- `char_count`
- `chunk_count`
- `embedding_count`
- `embedding_dimension`
- `embedding_model`
- `vector_store_path`
- `error_message`
- `created_at`
- `updated_at`

设计原因：

- Step 1 只写入上传阶段的基础元数据。
- 但模型预留了解析、切块、embedding 和索引状态字段，方便后续 Step 2 直接更新。

### `backend/app/db/init_db.py`

负责初始化数据库表结构。

当前使用：

```text
Base.metadata.create_all(bind=engine)
```

设计原因：

- v1.1 仍是 MVP 阶段，不引入复杂 migration 系统。
- 本地开发和 GitHub 分享时，用户启动后端即可自动创建 SQLite 表。

### `backend/app/repositories/__init__.py`

标记 `repositories` 为 Repository 包。

### `backend/app/repositories/file_repository.py`

封装 `files` 表的数据库操作。

当前能力：

- `create_uploaded_file()`：创建上传文件记录。
- `list_files()`：按创建时间倒序返回文件列表。
- `touch_failed()`：预留失败状态更新入口。

设计原因：

- Service 不直接操作 SQLAlchemy ORM。
- 未来迁移 PostgreSQL、增加测试替身或扩展查询时，业务层改动更小。

### `backend/app/core/config.py`

新增数据库配置：

- `DATABASE_PATH`
- `DATABASE_URL`

默认数据库路径：

```text
backend/data/beichen.db
```

设计原因：

- 默认配置开箱即用。
- `.env` 可以覆盖数据库位置。
- 本地数据库文件不进入 Git。

### `backend/app/main.py`

应用启动时调用 `init_db()` 初始化数据库。

设计原因：

- 用户启动后端后，数据库表自动可用。
- 不需要手动执行初始化脚本。

### `backend/app/schemas/file.py`

新增：

- `FileRecordResponse`
- `FileListResponse`

设计原因：

- 上传响应保持兼容。
- 文件列表接口使用独立响应结构，便于后续增加处理状态字段。

### `backend/app/services/file_service.py`

扩展 `FileService`：

- 上传文件保存到 `backend/uploads/` 后写入数据库。
- 数据库写入失败时删除刚保存的文件，减少文件系统和数据库不一致。
- 新增 `list_files()` 业务方法。

设计原因：

- 文件上传仍由 FileService 统一负责。
- Repository 只负责数据库读写，FileService 负责编排文件系统和数据库。

### `backend/app/api/v1/files.py`

新增：

```text
GET /api/v1/files
```

设计原因：

- 前端刷新后需要从后端恢复文件列表。
- API 层只调用 FileService，不直接接触数据库。

### `backend/requirements.txt`

新增：

```text
SQLAlchemy
```

设计原因：

- 明确项目后端新增 ORM 依赖。
- 别人拿到项目后可通过 `pip install -r requirements.txt` 安装。

### `backend/.env.example`

新增：

```text
DATABASE_PATH=data/beichen.db
```

设计原因：

- 告诉使用者本地 SQLite 数据库默认位置。
- 不包含敏感信息。

### `.gitignore`

新增：

```text
backend/data/
```

设计原因：

- 本地 SQLite 数据库属于运行数据，不应提交到 GitHub。

### `frontend/src/api/fileApi.ts`

新增：

- `listFiles()`

设计原因：

- 前端通过统一 API client 读取后端文件列表。
- 组件和 store 不直接写 fetch 细节。

### `frontend/src/stores/fileStore.ts`

新增：

- `loadFiles()`

调整：

- 初始文件列表从空数组开始。
- 文件中心通过后端接口恢复真实文件列表。

设计原因：

- 文件中心不再依赖 Mock 文件作为真实状态。
- 前端状态仍由 Zustand 管理，符合现有架构。

### `frontend/src/components/FileCenter.tsx`

新增：

- 打开文件中心时调用 `loadFiles()`。
- 读取失败时显示错误提示。

设计原因：

- 刷新页面或重新进入文件中心后，可以看到后端保存的文件记录。

## 3. 文件上传到数据库记录的调用链路

```text
Frontend FileCenter
  -> frontend/src/stores/fileStore.ts uploadFile()
  -> frontend/src/api/fileApi.ts uploadFile()
  -> POST /api/v1/files
  -> backend/app/api/v1/files.py upload_file()
  -> backend/app/services/file_service.py FileService.upload()
  -> backend/uploads/ 保存原始文件
  -> backend/app/repositories/file_repository.py create_uploaded_file()
  -> SQLite files 表
  -> 返回 UploadedFileResponse
  -> 前端 files 状态新增该文件
```

关键点：

- 文件二进制内容仍然保存在 `backend/uploads/`。
- SQLite 只保存文件元数据和状态。
- embeddings 仍然保存在 `backend/vector_store/` JSON 文件，不进入数据库。

## 4. 刷新恢复文件列表的调用链路

```text
Frontend FileCenter mounted
  -> frontend/src/stores/fileStore.ts loadFiles()
  -> frontend/src/api/fileApi.ts listFiles()
  -> GET /api/v1/files
  -> backend/app/api/v1/files.py list_files()
  -> backend/app/services/file_service.py FileService.list_files()
  -> backend/app/repositories/file_repository.py list_files()
  -> SQLite files 表
  -> 返回 FileListResponse
  -> 前端 files 状态替换为后端真实列表
```

刷新后当前可恢复：

- 文件 id。
- 原始文件名。
- 扩展名。
- 文件大小。
- 上传状态。
- 创建时间。

刷新后当前暂不完整恢复：

- 解析预览。
- chunk 预览。
- embedding 预览。
- indexed 状态。

这些属于 v1.1 后续 Step 2 范围。

## 6. 当前剩余问题

v1.1.1 只完成文件元数据持久化的第一步，仍有以下限制：

- 解析成功后还不会更新数据库状态。
- 切块成功后还不会更新数据库状态。
- embedding 成功后还不会更新数据库状态。
- vector-store 保存成功后还不会更新数据库 indexed 状态。
- 文件删除 API 尚未实现。
- 聊天会话和消息持久化尚未实现。
- 当前仍未引入数据库 migration。

## 7. 下一步建议

建议进入 v1.1.2：文件处理状态持久化。

目标：

- 解析成功后更新 `parsed` / `ready` 状态、`text_preview`、`char_count`。
- 切块成功后更新 `chunked` 状态、`chunk_count`。
- embedding 成功后更新 `embedded` 状态、`embedding_count`、`embedding_dimension`、`embedding_model`。
- vector-store 保存成功后更新 `indexed` 状态、`vector_store_path`。
- 处理失败时记录 `failed` 和 `error_message`。

这样刷新后文件中心才能看到更完整的处理状态，而不是只恢复上传记录。
