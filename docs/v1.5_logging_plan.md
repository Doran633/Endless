# v1.5.7 Local Error Logging Plan

## 1. 当前问题

项目已经具备：

- 真实 LLM 调用。
- 真实 embedding 调用。
- 文件上传、解析、切块、向量化、索引。
- Retrieval 和单文件 RAG。
- 会话和消息持久化。
- 邀请码访问。
- `/health/config` 非敏感配置检查。
- 本地启动/停止脚本稳定性增强。

但当前错误排查仍然依赖：

- 前端页面提示。
- PowerShell 终端输出。
- 手动复现。
- 临时查看后端报错。

一旦出现：

- LLM API 失败。
- Embedding API 失败。
- 文件解析失败。
- vector_store 写入失败。
- RAG 问答失败。
- 端口或环境配置问题。

开发者很难快速回答：

```text
这次错误发生在哪个请求？
后端具体在哪一层失败？
有没有 request_id 可以定位日志？
是 LLM 失败，还是 embedding 失败？
是用户输入问题，还是服务端配置问题？
```

所以 v1.5.7 需要补充基础错误日志能力。

## 2. 开发日志的作用

日志不是为了“让系统更聪明”，而是为了“让问题更可追踪”。

它的核心作用：

1. 定位错误
   - 知道错误发生在哪个接口、哪个模块、哪个阶段。

2. 串联请求
   - 通过 `request_id` 把前端错误提示、后端响应和日志行对应起来。

3. 降低排查成本
   - 不需要靠猜测判断是 LLM、Embedding、文件解析还是 RAG 出错。

4. 辅助部署
   - 上线到 VPS 后，不能一直盯着终端，必须能查看历史错误。

5. 支持后续稳定性优化
   - 有日志后才能知道哪些错误最频繁、哪些流程最脆弱。

日志不应该做：

- 不记录真实 API Key。
- 不记录真实邀请码。
- 不记录完整上传文件内容。
- 不记录完整 prompt。
- 不记录完整 chunks。
- 不记录完整 embeddings。

## 3. v1.5.7 目标状态

新增基础后端日志能力：

- 每个 HTTP 请求生成 `request_id`。
- 响应 header 返回 `X-Request-Id`。
- 应用错误响应中包含 `request_id`。
- 后端日志记录请求开始、请求完成和请求异常。
- LLM / Embedding / 文件处理 / RAG 相关错误能在日志中定位。
- 日志默认输出到控制台。
- 可选写入 `backend/logs/app.log`。

保持 MVP 简单：

- 不接入 Sentry。
- 不接入 ELK。
- 不接入 OpenTelemetry。
- 不引入复杂监控平台。
- 不新增数据库表。
- 不修改 RAG 主链路。

## 4. 日志范围设计

建议记录：

- `request_id`
- HTTP method
- path
- status_code
- elapsed_ms
- error_type
- error_message 简短摘要
- service/module 名称
- provider 类型
- model 名称

建议不要记录：

- API Key
- Authorization header
- `X-Beichen-Access`
- 真实邀请码
- 完整用户消息
- 完整 prompt
- 上传文件内容
- chunks 内容
- embedding vectors
- SQLite 记录内容

可接受记录：

- 文件扩展名
- 文件大小
- chunk_count
- embedding_dimension
- embedding_model
- provider/model 名称

## 5. request_id 设计

新增中间件：

```text
RequestIdMiddleware
```

流程：

```text
请求进入
-> 如果 header 中已有 X-Request-Id，复用
-> 如果没有，生成 uuid4
-> 放入 request.state.request_id
-> 响应 header 加 X-Request-Id
-> 日志中带 request_id
```

前端后续可以在错误提示中展示：

```text
请求编号：xxxx
```

v1.5.7 可以先不改前端，只确保后端响应和日志具备 request_id。

## 6. 错误响应设计

当前 AppError 响应结构大致是：

```json
{
  "code": 42001,
  "message": "xxx",
  "data": null
}
```

建议扩展为：

```json
{
  "code": 42001,
  "message": "xxx",
  "data": null,
  "request_id": "..."
}
```

成功响应可以暂不改 body，只在 header 返回 `X-Request-Id`。

这样不会破坏前端主要业务逻辑，因为前端主要看 `code`、`message`、`data`。

## 7. 文件结构建议

预计新增：

- `backend/app/core/logging_config.py`
  - 初始化 logger、格式、日志文件路径。

- `backend/app/core/request_context.py`
  - request_id 生成和读取工具。

预计修改：

- `backend/app/main.py`
  - 注册 request_id / logging middleware。

- `backend/app/core/exception_handlers.py`
  - 错误响应增加 request_id。
  - 记录 AppError。

- `backend/.env.example`
  - 增加日志配置：
    - `LOG_LEVEL=INFO`
    - `LOG_TO_FILE=false`
    - `LOG_DIR=logs`

- `.gitignore`
  - 确认 `*.log` 和 `backend/logs/` 被忽略。

- `docs/status.md`
  - 更新当前阶段状态。

- `docs/v1.5_logging_report.md`
  - 生成实现报告。

## 8. 日志输出方案

MVP 推荐：

```text
控制台日志为主
文件日志可选
```

`.env`：

```env
LOG_LEVEL=INFO
LOG_TO_FILE=false
LOG_DIR=logs
```

如果 `LOG_TO_FILE=true`：

```text
backend/logs/app.log
```

必须确保：

- `backend/logs/` 不提交 Git。
- 日志文件不包含密钥、邀请码、文件内容。

## 9. 测试方案

基础验证：

- `scripts/check-local.ps1`
- `python -m compileall app`
- `npm exec tsc -- --noEmit`

接口验证：

- 请求 `/health`
- 请求 `/health/config`
- 请求一个会触发 404 或 AppError 的接口
- 确认响应 header 包含 `X-Request-Id`
- 确认错误响应 body 包含 `request_id`

日志验证：

- 触发一次错误请求。
- 查看控制台是否打印 request_id。
- 如果 `LOG_TO_FILE=true`，确认 `backend/logs/app.log` 生成。
- 确认日志中不包含：
  - `sk-`
  - `APP_INVITE_CODES`
  - `X-Beichen-Access` 的值
  - 上传文件内容
  - chunks
  - embeddings

## 10. 风险和技术债

风险：

- 日志如果设计不当，可能泄露用户内容或密钥。
- 文件日志可能增长过大。
- request_id 如果只在后端存在，前端用户仍不容易反馈问题编号。

本阶段控制方式：

- 只记录摘要。
- 不记录敏感 header。
- 不记录 request body。
- 不记录完整 prompt 和文档内容。
- 文件日志默认关闭。

后续技术债：

- 日志轮转。
- 更细粒度的模块日志。
- 前端错误提示展示 request_id。
- 部署后结合 systemd / Nginx 日志。
