# v1.3.2 RAG Context Follow-up 实现报告

## 1. 工程效果

本阶段完成了 RAG 文件问答的基础连续追问能力。

当 `POST /api/v1/files/{file_id}/ask` 携带 `session_id` 时，后端会读取当前会话最近 6 条历史消息，将其作为“最近对话上下文”加入 RAG prompt，再基于当前用户问题执行检索和回答。

这使用户可以在文档问答后继续追问，例如：

```text
第一轮：这份文档的第二部分讲了什么？
第二轮：继续解释上面第二点。
```

第二轮回答可以同时看到：

- 当前问题。
- 当前问题检索到的文档 chunks。
- 当前会话最近几条对话上下文。

无 `session_id` 时，RAG 问答仍保持原有单轮行为。

## 2. 修改文件职责

### `backend/app/services/rag_service.py`

职责变化：

- `ask_file()` 新增可选参数 `conversation_context`。
- `_build_prompt()` 新增“最近对话上下文”区域。
- 新增 `_format_conversation_context()`，将历史 `ChatMessage` 转换为用户可读的 prompt 文本。

设计原因：

- RAG prompt 的构造应该仍由 `RagService` 负责。
- Retrieval、VectorStore、Embedding 不需要知道会话上下文。
- 无上下文时显示“无”，保证原单轮 RAG 调用仍稳定。

### `backend/app/services/conversation_service.py`

职责变化：

- `ask_file_and_persist()` 在调用 `RagService.ask_file()` 前读取最近历史消息。
- 新增 `_build_recent_context_messages()`，复用普通聊天上下文读取逻辑。
- `_build_chat_context_messages()` 改为基于 `_build_recent_context_messages()` 再追加当前用户消息。

设计原因：

- `ConversationService` 是会话编排层，适合决定是否读取历史消息。
- `RagService` 不直接访问数据库，避免 RAG 服务和持久化层耦合。
- 当前用户 query 不放进历史上下文，而是作为“当前问题”单独进入 RAG prompt，语义更清晰。

### `docs/status.md`

职责变化：

- 当前版本更新为 `v1.3.2`。
- 标记 RAG 文件问答连续追问基础能力已完成。
- 明确当前仍不是长期记忆，也没有实现历史消息语义检索。

## 3. RAG 连续追问调用链

```text
Frontend
-> POST /api/v1/files/{file_id}/ask { query, top_k, session_id }
-> Files API Router
-> ConversationService.ask_file_and_persist()
-> ChatRepository.list_recent_messages(session_id, limit=6)
-> ConversationService 转换并截断历史消息
-> RagService.ask_file(file_id, query, top_k, conversation_context)
-> RetrievalService.retrieve(file_id, query, top_k)
-> VectorStoreService 读取本地 JSON 索引
-> EmbeddingService 为 query 生成 embedding
-> cosine similarity 返回 top_k chunks
-> RagService 组装 RAG prompt
   - 系统身份说明
   - 文档片段
   - 最近对话上下文
   - 当前问题
-> LLMService
-> LLMProvider
-> ConversationService 保存 user / assistant 消息
-> 返回 AskFileResponse
```

## 4. 为什么不影响 RAG 主链路

本阶段没有修改：

- `RetrievalService`
- `VectorStoreService`
- `EmbeddingService`
- 向量索引 JSON 数据结构
- API 路径和请求结构
- 前端调用方式

检索仍然只根据当前用户 query 执行。

历史消息只在检索完成后进入 prompt，用来帮助 LLM 理解“上面第二点”“继续解释”等连续追问指代，不参与向量检索。

## 5. Token 风险和当前截断策略

风险：

- 最近 6 条历史消息可能包含较长回答。
- RAG prompt 本身已经包含文档 chunks，再加入对话上下文会增加 token 成本。
- 如果历史消息和 chunks 都很长，模型响应可能变慢。

当前策略：

- 默认最多读取最近 6 条消息。
- 每条历史消息最多保留 1200 个字符。
- 超出后追加 `...`。
- 当前 query 仍完整保留。
- 不做 tokenizer-aware 精确 token 预算。

后续如果 prompt 变长，应考虑：

- RAG 专用上下文条数更小，例如 4 条。
- 对 assistant 历史回答做更短截断。
- 引入会话摘要。
- 引入历史消息语义检索。

## 6. 这仍不是长期记忆

v1.3.2 只是“短上下文窗口”，不是长期记忆。

它不能做到：

- 跨会话记住用户偏好。
- 从大量历史消息中语义检索相关内容。
- 自动总结长期事实。
- 对历史信息做遗忘、更新或冲突处理。

它能做到：

- 在当前会话最近几轮内理解连续追问。
- 帮助 RAG 回答理解“上面”“刚才”“第二点”等指代。
- 在不引入复杂架构的前提下提升文档问答体验。

结果：通过。

已运行：

```powershell
npm exec tsc -- --noEmit
```

结果：通过。

已使用轻量后端验证脚本确认：

- RAG 携带 `session_id` 时，会读取最近 6 条历史消息。
- 历史消息会传入 `RagService.ask_file()` 的 `conversation_context`。

- 无 `session_id` 时，`RagService.ask_file()` 仍可不带上下文执行。

## 8. 当前剩余问题

- RAG 检索仍只基于当前 query，不会根据历史问题改写 query。
- 连续追问中的省略问题可能仍影响检索质量，例如“那第二点呢”可能检索不到最相关 chunk。
- 当前没有会话摘要和历史消息语义检索。
- 当前没有自动化测试目录，仍以编译检查和轻量脚本验证为主。
