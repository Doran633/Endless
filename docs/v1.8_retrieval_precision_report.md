# v1.8.4 Retrieval Precision Tuning 报告

## 1. 本阶段工程效果

本阶段在不改变 RAG 主链路的前提下，增强了 RetrievalService 的排序和过滤能力。

新增能力：

- 增加可配置 `RAG_SCORE_THRESHOLD`。
- 增加可配置 `RAG_RELATIVE_SCORE_GAP`。
- 增加轻量 keyword bonus。
- `RetrievalResult` 增加 `raw_score`、`keyword_bonus`、`final_score` 和 `relevance_level`。
- RAG prompt 只使用通过过滤的检索片段。
- 前端文件中心和聊天侧引用片段展示 High / Medium / Weak 相关等级。
- 前端展示 raw / bonus / final 分数，便于测评和排查。

本阶段没有新增 AI 业务功能，没有修改数据库结构，没有引入 pgvector、rerank 或多文件 RAG。

## 3. score_threshold 原理

`RAG_SCORE_THRESHOLD` 是绝对分数阈值。

如果某个片段最终分数低于阈值，就不进入 RAG prompt。

当前默认：

```env
RAG_SCORE_THRESHOLD=0
```

这表示默认不做绝对阈值过滤，避免上线后突然丢失太多召回片段。后续可以在测评时尝试：

```env
RAG_SCORE_THRESHOLD=0.45
RAG_SCORE_THRESHOLD=0.50
RAG_SCORE_THRESHOLD=0.55
```

## 4. relative_score_gap 原理

`RAG_RELATIVE_SCORE_GAP` 是相对最高分的尾部过滤。

例如最高分是 `0.68`，gap 是 `0.20`，则低于 `0.48` 的片段会被过滤。

它解决的问题是：

```text
top_k 强行返回 3 个片段，其中第 3 个明显弱相关。
```

当前默认：

```env
RAG_RELATIVE_SCORE_GAP=0.20
```

这个值较保守，通常只过滤明显落后的片段。

## 5. keyword bonus 原理

keyword bonus 是轻量字符串匹配，不调用 LLM，也不引入新依赖。

流程：

1. 从 query 中提取英文词和中文 n-gram。
2. 在 chunk 的 `section_path`、`section_title` 和正文中查找命中。
3. 根据命中比例增加最多 `RAG_KEYWORD_BONUS_MAX` 的分数。

当前默认：

```env
RAG_KEYWORD_BONUS_MAX=0.04
```

它不会取代 embedding，只是让“TXT / DOCX / PDF”“上传文件”“大小限制”等明确关键词更容易影响排序。

## 6. 为什么这一步不做 rerank

rerank 可以提升检索质量，但会增加模型依赖、调用成本、响应延迟和配置复杂度。

当前阶段更需要先完成低成本可解释调优：

- chunk 更干净。
- section metadata 可见。
- raw / bonus / final 分数可见。
- 弱相关片段可识别。

这些能力稳定后，再评估 rerank 才更有意义。

## 7. 如何重新索引并测试效果

测试步骤：

1. 部署最新代码。
2. 删除旧测试文件或重新上传同一份测试文档。
3. 等待自动完成解析、切块、embedding 和索引。
4. 用相同问题重新测试。
5. 在测评表中记录：
   - `max_score`
   - `average_score`
   - `retrieved_chunk_indexes`
   - `groundedness_score`
   - `citation_score`
   - `notes`
6. 重点观察：
   - 弱相关片段是否减少。
   - 正确依据是否更靠前。
   - `keyword_bonus` 是否合理。
   - High / Medium / Weak 是否符合人工直觉。

## 9. 剩余问题

- keyword bonus 是轻量字符串匹配，不能替代真正 rerank。
- 宽泛 overview 问题仍可能需要 summary chunk 或问题类型识别。
- score threshold 默认未启用绝对过滤，需要基于人工测评逐步调参。
- 前端历史中文源码仍有编码清理空间，应作为独立任务处理。
