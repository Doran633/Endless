# v1.5.8 Runtime Verification / Release Smoke Test 报告

## 1. 本阶段目标

v1.5.8 的目标不是新增 AI 功能，而是把“发布前本地检查”整理成可重复执行的流程。它用于确认当前项目从后端、前端、访问保护、日志到核心 RAG 链路都处于可运行状态。

## 2. 新增文件

- `scripts/smoke-test-local.ps1`

用于在 Windows 本地验证已经启动的前后端服务。脚本不会启动或停止服务，只检查当前固定端口上的运行状态，并通过现有 API 执行 smoke test。

脚本端口检测使用 `netstat`，因为在当前 Windows / Codex 本地环境中，`Get-NetTCPConnection` 可能无法稳定读取监听端口，而 `netstat -ano` 与日常手动排查方式一致。

## 3. 修改文件

- `scripts/check-local.ps1`
- `scripts/start-local.ps1`
- `scripts/stop-local.ps1`

这三个脚本的端口检测也同步改为 `netstat`。原因是 smoke test 过程中发现：`netstat` 可以正确看到 8000 / 5173 的 `LISTENING` 进程，但 `Get-NetTCPConnection` 在当前环境中可能返回空，导致 `check-local.ps1` 误报端口空闲，进而增加重复启动旧进程的风险。

## 4. 覆盖的验证项

### 4.1 后端启动

目的：确认 FastAPI 正在监听固定端口。

通过标准：`127.0.0.1:8000` 存在 `LISTENING` 进程。

失败排查：运行 `scripts/check-local.ps1`，如果端口未监听，启动后端；如果端口被旧进程占用，运行 `scripts/stop-local.ps1`。

### 4.2 前端启动

目的：确认 Vite 前端正在监听固定端口。

通过标准：`127.0.0.1:5173` 存在 `LISTENING` 进程，且首页返回 `200 OK`。

失败排查：如果前端未监听，进入 `frontend/` 运行 `npm run dev -- --host 127.0.0.1 --port 5173 --strictPort`；如果出现 `Access is denied`，使用普通 PowerShell 或提升权限启动。

### 4.3 健康接口

目的：确认后端基础健康接口正常。

通过标准：`GET /health` 返回 `200`，响应 header 包含 `X-Request-Id`。

失败排查：查看后端 PowerShell 日志，按 `request_id` 定位请求。

### 4.4 配置接口

目的：确认当前运行后端读取到了预期配置。

通过标准：`GET /health/config` 返回 LLM、Embedding、SQLite、uploads、vector_store 和访问保护摘要，并返回 `X-Request-Id`。

失败排查：确认是否有旧后端进程占用 8000；确认修改 `.env` 后是否重启后端。

### 4.5 邀请码保护

目的：确认公网部署前的最小访问门槛仍有效。

通过标准：当访问保护启用时，无邀请码请求 `/api/v1/files` 返回 `401`；携带本地 `.env` 中的访问 header 后可正常访问。

失败排查：检查 `APP_INVITE_CODES`、`APP_ACCESS_PASSWORD`、`APP_ACCESS_HEADER` 是否与前端/脚本一致。

### 4.6 普通聊天

目的：确认 LLM Provider 和普通聊天 API 可用。

通过标准：创建测试会话后，`POST /api/v1/chat` 携带 `session_id` 可以返回 assistant answer。

失败排查：查看后端日志中的 `LLMConfigError` 或 `LLMProviderError`；检查 `LLM_PROVIDER`、`LLM_MODEL`、`OPENAI_API_KEY`、`OPENAI_BASE_URL`。

### 4.7 文件上传

目的：确认文件上传 API、FileService、本地 uploads 和 SQLite 文件记录可用。

通过标准：上传临时 TXT 文件后返回 `file_id`、`extension`、`status` 等字段。

失败排查：检查 `backend/uploads/` 权限、文件大小限制和允许扩展名。

### 4.8 自动处理链路

目的：确认解析、切块、Embedding 和本地 VectorStore 主链路仍可运行。

通过标准：

- parse 返回 `char_count > 0`。
- chunks 返回 `chunk_count > 0`。
- embeddings 返回 `embedding_count > 0` 和 `embedding_dimension > 0`。
- vector-store 返回 `storage_path` 和 embedding 摘要。

失败排查：按接口阶段查看后端日志；Embedding 失败时优先检查 `EMBEDDING_PROVIDER`、`EMBEDDING_MODEL`、`EMBEDDING_API_KEY`、`EMBEDDING_BASE_URL`。

### 4.9 RAG 问答

目的：确认 Retrieval、RagService 和 LLMProvider 的组合链路可用。

通过标准：`POST /api/v1/files/{file_id}/ask` 返回 answer，并且 `used_chunk_count > 0`。

失败排查：确认文件已经索引；确认 embedding 模型维度与本地索引一致；查看 `RagError`、`RetrievalError` 或 `LLMProviderError`。

### 4.10 日志 request_id

目的：确认前端报错、API 响应和后端日志可以通过同一个 request_id 串起来。

通过标准：`/health` 和 `/health/config` 返回 `X-Request-Id`；错误响应和日志中也能看到 request_id。

失败排查：确认后端运行的是 v1.5.7 之后的代码；确认不是旧后端进程。

## 5. 如何运行

先启动本地服务：

```powershell
cd "C:\Users\lbc\Documents\New project 3\project"
scripts\start-local.ps1
```

然后执行完整 smoke test：

```powershell
scripts\smoke-test-local.ps1
```

如果只想验证本地链路，不想消耗 LLM 问答调用，可以使用：

```powershell
scripts\smoke-test-local.ps1 -SkipAiCalls
```

注意：`-SkipAiCalls` 仍可能在真实 embedding 配置下调用 embedding API，因为文件索引质量需要验证 embedding 链路。

## 6. 对未来部署的帮助

这个脚本可以作为 VPS 部署后的第一套人工验收流程。部署完成后，只需要把访问地址替换为服务器地址或在服务器本机执行同类检查，就能快速判断：

- 服务是否启动。
- 配置是否生效。
- 访问保护是否启用。
- LLM 和 Embedding 是否可调用。
- 文件和 RAG 主链路是否仍正常。
- 日志 request_id 是否可用于排查问题。

## 7. 安全边界

脚本会读取本地 `.env` 中的访问 header 和邀请码/口令用于本机请求，但不会打印真实邀请码、访问口令或 API Key。

脚本会上传一个临时 TXT 文件进行验证，完成后会调用删除 API 清理对应上传文件、vector_store 索引和数据库记录。

脚本不会提交或打印：

- `backend/.env`
- API Key
- 真实邀请码
- 上传文件内容
- vector_store chunk 内容
- embeddings
- SQLite 数据库
- 日志文件

## 8. 当前限制

- 该脚本假设前后端已经启动，不负责启动服务。
- 该脚本目前优先验证 Windows 本地环境。
- 完整模式会调用真实 LLM；真实 embedding 配置下也会调用 embedding API，因此会产生少量 API 调用成本。
- 该脚本不是端到端浏览器自动化测试，不验证所有 UI 细节。
