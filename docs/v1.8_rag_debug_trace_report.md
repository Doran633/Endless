# v1.8.1 RAG Debug Trace 实现报告

## 1. 本阶段目标

v1.8.1 不新增 AI 业务功能，不修改数据库结构，不引入 pgvector，不引入复杂 rerank，也不做多文件 RAG。

本阶段在现有单文件 RAG 闭环上新增轻量 debug trace，让每次文件问答都能看到基础检索质量摘要，便于后续判断 RAG 准确性问题来自检索、prompt、上下文还是模型回答。

## 2. 工程效果

RAG 问答现在会返回可选 `debug_trace`：

```text
trace_id
file_id
query
top_k
retrieved_count
max_score
min_score
average_score
used_chunk_ids
model
input_tokens
output_tokens
confidence
no_answer
```

前端文件中心和聊天侧 RAG 引用区域会展示摘要：

```text
Trace
置信度
命中片段数量
最高相关度
平均相关度
token 使用量
无答案判断
```

这让后续调参不再只凭感觉，而是可以观察每次回答背后的检索分数和片段命中情况。

## 3. 修改文件职责

### `backend/app/schemas/file.py`

新增 `RagDebugTrace` schema。

`AskFileResponse` 增加可选 `debug_trace` 字段。

`RetrieveFileResponse` 增加：

- `max_score`
- `min_score`
- `average_score`

用于观察检索结果分数分布。

### `backend/app/services/retrieval_service.py`

在现有 cosine similarity 排序结果基础上计算 score 摘要。

没有改变检索算法：

```text
query embedding
-> cosine similarity
-> sort by score
-> top_k
```

只是额外返回分数统计。

### `backend/app/services/rag_service.py`

在 RAG 回答生成后创建 `RagDebugTrace`。

新增轻量置信度分类：

```text
max_score >= 0.65 -> high
max_score >= 0.45 -> medium
else -> low
```

当前只是观测，不会阻止 LLM 回答。

`no_answer` 当前基于回答文本中是否包含“无法确认”或“未找到”做轻量判断。真正的检索阈值和无答案拦截会放到 v1.8.2。

### `backend/app/services/conversation_service.py`

RAG 问答持久化时，将 debug trace 摘要写入 assistant 消息 metadata。

这不修改数据库结构，因为 metadata 本来就是 JSON 字符串字段。

### `frontend/src/types/index.ts`

新增 `RagDebugTrace` 类型，并扩展：

- `AskFileResponse`
- `RetrieveFileResponse`
- `ChatMessageMetadata`
- `Message.metadata`

### `frontend/src/stores/chatStore.ts`

聊天侧 RAG 回答时，把 `debug_trace` 写入本地消息 metadata。

从后端恢复历史消息时，也会保留 metadata 中的 `debug_trace`。

### `frontend/src/components/FileCenter.tsx`

文件中心：

- 检索测试弹窗展示分数摘要。
- 文件问答结果展示 RAG 质量摘要。

### `frontend/src/components/MessageBubble.tsx`

聊天侧 RAG 引用区域展示 trace 摘要。

## 4. debug_trace 如何帮助判断 RAG 质量

### 4.1 判断检索是否命中

如果 `retrieved_count` 正常，但回答不准，需要看 chunks 是否相关。

如果 `retrieved_count` 为 0 或很低，说明检索阶段可能没有找到资料。

### 4.2 判断相关度是否可靠

通过：

```text
max_score
min_score
average_score
```

可以判断本次问题是否有明显相关片段。

例如：

- max_score 高，average_score 高：检索较稳定。
- max_score 高，average_score 低：可能只有一个片段相关。
- max_score 低，average_score 低：可能应该进入无答案策略。

### 4.3 判断 token 成本

通过：

```text
input_tokens
output_tokens
```

可以观察 prompt 长度和回答成本。后续调整 top_k、chunk_size、overlap 时，可以比较 token 是否明显增加。

### 4.4 判断模型是否拒答

`no_answer` 能帮助统计模型是否认为“资料中没有答案”。

当前这个字段只是轻量判断，不是最终质量指标。

## 5. 不展示的信息

本阶段不会展示：

- API Key。
- 邀请码。
- 完整 prompt。
- embeddings。
- 服务器真实路径。
- VectorStore 文件路径。

前端仍会展示引用 chunks，因为这是当前产品已有的文件问答依据展示能力。

## 6. 当前限制

- `confidence` 是基于 max_score 的简单分档，不是严格概率。
- 不同 embedding 模型的 score 分布不同，阈值不能直接照搬。
- `no_answer` 当前基于回答文本判断，后续应结合 score threshold。
- debug trace 当前不单独落库，只随 RAG 消息 metadata 保存摘要。
- 当前没有自动化 RAG 准确率评估测试集。
