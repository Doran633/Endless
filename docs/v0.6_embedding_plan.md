# v0.6 Embedding 抽象与调用计划

> 本计划用于 v0.6 开发阶段。
> 目标是在不实现向量数据库、不实现 RAG、不实现文件问答的前提下，完成 chunks 到 embedding vectors 的工程设计。

## 1. 当前状态

当前项目已经完成：

- v0.2 真实 LLM 聊天闭环。
- v0.3 真实文件上传闭环。
- v0.4 TXT / DOCX / 可复制文本型 PDF 文档解析闭环。
- v0.4.1 DOCX 表格解析增强。
- v0.4.2 北辰agent UI 简化优化。
- v0.5 文本切块闭环。

当前主链路：

```text
用户上传文件
  -> FileService 保存到 backend/uploads/
  -> DocumentParserService 读取文件并提取纯文本
  -> ChunkService 将文本切成 chunks
  -> 前端展示 chunk_count 和 chunk_preview
```

当前尚未完成：

- Embedding 调用。
- 向量存储。
- 向量检索。
- RAG 文件问答。
- chunk 持久化。
- 文件元数据数据库持久化。

v0.6 的任务是补上 RAG 链路中的“向量化”层：

```text
chunks
  -> EmbeddingService
  -> embedding vectors
```

## 2. 为什么 v0.6 只做 Embedding，不做向量数据库

Embedding 和向量数据库是两个不同阶段。

Embedding 解决的是：

```text
文本如何变成向量
```

向量数据库解决的是：

```text
向量如何存储、索引和检索
```

如果 v0.6 同时做 Embedding、VectorStore 和 RAG，会导致：

- Provider 抽象、向量维度、存储结构、检索策略同时变化。
- 很难判断 bug 来自 embedding 调用、向量写入，还是检索逻辑。
- 项目复杂度突然上升。
- 不利于学习真实 RAG 工程链路。

因此 v0.6 只做：

```text
chunk content
  -> embedding vector
```

不做：

```text
vector persistence
vector search
RAG answer
```

这样可以先验证 embedding 层的输入、输出、错误处理和配置方式。

## 3. Embedding 的作用

Embedding 是把文本转成一组数字向量。

例如一个 chunk：

```text
北辰agent 支持文档解析和文本切块。
```

经过 embedding 后变成：

```text
[0.012, -0.083, 0.221, ...]
```

这些数字表示文本语义。

后续 RAG 会用它来做相似度检索：

```text
用户问题
  -> query embedding
  -> 与 chunk embedding 做相似度计算
  -> 找出最相关 chunks
  -> 放入 LLM 上下文
```

所以 v0.6 的工程价值是：

- 为每个 chunk 生成向量。
- 明确 embedding provider 的输入输出。
- 为后续 VectorStore 提供稳定数据结构。

## 4. EmbeddingService 设计

### 4.1 职责

建议新增：

```text
backend/app/services/embedding_service.py
```

`EmbeddingService` 负责：

- 接收 chunk 列表。
- 选择 embedding provider。
- 调用 provider 生成 vectors。
- 返回 chunk 与 vector 的对应关系。
- 处理 embedding 配置错误和调用错误。

建议方法：

```text
embed_chunks(chunks: list[DocumentChunk]) -> EmbedChunksResponse
```

### 4.2 不做职责

`EmbeddingService` 不负责：

- 文档解析。
- 文本切块。
- 向量数据库写入。
- 向量检索。
- RAG prompt 组装。
- LLM 问答。

### 4.3 与现有服务关系

```text
DocumentParserService
  -> 提取全文

ChunkService
  -> 生成 chunks

EmbeddingService
  -> 生成 vectors

未来 VectorStore
  -> 保存 vectors
```

## 5. EmbeddingProvider 抽象设计

建议新增目录：

```text
backend/app/embedding/
```

建议文件：

```text
backend/app/embedding/base.py
backend/app/embedding/mock_provider.py
backend/app/embedding/openai_provider.py
```

### 5.1 抽象接口

建议接口：

```text
class EmbeddingProvider:
    def embed_texts(self, texts: list[str]) -> list[list[float]]:
        ...
```

输入：

- `texts`: chunk content 列表。

输出：

- `list[list[float]]`: 每个文本对应一个 vector。

约束：

- 输出数量必须等于输入文本数量。
- 每个 vector 维度必须稳定。
- provider 错误必须转换成应用级错误。

### 5.2 为什么需要 Provider 抽象

当前项目的 LLM 层已经使用：

```text
LLMProvider
MockLLMProvider
OpenAIProvider
```

Embedding 层也应该使用类似边界。

好处：

- 本地开发可以用 Mock。
- 真实环境可以切 OpenAI-compatible embedding。
- 后续可替换成本地 embedding 模型。
- Service 层不关心具体供应商。

## 6. MockEmbeddingProvider 设计

v0.6 建议先实现 `MockEmbeddingProvider`。

作用：

- 不依赖外部 API。
- 方便测试调用链。
- 保证每个 chunk 都能得到固定维度 vector。

建议行为：

```text
输入文本
  -> 根据文本内容生成稳定伪向量
  -> 返回固定维度 list[float]
```

建议维度：

```text
dimension = 8 或 16
```

为什么不直接随机：

- 随机结果不稳定。
- 测试难断言。

更好的 MVP Mock：

- 使用文本长度、字符编码和简单 hash 生成稳定向量。

示例：

```text
"hello" -> [0.12, 0.03, ...]
"hello" -> 每次结果相同
```

## 7. OpenAI-compatible Embedding Provider 预留方式

v0.6 可以先设计并预留 OpenAI-compatible Provider，不一定第一步就真实调用。

建议配置：

```text
EMBEDDING_PROVIDER=mock
EMBEDDING_MODEL=text-embedding-3-small
EMBEDDING_DIMENSION=1536
EMBEDDING_TIMEOUT_SECONDS=60
OPENAI_API_KEY=...
OPENAI_BASE_URL=...
```

如果使用 DeepSeek，需要注意：

- DeepSeek 当前主要用于 chat model。
- 是否提供 embedding endpoint 需要按实际平台能力确认。
- 如果没有 embedding API，应使用其他 OpenAI-compatible embedding 服务或本地 embedding 模型。

建议 v0.6 的 Provider 选择：

```text
mock
openai_compatible
```

OpenAI-compatible endpoint 形式通常是：

```text
POST {base_url}/embeddings
```

请求体：

```json
{
  "model": "text-embedding-3-small",
  "input": ["chunk 1", "chunk 2"]
}
```

响应中取：

```text
data[].embedding
```

## 8. API 设计

### 8.1 生成 chunk embeddings

建议接口：

```text
POST /api/v1/files/{file_id}/embeddings
```

请求体：

```json
{
  "extension": "txt"
}
```

说明：

- 当前没有数据库，后端无法直接读取已保存的 chunk。
- v0.6 可以沿用 MVP 链路：重新 parse -> chunk -> embed。
- 后续引入数据库后，应改成读取已保存 chunks。

后端流程：

```text
file_id + extension
  -> DocumentParserService.parse_text()
  -> ChunkService.chunk_text()
  -> EmbeddingService.embed_chunks()
  -> 返回 embedding 摘要
```

成功响应建议：

```json
{
  "code": 0,
  "message": "ok",
  "data": {
    "file_id": "uuid",
    "status": "embedded",
    "chunk_count": 5,
    "embedding_count": 5,
    "embedding_dimension": 16,
    "embedding_preview": [
      {
        "chunk_id": "uuid-0",
        "chunk_index": 0,
        "vector_preview": [0.12, -0.04, 0.31]
      }
    ]
  }
}
```

### 8.2 为什么不返回完整 vectors

不建议把完整 vectors 全部返回前端。

原因：

- 向量很长。
- 前端不需要直接展示完整向量。
- 大文档会返回大量数字，浪费网络。
- 后续完整 vectors 应交给 VectorStore。

v0.6 前端只需要知道：

- 是否生成成功。
- 生成了多少个 embedding。
- 维度是多少。
- 前几个 vector 的短预览。

## 9. 前端展示方案

### 9.1 文件中心最小改动

已切块文件显示“向量化”按钮。

状态建议：

- `chunked`：已切块。
- `embedding` 或 `processing`：向量化中。
- `embedded`：已向量化。
- `failed`：失败。

MVP 可以复用 `processing`，并新增 `embedded`。

### 9.2 展示字段

文件列表可以展示：

- `chunk_count`
- `embedding_count`
- `embedding_dimension`

预览弹窗显示：

```text
Embedding preview
Chunk 1: [0.12, -0.04, 0.31, ...]
Chunk 2: [...]
```

提示文案：

```text
已完成向量化。向量存储和 RAG 检索将在后续阶段开放。
```

### 9.3 不进入聊天区

v0.6 仍然不开放文件问答。

原因：

- 还没有 VectorStore。
- 还没有 retrieval。
- LLM 还拿不到检索上下文。

## 11. 风险和技术债

### 11.1 当前没有持久化

v0.6 如果只是返回 embedding 摘要，刷新页面后状态会丢失。

这是 MVP 阶段可接受的技术债。

后续 VectorStore 阶段必须解决。

### 11.2 重新 parse 和 chunk 成本

当前 API 可能每次重新执行：

```text
parse -> chunk -> embed
```

短文档可以接受。

长文档会变慢，也会增加 embedding 成本。

后续应保存：

- document text
- chunks
- embedding vectors

### 11.3 Mock embedding 不能代表真实语义

Mock embedding 只能验证工程链路。

它不能用于真实相似度检索。

因此不要用 mock embedding 评估 RAG 效果。

### 11.4 维度必须一致

同一个向量库中的 vectors 维度必须一致。

如果后续切换模型：

- `text-embedding-3-small`: 维度可能不同于其他模型。
- 本地模型维度也可能不同。

因此 v0.6 必须记录 `embedding_dimension`。

### 11.5 Provider 错误处理

真实 embedding API 可能出现：

- API Key 缺失。
- 超时。
- rate limit。
- input 太长。
- 返回维度异常。

v0.6 应该把这些转换成稳定 JSON 错误。

## 13. 后续如何接入 VectorStore 和 RAG

v0.6 完成后，后续路线：

```text
chunks
  -> EmbeddingService
  -> vectors
  -> VectorStore
  -> RetrievalService
  -> RagService
  -> LLMService
```

### v0.7 VectorStore

目标：

- 增加 `VectorStore` 抽象。
- 保存 chunk_id、file_id、content、embedding。
- 支持按 file_id 查询 vectors。

MVP 可选：

- 内存向量存储。
- 本地 JSON 存储。
- PostgreSQL + pgvector。

学习优先建议：

- 先做简单内存或本地存储理解流程。
- 再进入 PostgreSQL + pgvector。

### v0.8 Retrieval

目标：

- 对用户 query 生成 embedding。
- 计算 query vector 与 chunk vectors 的相似度。
- 返回 top_k chunks。

### v0.9 RAG 文件问答

目标：

- 将 top_k chunks 作为上下文。
- 调用 LLM。
- 返回基于文件内容的回答。

关键原则：

- Embedding 只负责向量化。
- VectorStore 只负责保存和检索向量。
- RagService 只负责编排检索结果和 LLM 上下文。

这样每一层都清楚，后续扩展和 debug 才不会乱。
