# v1.7.2 Runtime Backup and Restore 规划

## 1. 当前问题

当前项目已经完成公网部署验证，并开始具备小范围真实试用价值。

运行时数据已经不再只是临时开发文件，而是包含真实用户试用数据：

- SQLite 数据库：文件元数据、处理状态、会话、消息、匿名 client_id 归属。
- uploads：用户上传的原始文件。
- vector_store：本地 JSON 向量索引，包含 chunks 和 embeddings。
- logs：请求日志和错误排查信息。

当前主要问题：

1. 还没有固定备份流程。
2. 还没有恢复流程。
3. 部署更新前没有强制备份习惯。
4. SQLite、uploads 和 vector_store 必须一起看待，否则数据会不一致。
5. 服务器误操作或部署路径错误可能导致试用数据丢失。

v1.7.2 的目标是补齐最小备份和恢复能力，而不是引入复杂运维系统。

## 2. 为什么现在要做备份与恢复

在本地开发阶段，数据丢失通常只是“重新测一次”。

但公网试用后，数据开始有真实价值：

- 用户上传过的文件。
- 用户已经索引过的文档。
- 用户会话历史。
- RAG 问答记录。
- 排查线上错误需要的日志。

如果没有备份，风险会集中在几个场景：

- `git pull` 或手动部署时误删 runtime 目录。
- systemd 配置路径写错。
- SQLite 文件损坏。
- 服务器磁盘异常。
- 上传目录和 vector_store 不一致。
- 想回滚版本时没有可恢复数据。

因此，v1.7.2 应优先建立“部署前备份”和“必要时恢复”的最小闭环。

## 3. 备份对象

### 3.1 必须备份

生产环境必须备份：

```text
/opt/beichen-agent/runtime/data/
/opt/beichen-agent/runtime/uploads/
/opt/beichen-agent/runtime/vector_store/
```

对应含义：

- `data/`：SQLite 数据库。
- `uploads/`：原始上传文件。
- `vector_store/`：本地 JSON 向量索引。

这三者必须保持一致。

如果只备份 SQLite，不备份 uploads，文件列表可能存在但原始文件丢失。

如果只备份 uploads，不备份 vector_store，RAG 索引需要重新生成。

如果只备份 vector_store，不备份 SQLite，前端文件列表和会话绑定会丢失。

### 3.2 建议备份

建议备份：

```text
/opt/beichen-agent/runtime/logs/
```

日志不是核心业务数据，但在排查线上问题时有价值。

### 3.3 不放入 Git 的内容

以下内容绝不能提交 GitHub：

```text
backend/.env
runtime/backend.env
runtime/data/
runtime/uploads/
runtime/vector_store/
runtime/logs/
*.db
*.sqlite
*.sqlite3
*.log
backup archives
```

备份文件也不应提交 Git。

## 4. 备份策略

### 4.1 MVP 推荐策略

当前 1-5 人可信试用阶段，推荐使用：

**手动触发 + 本地服务器压缩包备份。**

暂不引入：

- 对象存储。
- 自动异地灾备。
- 数据库复制。
- 复杂定时任务。
- 专业备份平台。

原因：

- 当前数据量小。
- 当前用户少。
- 当前部署还处于学习和验证阶段。
- 手动备份更容易理解和排查。

### 4.2 备份时机

建议在以下时机备份：

1. 每次部署更新前。
2. 每次修改 systemd / Nginx / runtime 路径前。
3. 每次清理服务器文件前。
4. 用户上传重要测试文件后。
5. 每周固定一次。

### 4.3 备份文件命名

建议备份文件命名：

```text
beichen-runtime-YYYYMMDD-HHMMSS.tar.gz
```

示例：

```text
beichen-runtime-20260804-153000.tar.gz
```

备份目录建议：

```text
/opt/beichen-agent/backups/
```

## 5. 恢复策略

### 5.1 恢复原则

恢复不是普通操作，必须谨慎。

恢复前应：

1. 停止后端服务。
2. 再备份一次当前 runtime。
3. 解压指定备份。
4. 检查文件归属和权限。
5. 重启后端。
6. 验证 `/health` 和 `/health/config`。
7. 验证文件列表、会话列表和 RAG 问答。

### 5.2 恢复范围

MVP 阶段建议恢复整个 runtime 数据包，而不是只恢复某一个文件。

原因：

- SQLite、uploads、vector_store 存在一致性关系。
- 局部恢复容易造成文件记录存在但文件缺失，或索引存在但数据库缺失。

### 5.3 恢复后的检查

恢复后必须检查：

- 后端服务是否 active。
- `/health` 是否返回 ok。
- `/health/config` 路径是否指向正确 runtime。
- 文件中心是否能恢复文件列表。
- 历史会话是否能恢复。
- 已 indexed 文件是否还能 RAG 问答。

## 6. 建议新增文件

### 6.1 `deploy/scripts/backup-runtime.sh.example`

职责：

- 在 Ubuntu VPS 上执行 runtime 数据备份。
- 检查 runtime 目录是否存在。
- 创建 backups 目录。
- 生成带时间戳的 `.tar.gz` 压缩包。
- 默认备份 data、uploads、vector_store。
- 可选包含 logs。
- 输出备份路径。

安全边界：

- 不打印 API Key。
- 不打印邀请码。
- 不提交真实备份文件。
- 不删除任何数据。

### 6.2 `deploy/scripts/restore-runtime.sh.example`

职责：

- 在 Ubuntu VPS 上从指定备份恢复 runtime 数据。
- 要求用户显式传入备份文件路径。
- 提醒恢复会覆盖当前 runtime。
- 停止或提示停止 systemd 服务。
- 解压备份到 runtime 目录。
- 检查权限。
- 提示重启服务和运行 smoke test。

安全边界：

- 不自动下载远程文件。
- 不自动删除 backups 目录。
- 不恢复真实 `.env`，除非后续明确需要。

### 6.3 `docs/v1.7_backup_restore_report.md`

职责：

- 记录本阶段实现内容。
- 说明备份对象。
- 说明恢复流程。
- 说明如何验证。
- 说明风险和限制。

## 7. 建议脚本设计

### 7.1 备份脚本参数

建议支持：

```bash
./backup-runtime.sh.example
./backup-runtime.sh.example --include-logs
```

默认配置：

```bash
APP_ROOT=/opt/beichen-agent
RUNTIME_DIR=/opt/beichen-agent/runtime
BACKUP_DIR=/opt/beichen-agent/backups
```

备份内容：

```text
runtime/data
runtime/uploads
runtime/vector_store
```

可选：

```text
runtime/logs
```

### 7.2 恢复脚本参数

建议支持：

```bash
./restore-runtime.sh.example /opt/beichen-agent/backups/beichen-runtime-YYYYMMDD-HHMMSS.tar.gz
```

恢复流程：

1. 检查备份文件存在。
2. 提示用户确认。
3. 检查 runtime 目录。
4. 建议先停止 `beichen-agent` 服务。
5. 解压备份。
6. 修正 `www-data:www-data` 权限。
7. 提示重启后端和运行验证。

## 8. 部署更新中的备份流程

每次服务器更新前建议执行：

```bash
cd /opt/beichen-agent/app
sudo bash deploy/scripts/backup-runtime.sh.example
```

然后再执行：

```bash
sudo -u www-data git pull origin main
cd frontend
sudo -u www-data npm install
sudo -u www-data npm run build
sudo systemctl restart beichen-agent
sudo nginx -t
sudo systemctl reload nginx
curl http://127.0.0.1:8000/health
curl http://127.0.0.1:8000/health/config
```

如果更新失败，再根据备份进行恢复。

## 9. 测试方案

### 9.1 本地静态检查

需要运行：

```powershell
python -m compileall app
npm exec tsc -- --noEmit
```

### 9.2 脚本语法检查

在 Windows 本地无法完整执行 Linux shell 脚本，但可以检查：

- 文件存在。
- 无真实 API Key。
- 无真实邀请码。
- 无真实服务器密码。
- 脚本不包含危险的无边界删除命令。

### 9.3 服务器手动验证

在 Ubuntu VPS 上验证：

1. 运行备份脚本。
2. 确认 backups 目录生成 `.tar.gz`。
3. 查看压缩包内容包含 data、uploads、vector_store。
4. 不立即执行真实恢复，除非先备份当前数据。
5. 在测试目录中试解压，确认结构正确。

## 10. 风险和技术债

### 10.1 当前备份方案的限制

- 仍是手动备份。
- 没有自动定时。
- 没有异地备份。
- 没有加密备份。
- 没有版本化恢复 UI。

### 10.2 为什么当前可以接受

当前项目仍是个人 MVP 和小范围可信试用。

手动备份已经能显著降低：

- 部署误操作风险。
- 数据误删风险。
- 回滚无数据可用风险。

### 10.3 后续升级方向

未来可以升级为：

- cron 定时备份。
- 备份上传对象存储。
- 加密备份。
- PostgreSQL 后使用 `pg_dump`。
- pgvector 后增加向量索引备份策略。

## 11. 不做范围

v1.7.2 不做：

- 不新增 AI 功能。
- 不修改 RAG 主链路。
- 不修改数据库结构。
- 不迁移 PostgreSQL。
- 不引入对象存储。
- 不引入 Docker。
- 不引入 CI/CD。
- 不实现自动定时备份。
- 不提交真实备份文件。
- 不提交真实 `.env`。
