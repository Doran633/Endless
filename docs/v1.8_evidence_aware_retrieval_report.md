# v1.8.8 Evidence-aware Retrieval 报告

## 1. 工程效果

v1.8.8 在现有单文件 RAG 检索链路中增加了 evidence-aware scoring，用于区分：

- 语义相关：chunk 和 query 看起来相似。
- 可作为证据：chunk 能直接支撑答案。

本阶段重点解决 v1.8.7 测试中暴露的问题：

- 短标题 chunk 可能获得较高相关度，但不能支撑答案。
- 泛相关配置片段、RAG 指标片段可能混入 used_chunks。
- 回答本身正确，但引用片段的 citation_score 偏低。

实现后，RetrievalResult 会返回：

- `evidence_score`
- `evidence_level`
- `evidence_reason`

前端文件中心和聊天侧 RAG 引用区域会展示 evidence 诊断信息，便于人工测评。

## 2. 修改文件职责

- `backend/app/services/retrieval_service.py`
  - 新增 evidence-aware scoring。
  - 识别 title-only chunk。
  - 对明确事实、数字、单位、支持/不支持、文件类型等内容加 evidence bonus。
  - 对过短、只有标题、缺少说明性内容、意图噪声片段加 evidence penalty。
  - final_score 纳入 evidence_score。

- `backend/app/services/rag_service.py`

## 3. evidence_score 计算规则

当前 evidence_score 是轻量规则分，不调用 LLM。

加分规则：

- `evidence_bonus:explicit_fact`
  - chunk 包含明确事实信号，例如数字、单位、TXT / DOCX / PDF、支持/不支持、上限、上传、解析、切块、向量、索引、部署等。

- `evidence_bonus:body_length`
  - normal chunk 内容长度足够，说明它更可能包含正文证据，而不只是标题。

- `evidence_bonus:overview_summary`
  - overview 问题命中 section_summary chunk 时加分。

降权规则：

- `evidence_penalty:title_only`
  - chunk 很短、没有正文、没有事实信号、没有解释性标点，认为是标题类片段。

- `evidence_penalty:thin_content`
  - chunk 缺少句号、冒号、换行、枚举等说明性信号。

- `evidence_penalty:intent_noise`
  - 当前配置、RAG 质量指标等片段在非对应 intent 中出现时降权。

最终分数：

```text
final_score = raw_score
            + keyword_bonus
            + section_boost
            + answerability_bonus
            + evidence_score
            - section_penalty
            - length_penalty
```

## 4. title-only chunk 识别方式

当前规则认为一个 chunk 可能是 title-only，当它满足：

- 不是 section_summary。
- 字符数较短。
- 没有换行。
- 没有明确事实信号。
- 没有句号、冒号、逗号、枚举、竖线等说明性信号。

这类片段并不一定完全无关，但通常不能直接支撑答案，所以会被标记为 weak evidence 并降权。

## 5. evidence_level 划分

- `strong`
  - evidence_score 较高，通常包含明确事实或有效 summary。

- `medium`
  - 具备一定正文信息，但证据强度不算特别高。

- `weak`
  - title-only、过短、噪声或证据分明显为负。

RAG 生成阶段只使用 `strong` 和 `medium` chunks。

## 6. RAG prompt 如何过滤弱证据

v1.8.8 后，RagService 不再把所有 retrieved chunks 都交给 LLM：

```text
retrieved chunks
-> 过滤 evidence_level = weak
-> strong / medium chunks 进入 RAG prompt
-> 如果没有可用证据，直接触发 no-answer policy
```

这样可以减少“标题高相关但不能支撑答案”的情况，提高 citation_score。

## 7. 为什么这一步不做 rerank

当前阶段不做 rerank，原因是：

- 项目仍处于单文件 RAG 质量打磨阶段。
- rerank 会增加模型依赖、成本和延迟。
- 当前问题主要是可解释规则能覆盖的 evidence 质量问题。
- 先建立透明规则和测评基线，更适合 MVP 演进。

等 evidence-aware retrieval 的收益和边界清楚后，再考虑 Hybrid Retrieval 或 rerank 更稳妥。

## 8. 如何重新评估 citation_score

测试步骤：

1. 重新上传同一份测试文档。
2. 等待自动完成解析、切块、embedding 和索引。
3. 使用固定问题集重新测试。
4. 重点观察：
   - title-only chunk 是否下降。
   - 正文事实 chunk 是否上升。
   - evidence_level 是否符合人工判断。
   - citation_score 是否从 0.5-1.5 区间上移。
   - no-answer 问题是否仍保持谨慎。

建议优先复测：

- 北辰agent 当前完成了哪些核心能力？
- 当前支持上传哪些文件类型？
- 单个上传文件大小上限是多少？
- 当前试运行人数上限是多少？
- 当前是否支持微信登录？
- 当前是否支持扫描件 PDF OCR？

## 9. 当前限制

- evidence_score 仍是规则评分，不是语义推理。
- 对复杂长文档、表格、跨章节问题仍可能不足。
- 新规则需要通过更强测试集继续校准。
- 本阶段没有引入 pgvector、多文件 RAG、rerank 或 LLM 评分。
