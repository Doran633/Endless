# v0.9.0 RAG 文件问答开发计划

> 本计划用于 v0.9.0 开发阶段。目标是在现有文件上传、文档解析、文本切块、mock embedding、本地 VectorStore 和 RetrievalService 的基础上，实现最小 RAG 文件问答闭环。

## 1. 当前状态

当前项目已经完成到 v0.8.0 Local Retrieval Loop。

已具备的后端能力：

- `ChatService`：负责普通 AI 聊天调用。
- `LLMProvider` / `MockLLMProvider` / `OpenAIProvider`：负责隔离具体模型调用方式。
- `FileService`：负责上传文件保存到 `backend/uploads/`。
- `DocumentParserService`：负责 TXT / DOCX / 可复制文本型 PDF 的文本解析。
- `ChunkService`：负责把解析文本切成 chunks。
- `EmbeddingService` / `MockEmbeddingProvider`：负责为 chunks 或 query 生成稳定 mock vectors。
- `VectorStoreService`：负责把 chunks 和 mock vectors 保存到 `backend/vector_store/{file_id}.json`。
- `RetrievalService`：负责读取本地向量索引，基于 query embedding 和 cosine similarity 返回 top_k chunks。

已具备的前端能力：

- 普通聊天可以调用真实 LLM。
- 文件中心可以上传文件、解析、切块、mock 向量化、保存本地索引。
- 聊天侧可以上传文件并自动完成处理流程。
- 文件中心可以对 indexed 文件执行检索，并展示相关 chunks。

当前缺失：

- 还不能基于文件内容生成自然语言答案。
- 还没有 `RagService`。
- 还没有 `/api/v1/files/{file_id}/ask` 文件问答接口。
- 还没有 RAG prompt 组装逻辑。
- 前端还没有真正的文件问答结果展示。

## 2. 为什么现在可以进入 RAG

RAG 的最小链路可以拆成两部分：

```text
Retrieval
  -> 找到与问题相关的上下文 chunks

Generation
  -> 把上下文交给 LLM 生成答案
```

v0.8.0 已经完成 Retrieval：

```text
query
  -> query embedding
  -> VectorStore 检索
  -> top_k chunks
```

因此 v0.9.0 可以在不改变底层文件处理能力的前提下，补上 Generation：

```text
top_k chunks
  -> RAG prompt
  -> LLM answer
```

现在进入 RAG 的原因是：

- 文件已经可以上传和解析。
- 文本已经可以切块。
- chunks 已经可以生成 mock vectors。
- 本地 VectorStore 已经可以保存和读取索引。
- RetrievalService 已经可以返回相关上下文。
- 真实 LLM 聊天链路已经在 v0.2 完成。

也就是说，RAG 所需的两个核心输入已经存在：

- 用户问题。
- 与问题相关的文档片段。

v0.9.0 不需要重新设计架构，只需要把现有模块按清晰边界编排起来。

## 3. RagService 设计

建议新增：

```text
backend/app/services/rag_service.py
```

`RagService` 的职责：

- 接收 `file_id`、`query`、`top_k`。
- 调用 `RetrievalService.retrieve()` 获取相关 chunks。
- 根据 chunks 和 query 组装 RAG prompt。
- 调用现有 `LLMProvider` 生成答案。
- 返回答案和引用 chunks。

`RagService` 不负责：

- 文件上传。
- 文档解析。
- 文本切块。
- embedding 生成细节。
- 向量索引保存。
- 多文件检索。
- Agent 工作流。
- 数据库持久化。

建议内部结构：

```text
RagService
  retrieve context
  build prompt
  call llm provider
  return answer with used chunks
```

建议方法：

```text
ask_file(file_id: str, query: str, top_k: int = 3) -> AskFileResponse
```

辅助方法：

```text
_build_prompt(query: str, chunks: list[RetrievalResult]) -> str
```

设计原则：

- `RetrievalService` 只负责找上下文。
- `RagService` 只负责编排 RAG 问答。
- `LLMProvider` 仍然负责具体模型调用。
- prompt 暂时写在 `RagService` 内部，不提前引入复杂 prompt 管理系统。

## 4. API 设计

新增接口：

```text
POST /api/v1/files/{file_id}/ask
```

请求体：

```json
{
  "query": "这个文件主要讲了什么？",
  "top_k": 3
}
```

字段说明：

- `query`：用户针对该文件提出的问题，必填。
- `top_k`：使用多少个相关 chunks，默认 3，建议限制为 1 到 8。

响应体：

```json
{
  "file_id": "xxx",
  "query": "这个文件主要讲了什么？",
  "answer": "根据文档内容，...",
  "top_k": 3,
  "used_chunk_count": 3,
  "used_chunks": [
    {
      "chunk_id": "xxx_chunk_0001",
      "chunk_index": 0,
      "content": "相关文本片段...",
      "char_count": 300,
      "score": 0.86
    }
  ],
  "provider": "openai-compatible",
  "model": "deepseek-v4-flash"
}
```

后端调用链：

```text
frontend
  -> POST /api/v1/files/{file_id}/ask
  -> files.py router
  -> RagService.ask_file()
  -> RetrievalService.retrieve()
  -> VectorStoreService.load_file_vectors()
  -> EmbeddingService / MockEmbeddingProvider
  -> RagService._build_prompt()
  -> LLMProvider.generate()
  -> response
```

错误处理：

- 文件未索引：返回明确错误，提示需要先完成索引保存。
- query 为空：返回参数错误。
- 检索结果为空：返回无法找到相关内容。
- LLM 调用失败：沿用当前 LLM 错误处理，不暴露 API Key 或内部异常细节。

## 5. Prompt 组装方案

v0.9.0 不引入复杂 prompt 模板系统，只在 `RagService` 内部使用一个简单、可读、可测试的 prompt。

建议 prompt 结构：

```text
你是一个严谨的文档问答助手。
请只根据提供的文档片段回答用户问题。
如果文档片段中没有足够信息，请明确说明“根据当前文档内容无法确认”。
不要编造文档中不存在的信息。

用户问题：
{query}

文档片段：
[片段 1 | score={score}]
{chunk_content}

[片段 2 | score={score}]
{chunk_content}

请用中文回答，回答要简洁、准确，并尽量指出依据来自哪些片段。
```

设计原因：

- 限制 LLM 不要脱离文档内容。
- 允许答案承认信息不足。
- 保留 score 和片段编号，便于调试。
- 先保证最小闭环，不提前做引用格式、长上下文压缩、重排序等复杂能力。

需要控制的风险：

- chunks 过长会导致 prompt 太大。
- mock embedding 的检索质量有限，答案质量也会受影响。
- LLM 仍可能产生幻觉，因此 prompt 必须强调“只根据文档片段回答”。

## 6. 前端交互方案

文件中心保留现有能力，并新增“问答”入口。

建议交互：

- 对 `indexed` 状态文件展示“问答”按钮。
- 点击后打开文件问答 Modal。
- 用户输入问题和 top_k。
- 点击提交后调用 `/api/v1/files/{file_id}/ask`。
- 前端展示：
  - AI 答案。
  - 使用的 chunks。
  - 每个 chunk 的 score、chunk_index、content。

展示原则：

- 答案放在上方。
- 引用 chunks 放在下方，可折叠或用简洁列表展示。
- 明确标注这是“基于当前文件索引生成的回答”。
- 不把文件问答结果混入普通聊天历史，避免 v0.9 范围膨胀。

暂不做：

- 聊天页直接文件问答。
- 多文件选择。
- 引用高亮。
- 流式输出。
- 问答历史保存。

## 7. 风险和技术债

### 风险 1：Mock embedding 检索质量有限

当前使用的是稳定 mock vector，不是真实语义 embedding。因此检索结果只能验证工程链路，不能代表真实语义检索效果。

影响：

- 有些问题可能检索不到最相关片段。
- LLM 的回答质量会受上下文质量影响。

处理方式：

- v0.9.0 接受这个限制。
- v1.0 前再接真实 embedding provider。

### 风险 2：RAG prompt 可能过长

如果 top_k 较大或 chunk 内容较长，prompt 会变大。

影响：

- LLM 调用变慢。
- token 成本增加。
- 可能超过模型上下文限制。

处理方式：

- v0.9.0 限制 top_k。
- 后续再增加上下文长度控制和 chunk 内容截断。

### 风险 3：前端状态仍以内存为主

当前没有数据库，刷新页面后前端状态可能与后端本地文件不完全一致。

影响：

- 已上传和已索引文件在后端存在，但前端列表未必能完整恢复。

处理方式：

- v0.9.0 不解决。
- 后续进入数据库阶段再统一处理文件元数据、解析状态、索引状态。

### 风险 4：文件问答边界容易膨胀

RAG 一旦可用，很容易继续加入多文件问答、聊天内引用、历史记忆、权限、Agent 等能力。

处理方式：

- v0.9.0 只做单文件问答。
- 不做 Agent。
- 不做多文件检索。
- 不做企业权限。

### 风险 5：答案可靠性需要明确提示

即使 prompt 写得谨慎，LLM 仍可能补充文档外信息。

处理方式：

- prompt 中明确要求只基于文档片段回答。
- 前端展示 used chunks，方便用户核对。
- 后续增加“无法回答”判断和引用检查。

## 8. 测试方案

后端验证：

```text
python -m compileall app
```

接口链路测试：

1. 上传 TXT 文件。
2. 调用 `/parse`。

4. 调用 `/embeddings`。
5. 调用 `/vector-store`。
6. 调用 `/ask`。
7. 确认返回 answer 和 used_chunks。

建议测试问题：

```text
这个文档主要讲了什么？
文档里提到了哪些风险？
根据文档，下一步建议是什么？
```

前端验证：

```text
npm exec tsc -- --noEmit
```

浏览器验证：

- 启动后端固定端口 `8000`。
- 启动前端固定端口 `5173`。
- 上传 TXT / DOCX / PDF。
- 完成解析、切块、向量化、索引保存。
- 在文件中心点击“问答”。
- 输入问题。
- 确认能看到答案和引用 chunks。

范围检查：

- 不应新增数据库。
- 不应新增 pgvector。
- 不应实现多文件问答。
- 不应新增 Agent。
- 不应把文件内容直接塞进普通聊天输入。

## 9. 后续如何扩展到多文件 RAG 和 Agent

### 多文件 RAG

当前 v0.9.0 只做单文件：

```text
file_id + query -> answer
```

后续可以扩展为：

```text
file_ids[] + query -> multi-file retrieval -> answer
```

需要新增：

- 多文件检索参数。
- 跨文件 top_k 合并排序。
- chunk 中携带 file_id、original_name。
- 前端文件选择器。
- 更清晰的引用展示。

### 真实 embedding

当前是 mock embedding，后续需要新增：

- OpenAI-compatible embedding provider。
- embedding API Key 配置。
- embedding model 配置。
- 维度校验。
- 向量重建机制。

### 数据库和 pgvector

当前本地 JSON 适合 MVP 验证，不适合正式使用。

后续引入数据库时：

- 文件元数据进入 PostgreSQL。
- chunks 进入数据库表。
- embeddings 进入 pgvector。
- VectorStoreService 替换为 pgvector 查询实现。
- API 层保持尽量不变。

### Agent Workflow

Agent 不应在 v0.9.0 引入。等 RAG 闭环稳定后，再把确定性流程抽象成 workflow。

未来 Agent 可以调用的工具：

- 文件上传工具。
- 文档解析工具。
- 检索工具。
- RAG 问答工具。
- 数据分析工具。

建议演进顺序：

```text
v0.9 单文件 RAG
  -> v1.0 真实 embedding + 基础稳定性
  -> v1.1 数据库 / pgvector
  -> v1.2 多文件知识库
  -> v1.3 Agent Workflow
```
