# v1.0.0 Real Embedding MVP 开发计划

> 本计划用于 v1.0.0 阶段。目标是在不改变当前 RAG 主链路结构的前提下，把 embedding 从 mock 工程验证升级为真实语义向量，并整理项目到可以准备 GitHub 分享的状态。

## 1. 当前状态

当前项目已完成 v0.9.1 Chat-side RAG QA。

已具备能力：

```text
聊天框上传文件
  -> 文件上传
  -> 文档解析
  -> 文本切块
  -> mock embedding
  -> 本地 JSON VectorStore
  -> Retrieval 检索
  -> RagService 文件问答
  -> 聊天消息流展示答案和引用 chunks
```

当前后端已有 embedding 抽象：

- `backend/app/embedding/base.py`
  - `EmbeddingProvider`
  - `embed_texts(texts: list[str]) -> list[list[float]]`
- `backend/app/embedding/mock_provider.py`
  - `MockEmbeddingProvider`
  - 使用 `sha256` 生成稳定 mock vectors
- `backend/app/services/embedding_service.py`
  - 根据 `settings.embedding_provider` 创建 provider
  - 当前仅支持 `mock`
  - 负责校验 vector 数量和维度
- `backend/app/core/config.py`
  - 已有 `EMBEDDING_PROVIDER`
  - 已有 `EMBEDDING_MODEL`
  - 已有 `EMBEDDING_DIMENSION`
  - 已有 `EMBEDDING_TIMEOUT_SECONDS`

当前主要限制：

- embedding 仍是 mock，不具备真实语义能力。
- Retrieval 的 cosine similarity 工程链路可用，但检索质量受 mock vector 限制。
- 本地 `backend/vector_store/` 中的旧索引如果由 mock embedding 生成，接入真实 embedding 后需要重新索引。
- 根目录暂未看到 `README.md`。
- `.gitignore` 已忽略 `.env`、`backend/uploads/`、`backend/vector_store/`，但还应明确忽略 `.claude/` 等本地工具配置。

## 2. 为什么 v1.0 要做真实 embedding

v0.9.1 已经证明 RAG 工程闭环成立：

```text
file_id + query
  -> retrieve chunks
  -> build prompt
  -> call LLM
  -> answer
```

但当前检索不是真实语义检索。

mock embedding 的作用是：

- 验证接口结构。
- 验证向量维度校验。
- 验证 VectorStore JSON 存储。
- 验证 cosine similarity 排序。
- 验证前端状态流。

mock embedding 不能保证：

- 相似问题命中相似 chunk。
- 同义表达能被检索到。
- 长文档中相关片段排序合理。
- RAG 回答质量稳定。

因此 v1.0 的核心不是新增更多功能，而是把当前最重要的能力做实：

```text
真实 embedding
  -> 更准确 Retrieval
  -> 更可靠 RAG context
  -> 更好的文件问答答案
```

完成 v1.0 后，项目才更适合作为 GitHub 可演示 MVP 分享给别人。

## 3. Embedding Provider 设计

### 3.1 保持现有抽象

继续使用当前接口：

```python
class EmbeddingProvider(ABC):
    @abstractmethod
    def embed_texts(self, texts: list[str]) -> list[list[float]]:
        ...
```

设计原则：

- 不改 `EmbeddingService` 对外职责。
- 不改 `ChunkService`。
- 不改 `VectorStoreService`。
- 不改 `RetrievalService`。
- 不改 `RagService`。

### 3.2 新增真实 Provider

建议新增：

```text
backend/app/embedding/openai_provider.py
```

类名：

```text
OpenAIEmbeddingProvider
```

职责：

- 调用 OpenAI-compatible embeddings API。
- 从 `settings` 读取 API Key、base URL、model 和 timeout。
- 接收 `texts: list[str]`。
- 返回 `list[list[float]]`。
- 校验响应格式。
- 把网络错误转换为 `EmbeddingProviderError`。
- 缺少配置时抛出 `EmbeddingConfigError`。

建议请求路径：

```text
{EMBEDDING_BASE_URL}/embeddings
```

请求体示例：

```json
{
  "model": "text-embedding-3-small",
  "input": ["chunk text 1", "chunk text 2"]
}
```

响应读取：

```text
data[].embedding
```

### 3.3 Provider 选择

`EmbeddingService._create_provider()` 增加：

```text
mock -> MockEmbeddingProvider
openai -> OpenAIEmbeddingProvider
```

这样 `.env` 中可以切换：

```env
EMBEDDING_PROVIDER=mock
```

或：

```env
EMBEDDING_PROVIDER=openai
```

### 3.4 为什么不复用 LLM 的 OPENAI_API_KEY

可以支持默认复用，但建议给 embedding 独立配置：

```env
EMBEDDING_API_KEY=
EMBEDDING_BASE_URL=
```

原因：

- LLM 和 embedding 可能来自不同服务商。
- LLM 模型和 embedding 模型权限可能不同。
- 成本、限流、base URL 可能不同。

MVP 可做一个温和 fallback：

```text
EMBEDDING_API_KEY 未设置时，可回退到 OPENAI_API_KEY
EMBEDDING_BASE_URL 未设置时，可回退到 OPENAI_BASE_URL
```

但文档中应鼓励显式配置 embedding。

- `backend/.env` 不提交 Git。
- `.env.example` 只放空值或示例值。
- 前端不接触任何 API Key。

## 6. 重新索引流程

接入真实 embedding 后，旧的 mock 索引不能代表真实语义。

原因：

- mock vector 默认维度是 16。
- 真实 embedding 通常是 768、1024、1536 或更高维度。
- `RetrievalService` 会校验 query vector 和 stored vector 维度一致。
- 即使维度一致，mock vector 也没有语义意义。

v1.0 推荐重新索引方式：

### 6.1 MVP 手动重新索引

最简单方式：

1. 切换 `.env`：

```env
EMBEDDING_PROVIDER=openai
```

2. 重启后端。
3. 重新上传文件。
4. 系统自动重新解析、切块、真实 embedding、保存 VectorStore。

### 6.2 文件中心重新索引

如果文件已在前端状态中，可在文件中心重新执行：

```text
向量化 -> 索引
```

但当前没有数据库，刷新后文件列表不可恢复，所以更可靠的是重新上传。

### 6.3 暂不做批量重建

v1.0 不做：

- 批量 rebuild API。
- 后台任务队列。
- 索引版本迁移。
- 混合 mock/real 索引管理。

这些等数据库阶段再做。

## 7. RAG 检索质量提升方案

v1.0 的主要质量提升来自真实 embedding。

建议保持 Retrieval 逻辑不变：

```text
query embedding
  -> cosine similarity
  -> top_k chunks
```

可做的轻量优化：

- 默认 top_k 保持 3。
- `/ask` 最大 top_k 保持 8 或收敛到 5。
- RAG prompt 中限制每个 chunk 的最大字符数，避免上下文过长。
- 在响应中继续返回 used_chunks，方便用户核对。
- VectorStore 中记录真实 `embedding_model` 和 `embedding_dimension`。

暂不做：

- rerank model。
- hybrid search。
- BM25。
- semantic chunk。
- query rewrite。
- 多轮 RAG。

原因：

- 当前最需要证明真实 embedding 后的效果提升。
- 过早加入 rerank 或 hybrid search 会让问题定位变难。

## 10. 风险和技术债

### 10.1 Embedding 服务商兼容性

不同 OpenAI-compatible 服务可能响应格式略有差异。

处理：

- v1.0 先支持标准 `/embeddings` 格式。
- 不为多个服务商写分支。

### 10.2 维度配置错误

如果 `.env` 中 `EMBEDDING_DIMENSION` 与真实模型不一致，会造成检索失败或误导。

处理：

- Provider 返回后以后端实际 vector 长度为准。
- VectorStore 保存实际 dimension。
- 文档中要求用户填写正确维度。

### 10.3 成本和限流

真实 embedding 会产生 API 成本。

处理：

- 只在上传/重新索引时调用 embedding。
- 不做频繁自动重建。
- query embedding 每次检索会调用一次 provider。

### 10.4 本地 JSON VectorStore 不适合生产

当前仍使用本地 JSON。

限制：

- 不适合大文件。
- 不适合多人并发。
- 不适合多文件知识库。

处理：

- v1.0 接受。
- 后续数据库阶段再迁移到 PostgreSQL / pgvector。

### 10.5 前端状态仍不持久

刷新页面后：

- 聊天历史不会完整恢复。
- active RAG 文件绑定会丢失。
- 文件列表可能不反映后端已有文件。

处理：

- v1.0 接受。
- 后续数据库阶段统一解决。
