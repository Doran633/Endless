# v1.8.5 Query Intent and Ranking Reason 报告

## 1. 本阶段工程效果

本阶段在 v1.8.4 的 raw / bonus / final 评分基础上，继续增强检索排序的可解释性。

新增能力：

- RetrievalService 支持轻量 query intent 识别。
- 支持 `capability`、`limit`、`deployment`、`usage`、`quantity`、`general` 六类 intent。
- 根据 query intent 和 `section_path` 进行 section boost / penalty。
- 对标题类或极短 chunk 增加 length penalty。
- 对数值型问题中包含数字或单位的 chunk 增加 answerability bonus。
- `RetrievalResult` 增加 query_intent、section_boost、section_penalty、length_penalty、answerability_bonus 和 ranking_reason。
- 前端文件中心和聊天侧展示主要加减分字段和 ranking_reason。

本阶段没有新增 AI 业务功能，没有修改数据库结构，没有引入 pgvector、rerank 或多文件 RAG。

## 3. query intent 识别规则

当前使用规则识别，不调用 LLM。

识别顺序：

1. `quantity`：包含“多少、几人、人数、数量、上限、大小、MB、GB”等。
2. `limit`：包含“限制、风险、不支持、缺陷、问题、失败”等。
3. `deployment`：包含“服务器、部署、配置、Nginx、systemd、VPS、SQLite、HTTPS、域名”等。
4. `usage`：包含“怎么、如何、流程、步骤、使用、操作、上传后”等。
5. `capability`：包含“功能、能力、核心、完成、支持、可以、文件类型、上传、能做”等。
6. `general`：未命中上述规则。

这个顺序是有意设计的。例如“上传大小限制是多少”会优先进入 `quantity`，因为它问的是数值事实。

## 4. section boost / penalty 原理

section boost 利用 v1.8.3 已经保存的 `section_path`。

例如：

```text
当前已完成功能 > 文件上传与自动处理
```

当 query intent 是 `capability`、`quantity` 或 `usage` 时，这类功能章节会获得轻量加分。

当 query intent 不是对应类型时，配置类、RAG 指标类、限制风险类片段可能被降权。

目标不是硬编码答案，而是让系统知道：

```text
问功能时，功能章节更可能是答案。
问限制时，限制章节更可能是答案。
问部署时，配置章节更可能是答案。
```

## 5. short chunk penalty 原理

短标题容易被 embedding 误判为高度相关。

例如：

```text
北辰agent 小范围上线试运行计划
```

它和“运行人数上限是多少”语义接近，但本身没有答案。

因此当前规则会对低于 80 字且像标题的 chunk 增加 length penalty，避免它压过包含事实的正文片段。

## 6. quantity / answerability bonus 原理

数值型问题需要能直接回答“多少、几人、上限、大小”等。

当 query intent 是 `quantity` 时，如果 chunk 包含数字或明确单位，例如：

```text
5 人
20MB
40GB
```

系统会增加 answerability bonus。

这解决的是：

```text
标题片段很像问题，但没有数字；
正文片段分数略低，但真正包含答案。
```

## 7. ranking_reason 如何帮助排查

每个检索结果会返回类似：

```text
intent:quantity
keyword_bonus
section_boost:capability
answerability_bonus:number_or_unit
length_penalty:short_title_like
```

你可以据此判断：

- 这个片段为什么排上来。
- 它是靠向量分，还是靠关键词加分。
- 它是否因为章节类型被加分或降权。
- 它是否因为太短被降权。
- 它是否因为包含数字或单位被奖励。

## 8. 为什么这一步仍不做 rerank

当前问题仍然可以用低成本、可解释规则改善。

rerank 会增加：

- 新模型依赖。
- 调用成本。
- 响应延迟。
- 部署配置复杂度。

在 section metadata、ranking reason 和人工测评基线稳定前，直接引入 rerank 会让系统更难解释。当前阶段继续选择可解释工程补丁更合适。

## 9. 如何重新评估

部署后必须重新上传或重新索引测试文件。

建议使用同一批问题比较：

- “运行人数上限是多少？”
- “单个上传文件大小上限是多少？”
- “支持上传哪些文件类型？”
- “目前完成了哪些核心能力？”
- “当前有哪些限制？”
- “服务器配置是什么？”

重点观察：

- 正确答案片段是否更靠前。
- 配置类和限制类噪声是否减少。
- 短标题是否被 length penalty 降权。
- 数值型问题是否优先命中含数字或单位的片段。
- Citation Score 是否从 0.5-1.5 向 1.5-2 靠近。
