# v0.7 VectorStore 向量存储报告

## 1. 本次完成内容

v0.7 完成了最小 VectorStore 本地向量存储闭环。

当前后端可以把文档处理结果保存为本地 JSON 索引：

```text
file_id + extension
  -> DocumentParserService.parse_text()
  -> ChunkService.create_chunks()
  -> EmbeddingService.embed_chunk_vectors()
  -> VectorStoreService.save_file_vectors()
  -> backend/vector_store/{file_id}.json
```

前端现在可以：

- 在文件中心手动触发“索引”。
- 在聊天侧上传文件后自动完成上传、解析、切块、mock 向量化和本地索引保存。
- 展示 `indexed` 状态、embedding 数量、维度和本地索引路径摘要。

本阶段没有实现 RAG、文件问答、RetrievalService、真实 embedding API、PostgreSQL、pgvector 或复杂数据库。

### `backend/app/services/vector_store_service.py`

新增 `VectorStoreService`。

职责：

- 校验 chunks 和 vectors 数量一致。
- 校验 vector 维度一致。
- 保存本地 JSON 索引。
- 按 `file_id` 读取索引摘要。

不负责：

- 文档解析。
- 文本切块。
- embedding 生成。
- 相似度检索。
- RAG prompt 组装。
- LLM 文件问答。

## 3. 当前调用链路

### 3.1 聊天侧自动链路

```text
ChatInput.handleFileChange()
  -> fileStore.ingestFile(file)
  -> uploadFileApi(file)
  -> POST /api/v1/files
  -> parseFileApi(file_id, extension)
  -> POST /api/v1/files/{file_id}/parse
  -> chunkFileApi(file_id, extension)
  -> POST /api/v1/files/{file_id}/chunks
  -> embedFileApi(file_id, extension)
  -> POST /api/v1/files/{file_id}/embeddings
  -> storeFileVectorsApi(file_id, extension)
  -> POST /api/v1/files/{file_id}/vector-store
  -> files[].status = indexed
```

### 3.2 后端保存索引链路

```text
files.py store_file_vectors()
  -> DocumentParserService.parse_text()
  -> ChunkService.create_chunks()
  -> EmbeddingService.embed_chunk_vectors()
  -> VectorStoreService.save_file_vectors()
  -> backend/vector_store/{file_id}.json
```

### 3.3 读取索引摘要链路

```text
GET /api/v1/files/{file_id}/vector-store
  -> VectorStoreService.get_file_vector_summary()
  -> load backend/vector_store/{file_id}.json
  -> 返回 chunk_count / embedding_count / dimension / storage_path
```

## 4. 工程效果

v0.7 之后，项目的 RAG 前置链路变成：

```text
文件
  -> 解析
  -> 切块
  -> mock 向量化
  -> 本地向量索引保存
```

这意味着系统已经具备了后续 Retrieval 的数据基础。

但当前向量索引只是本地 JSON 文件，不是生产级向量数据库。

## 5. 为什么现在不用 pgvector

当前不引入 PostgreSQL / pgvector，原因是：

- 项目还没有数据库、ORM 和迁移体系。
- 当前 embedding 是 mock vector，不能代表真实语义。
- 当前还没有 RetrievalService，pgvector 的检索能力无法真正发挥价值。
- 过早引入数据库会把 v0.7 从“向量存储边界”扩大成“数据库工程阶段”。

本阶段使用 JSON 的价值是：

- 更容易观察数据结构。
- 更容易理解 VectorStore 职责。
- 后续可以把 `VectorStoreService` 的内部实现替换为 pgvector，而不重写上层 RAG 编排。

## 6. 当前能力边界

当前可以：

- 保存 chunks 和 mock embeddings 到本地 JSON。
- 根据 `file_id` 读取索引摘要。
- 前端展示 indexed 状态。
- 聊天侧上传文件后自动保存索引。

当前不能：

- 根据用户问题检索相关 chunks。
- 基于文件内容回答问题。
- 使用真实 embedding API。
- 使用 pgvector。
- 刷新后自动恢复完整文件列表。
- 多用户隔离索引。

## 8. 剩余问题

当前技术债：

- 本地 JSON 不适合并发和生产环境。
- `POST /vector-store` 当前会重新执行 parse、chunk 和 embed。
- 文件元数据仍没有数据库持久化。
- 文件列表刷新后仍无法从后端恢复。
- mock vectors 不能用于真实语义检索质量评估。
- 还没有 RetrievalService，因此不能做 top_k 检索。

## 9. 下一阶段建议

v0.8 建议进入 Retrieval 检索服务阶段。

目标：

```text
用户问题
  -> mock query embedding
  -> VectorStoreService.load_file_vectors()
  -> RetrievalService 计算相似度
  -> 返回 top_k chunks
```

v0.8 仍可以暂不调用 LLM 生成文件问答，先验证检索结果是否能从本地索引中取出。
