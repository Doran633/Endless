# v1.1.4 File Lifecycle 文件生命周期闭环报告

## 1. 工程效果

v1.1.4 补齐了文件从进入系统到离开系统的最小生命周期。

文件中心上传文件后会自动完成：

```text
上传 -> 解析 -> 切块 -> embedding -> 保存本地 JSON 索引 -> 可问答
```

文件中心仍保留解析、切块、向量化和索引按钮，用于逐步调试以及失败后的人工重试。

用户删除文件时，系统会同步清理：

- SQLite `files` 表记录。
- `backend/uploads/` 中对应的原始文件。
- `backend/vector_store/` 中对应的 JSON 索引。
- 前端文件列表中的对应项目。
- 当前会话中对该文件的 RAG 绑定。

本次没有修改 RetrievalService、RagService、LLMProvider 或 RAG prompt，现有 RAG 主链路保持不变。

## 2. 修改文件职责

### `backend/app/core/errors.py`

新增：

- `FileRecordNotFoundError`：数据库中不存在目标文件时返回 404。
- `FileDeleteError`：文件系统或数据库删除失败时返回稳定的 500 业务错误。

### `backend/app/schemas/file.py`

新增 `DeleteFileResponse`，固定返回：

- `file_id`
- `deleted`
- `original_deleted`
- `vector_index_deleted`

### `backend/app/repositories/file_repository.py`

新增：

- `get_file()`：按 `file_id` 查询 SQLite 文件记录。
- `delete_file()`：删除对应数据库记录并提交事务。

Repository 只处理数据库，不接触上传目录和 VectorStore。

### `backend/app/services/file_service.py`

新增 `delete_file(file_id)`，负责完整删除编排：

- 确认数据库记录存在。
- 根据记录中的 `id` 和 `extension` 构造精确文件路径。
- 只删除对应原始文件和 `{file_id}.json` 索引。
- 最后删除数据库记录。
- 将底层文件系统或 SQLAlchemy 错误转换为稳定业务错误。

### `backend/app/api/v1/files.py`

新增 `DELETE /api/v1/files/{file_id}`。API 层只接收路径参数、调用 FileService 并返回统一响应，不直接操作数据库或磁盘。

### `frontend/src/api/fileApi.ts`

新增 `deleteFile(fileId)` 和删除响应类型，封装前端到后端 DELETE 请求及错误读取。

### `frontend/src/stores/fileStore.ts`

将原来的本地 `removeFile()` 替换为异步 `deleteFile()`：

- 先等待后端真实删除成功。
- 再从前端文件列表移除记录。
- 如果目标是当前 active RAG 文件，同时清理文件侧绑定状态。

### `frontend/src/components/FileCenter.tsx`

调整：

- 文件中心上传改用现有 `ingestFile()` 完整处理链路。
- 上传区说明改为自动处理语义。
- 展示上传、解析、切块、向量化、索引、完成和失败状态。
- 删除前显示确认弹窗。
- 删除成功后更新列表；失败时显示后端返回原因。
- 删除当前会话绑定文件时调用 `clearCurrentSessionRagFile()`。
- 保留已有手动处理按钮。

### `docs/status.md`

同步当前版本、已完成功能、剩余缺口和下一阶段方向。

## 3. 文件中心自动处理调用链路

```text
FileCenter.handleUpload(file)
  -> fileStore.ingestFile(file)
  -> POST /api/v1/files
  -> POST /api/v1/files/{file_id}/parse
  -> POST /api/v1/files/{file_id}/chunks
  -> POST /api/v1/files/{file_id}/embeddings
  -> POST /api/v1/files/{file_id}/vector-store
  -> SQLite 状态更新 + backend/vector_store/{file_id}.json
  -> 前端状态变为 indexed
  -> 文件可用于单文件 RAG 问答
```

该实现直接复用聊天侧已经验证过的 `ingestFile()`，没有新增复合后端 API。

## 4. 文件删除调用链路

```text
FileCenter 删除确认
  -> fileStore.deleteFile(file_id)
  -> fileApi.deleteFile(file_id)
  -> DELETE /api/v1/files/{file_id}
  -> FileService.delete_file(file_id)
  -> FileRepository.get_file(file_id)
  -> 删除 backend/uploads/{file_id}.{extension}
  -> 删除 backend/vector_store/{file_id}.json
  -> FileRepository.delete_file(file_id)
  -> 前端移除文件记录
  -> 必要时解除当前会话 RAG 文件绑定
```

删除逻辑不会删除 `uploads/` 或 `vector_store/` 目录，只会删除由目标数据库记录计算出的两个具体文件。

## 5. 错误处理

- SQLite 中不存在 `file_id`：返回 HTTP 404 和 `File record not found`。
- 原始文件或索引原本不存在：对应返回字段为 `false`，但仍允许清理剩余资源和数据库记录。
- 目标路径不是普通文件：返回稳定 `FileDeleteError`。
- 文件系统删除失败或数据库提交失败：返回 HTTP 500，不在前端移除列表记录。
- 自动处理任一步失败：保留文件记录并显示失败原因，用户可从手动按钮重新开始处理。

当前删除不是跨 SQLite 与文件系统的原子事务。如果删除部分磁盘文件后数据库提交失败，可能留下不一致状态。MVP 暂不引入事务日志或补偿任务，后续部署到多人环境前应增加可重试删除状态和一致性清理机制。

## 6. 是否修改业务逻辑

本次修改了两项明确业务行为：

1. 文件中心上传从“只上传”变为“自动完成全部索引准备”。
2. 文件中心删除从“只移除前端显示”变为“真实清理后端资源”。

没有修改：

- 文档解析算法。
- chunk 策略。
- embedding provider 抽象与切换方式。
- VectorStore JSON 数据结构。
- RetrievalService 和 cosine similarity。
- RagService、LLM 调用和 RAG prompt。

## 7. 测试方法与结果

后端编译检查：

```text
cd backend
python -m compileall app
```

结果：通过。

前端类型检查：

```text
cd frontend
npm exec tsc -- --noEmit
```

结果：通过。

DELETE 使用独立临时 SQLite、上传目录和 VectorStore 目录完成脚本验证：

```text
POST /api/v1/files
创建对应本地 JSON 索引
DELETE /api/v1/files/{file_id}
GET /api/v1/files
再次 DELETE /api/v1/files/{file_id}
```

验证结果：

- 首次删除返回 HTTP 200。
- `deleted = true`。
- `original_deleted = true`。
- `vector_index_deleted = true`。
- 删除后文件列表为空。
- 再次删除同一文件返回 HTTP 404。

测试环境出现一条 FastAPI TestClient 关于未来 `httpx2` 的弃用提示，不影响当前功能结果，后续建立正式测试目录时需要统一测试依赖版本。

## 8. 风险和技术债

- 自动处理复用多个现有 API，因此文档会被重复解析，embedding 也会在向量化和索引阶段重复生成。当前保持接口简单，后续可用一个轻量 ingestion 编排 API 减少重复计算。
- 自动处理只存在前端运行时，页面关闭会中断后续调用，没有后端任务恢复能力。
- 删除过程不是文件系统与数据库之间的原子事务。
- 文件删除是硬删除，没有回收站或恢复能力。
- 当前 VectorStore 摘要要求索引目录位于 `backend/` 内部；将 `VECTOR_STORE_DIR` 配置为 backend 之外的绝对路径会导致相对路径转换失败。
- 当前只清理当前会话的 RAG 绑定；会话尚未持久化，因此不存在后端跨会话引用检查。
- 当前没有专门的自动化测试目录，本次仍以编译、类型检查和独立 API 脚本验证为主。

## 9. 下一阶段建议

下一阶段建议继续 v1.1 持久化主线，补齐聊天会话、聊天消息和当前会话文件绑定的 SQLite 持久化。这样页面刷新后，用户不仅能恢复文件列表，也能恢复真实聊天工作上下文。
