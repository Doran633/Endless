# v0.7 VectorStore 向量存储计划

> 本计划用于 v0.7 开发阶段。目标是在不实现 RAG、不实现文件问答、不调用真实 embedding API、不引入数据库的前提下，完成最小向量存储闭环。

## 1. 当前状态

当前项目已经完成：

- v0.2 真实 LLM 聊天闭环。
- v0.3 文件上传闭环。
- v0.4 TXT / DOCX / 可复制文本型 PDF 文档解析闭环。
- v0.5 文本切块闭环。
- v0.6 mock embedding 向量化闭环。
- v0.6.1 聊天侧文件自动接入体验。

当前文件处理链路是：

```text
用户上传文件
  -> FileService 保存到 backend/uploads/
  -> DocumentParserService 解析文本
  -> ChunkService 生成 chunks
  -> EmbeddingService 生成 mock vectors
  -> 前端展示 embedding 摘要
```

当前缺口是：

- vectors 只在接口响应中返回摘要，没有保存。
- chunks 没有持久化。
- embedding vectors 没有持久化。
- 服务重启或页面刷新后，文件处理结果无法恢复。
- 后续 Retrieval 无法从系统中读取已向量化的文档数据。

v0.7 要补上的不是“问答能力”，而是 RAG 前置链路里的“索引存储能力”。

## 2. 为什么 v0.7 只做 VectorStore，不做 RAG

RAG 至少包含四个环节：

```text
文档解析
  -> 文本切块
  -> 向量化
  -> 向量存储
  -> 问题向量化
  -> 相似度检索
  -> 构造上下文
  -> 调用 LLM 回答
```

当前项目已经完成到：

```text
文档解析
  -> 文本切块
  -> mock 向量化
```

如果 v0.7 直接做 RAG，会同时引入：

- 向量保存。
- 相似度检索。
- query embedding。
- top_k 策略。
- RAG prompt 组装。
- LLM 回答引用文件内容。
- 错误归因和上下文长度控制。

这会让问题范围突然扩大。为了保持 MVP 简单，也为了让工程链路更容易学习和调试，v0.7 只做：

```text
chunks + vectors
  -> VectorStore
  -> 保存
  -> 读取
```

不做：

```text
query -> retrieval -> RAG answer
```

这样做的价值是：先把“索引数据怎么存、怎么按 file_id 找回来、结构是否稳定”解决清楚，再进入检索和问答。

## 3. VectorStore 的作用

VectorStore 是 RAG 系统里的向量索引存储边界。

它负责：

- 保存 chunk 文本。
- 保存 chunk 对应的 embedding vector。
- 保存 file_id、chunk_id、chunk_index 等元数据。
- 支持按 file_id 查询已经存储的向量记录。
- 后续支持相似度检索。

它不负责：

- 文件上传。
- 文档解析。
- 文本切块。
- embedding 生成。
- RAG prompt 组装。
- LLM 回答。

v0.7 的 VectorStore 暂时只需要支持：

```text
save(file_id, chunks, vectors)
list_by_file(file_id)
get_summary(file_id)
```

后续 v0.8 再扩展：

```text
search(query_vector, top_k, file_id?)
```

## 4. 存储方案选择

### 4.1 推荐方案：本地 JSON 文件存储

v0.7 推荐使用本地 JSON 文件存储，目录建议：

```text
backend/vector_store/
```

每个文件生成一个索引文件：

```text
backend/vector_store/{file_id}.json
```

优点：

- 不需要引入数据库。
- 不需要安装 PostgreSQL / pgvector。
- 便于直接打开文件观察数据结构。
- 适合学习 VectorStore 的最小职责。
- 与当前本地 `backend/uploads/` 文件存储方式一致。

缺点：

- 不适合大规模数据。
- 不适合并发写入。
- 不支持高效相似度检索。
- 缺少事务能力。

这些缺点在 v0.7 阶段可以接受，因为本阶段目标是建立工程边界，不是构建生产级向量数据库。

### 4.2 为什么现在不用 pgvector

现在不建议使用 PostgreSQL + pgvector，原因是：

- 当前项目还没有数据库基础设施。
- 还没有 SQLAlchemy、Alembic、连接池和迁移体系。
- 当前 embedding 仍是 mock vector，不代表真实语义。
- 当前还没有 RetrievalService，无法体现 pgvector 检索价值。
- 过早引入 pgvector 会让 v0.7 同时承担数据库设计、迁移、部署和向量存储四类复杂度。

更合理的节奏是：

```text
v0.7 本地 JSON VectorStore
  -> v0.8 RetrievalService
  -> v0.9 RAG 问答
  -> v1.x 再迁移 PostgreSQL + pgvector
```

这样既保留未来扩展方向，也不会打破当前 MVP 简单原则。

## 5. 数据结构设计

建议每个 `{file_id}.json` 保存一个完整文件索引。

示例结构：

```json
{
  "file_id": "uuid",
  "status": "stored",
  "embedding_model": "mock-embedding",
  "embedding_dimension": 16,
  "chunk_count": 3,
  "created_at": "2026-07-24T12:00:00Z",
  "items": [
    {
      "chunk_id": "uuid-0",
      "file_id": "uuid",
      "chunk_index": 0,
      "content": "chunk text",
      "char_count": 120,
      "embedding": [0.12, -0.04, 0.31]
    }
  ]
}
```

字段说明：

- `file_id`：文件唯一标识。
- `status`：当前索引状态，v0.7 固定为 `stored`。
- `embedding_model`：当前 embedding 模型名称。
- `embedding_dimension`：向量维度。
- `chunk_count`：chunk 数量。
- `created_at`：索引创建时间。
- `items`：chunk 与 vector 的一一对应记录。

每条 item 包含：

- `chunk_id`
- `file_id`
- `chunk_index`
- `content`
- `char_count`
- `embedding`

v0.7 可以返回摘要，不需要把完整 vectors 全量返回给前端。

## 6. VectorStoreService 设计

建议新增：

```text
backend/app/services/vector_store_service.py
```

职责：

- 接收 `file_id`、chunks 和 vectors。
- 校验 chunks 与 vectors 数量一致。
- 校验 vector 维度一致。
- 将索引写入本地 JSON 文件。
- 按 file_id 读取索引摘要。
- 按 file_id 判断索引是否存在。

建议方法：

```text
save_file_vectors(file_id, chunks, vectors, embedding_model, embedding_dimension)
get_file_vector_summary(file_id)
load_file_vectors(file_id)
exists(file_id)
```

不做职责：

- 不生成 embedding。
- 不解析文档。
- 不切块。
- 不做相似度检索。
- 不调用 LLM。

### 错误处理

建议新增应用级错误：

```text
VectorStoreError
VectorStoreNotFoundError
```

典型错误：

- vectors 数量与 chunks 数量不一致。
- vector 维度不一致。
- JSON 写入失败。
- JSON 读取失败。
- 指定 file_id 的索引不存在。

## 7. API 设计

v0.7 建议最小新增两个 API。

### 7.1 保存文件向量索引

接口：

```text
POST /api/v1/files/{file_id}/vector-store
```

请求体：

```json
{
  "extension": "txt"
}
```

后端流程：

```text
file_id + extension
  -> DocumentParserService.parse_text()
  -> ChunkService.create_chunks()
  -> EmbeddingService.embed_chunks()
  -> VectorStoreService.save_file_vectors()
  -> 返回存储摘要
```

成功响应：

```json
{
  "code": 0,
  "message": "ok",
  "data": {
    "file_id": "uuid",
    "status": "stored",
    "chunk_count": 8,
    "embedding_count": 8,
    "embedding_dimension": 16,
    "storage_path": "vector_store/uuid.json",
    "created_at": "2026-07-24T12:00:00Z"
  }
}
```

说明：

- v0.7 仍然可以重复执行 `parse -> chunk -> embed -> store`。
- 这会带来重复计算，但当前没有数据库，属于可接受的 MVP 技术债。
- 后续有持久化后，应改为读取已保存 chunks 和 embeddings。

### 7.2 查询文件向量索引摘要

接口：

```text
GET /api/v1/files/{file_id}/vector-store
```

成功响应：

```json
{
  "code": 0,
  "message": "ok",
  "data": {
    "file_id": "uuid",
    "status": "stored",
    "chunk_count": 8,
    "embedding_dimension": 16,
    "created_at": "2026-07-24T12:00:00Z"
  }
}
```

不建议 v0.7 返回完整 vectors。

原因：

- vectors 数据量大。
- 前端不需要展示完整向量。
- 后续完整 vectors 应由 RetrievalService 在后端内部读取。

## 8. 与现有 EmbeddingService 的关系

当前 `EmbeddingService` 负责：

```text
chunks -> vectors
```

v0.7 新增 `VectorStoreService` 后，职责应变成：

```text
EmbeddingService
  -> 只负责生成 vectors

VectorStoreService
  -> 只负责保存和读取 vectors
```

二者关系：

```text
DocumentParserService
  -> ChunkService
  -> EmbeddingService
  -> VectorStoreService
```

重要边界：

- 不要让 `EmbeddingService` 直接写文件。
- 不要让 `VectorStoreService` 自己调用 embedding provider。
- API 层可以暂时编排四个 service，但后续可迁移到 `FileIngestionService` 或 `IndexingService`。

当前 MVP 可以接受 API 层编排：

```text
files.py endpoint
  -> parser
  -> chunker
  -> embedder
  -> vector store
```

等流程变复杂后再抽出编排服务。

## 9. 前端展示方案

v0.7 前端只做轻量展示，不进入文件问答。

建议：

- `FileItem.status` 增加 `indexed`。
- 文件中心显示“已入库”或“已索引”状态。
- 聊天侧自动处理完成文案从“文件已准备”升级为“文件已索引，后续 RAG 阶段可用于检索问答”。
- 文件中心增加“索引”按钮或在聊天侧自动处理后自动调用 vector-store API。

推荐 v0.7 用户路径：

```text
聊天侧上传文件
  -> 自动上传
  -> 自动解析
  -> 自动切块
  -> 自动向量化
  -> 自动保存到 VectorStore
  -> 显示“文件已索引”
```

文件中心展示字段：

- `chunk_count`
- `embedding_count`
- `embedding_dimension`
- `indexed_at`
- `vector_store_path` 或简化为“本地索引已保存”

注意：

- 不展示完整 vectors。
- 不出现“现在可以问文件”的文案。
- 可以提示“RAG 问答将在后续阶段开放”。

## 10. 风险和技术债

### 10.1 本地 JSON 不适合生产

本地 JSON 缺少事务、并发控制和高效检索能力。它只适合 MVP 学习和单机开发。

后续迁移 pgvector 时，需要重新实现 VectorStore 接口。

### 10.2 重复计算

保存索引时如果重新执行：

```text
parse -> chunk -> embed
```

会重复消耗计算。当前是 mock embedding，成本可接受。未来真实 embedding API 接入后，必须避免重复调用。

### 10.3 文件状态仍不完整持久化

即使 vectors 保存到 JSON，当前文件列表仍主要存在前端状态中。刷新页面后，前端可能不知道哪些文件已经索引。

v0.7 可以接受这个限制，但后续需要：

- 文件列表 API。
- 文件元数据存储。
- 索引状态读取。

### 10.4 JSON 文件可能损坏

开发过程中手动编辑或写入中断可能导致 JSON 文件损坏。

MVP 处理方式：

- 读取失败时返回清晰错误。
- 写入时先构造完整对象，再一次性写入。

### 10.5 mock embedding 不能用于真实检索效果评估

mock vectors 只能验证工程链路，不能代表语义相似度。

因此 v0.8 如果继续用 mock embedding，只能验证检索流程，不能评估问答质量。

## 11. 测试方案

### 11.1 后端编译检查

运行：

```text
python -m compileall app
```

预期：

- Python 编译通过。

### 11.2 前端类型检查

运行：

```text
npm exec tsc -- --noEmit
```

预期：

- TypeScript 类型检查通过。

### 11.3 API 手动验证

流程：

```text
1. POST /api/v1/files 上传 TXT
2. POST /api/v1/files/{file_id}/vector-store
3. 确认 backend/vector_store/{file_id}.json 已生成
4. GET /api/v1/files/{file_id}/vector-store
5. 确认返回 status=stored
6. 确认 chunk_count 与 embedding_count 一致
7. 确认 embedding_dimension=16
```

### 11.4 文件内容检查

打开生成的 JSON 文件，确认：

- `file_id` 正确。
- `items` 数量正确。
- 每个 item 都有 `chunk_id`、`content` 和 `embedding`。
- 每个 embedding 的维度一致。

### 11.5 前端验证

浏览器验证：

1. 在聊天输入区上传 TXT 文件。
2. 确认自动完成上传、解析、切块、向量化和索引保存。
3. 打开文件中心。
4. 确认文件状态显示为“已索引”。
5. 确认页面没有开放文件问答入口。
6. 发送普通聊天消息，确认仍只走普通 LLM 聊天。

## 12. 后续如何接入 Retrieval 和 RAG

v0.7 完成后，链路会变成：

```text
File
  -> parse
  -> chunks
  -> embeddings
  -> VectorStore
```

v0.8 Retrieval 可以在此基础上增加：

```text
用户问题
  -> query embedding
  -> VectorStore.search(query_vector, top_k, file_id?)
  -> 返回相关 chunks
```

v0.9 RAG 可以继续增加：

```text
相关 chunks
  -> RagService 构造上下文
  -> LLMService 调用模型
  -> 返回基于文件内容的回答
```

建议后续服务边界：

```text
VectorStoreService
  -> 保存和读取索引

RetrievalService
  -> 计算相似度并返回 top_k chunks

RagService
  -> 编排检索结果和 LLM 回答
```

这样每一层职责清晰，后续从本地 JSON 迁移到 pgvector 时，只需要替换 VectorStore 实现，不需要重写 RAG 主链路。
