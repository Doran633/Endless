# v1.5 Deployment Readiness 部署准备规划

## 1. 当前项目部署状态评估

当前项目已经具备本地 MVP 的核心能力：

- React + Vite 前端。
- FastAPI 后端。
- SQLite + SQLAlchemy 持久化。
- `backend/uploads/` 本地文件存储。
- `backend/vector_store/` 本地 JSON 向量索引。
- OpenAI-compatible LLM Provider。
- OpenAI-compatible Embedding Provider。
- 单文件 RAG 问答。
- 普通聊天和 RAG 文件问答短上下文。
- 会话和消息持久化。
- Windows 本地启动、停止和检查脚本。
- GitHub Safety Check。
- README、本地试运行指南和常见问题文档。

当前项目适合：

- 本地试运行。
- 可信任用户小范围体验。
- 低成本个人项目 MVP 继续演进。

当前项目还不适合直接公开给所有人使用。

主要原因：

- 没有登录或访问口令。
- 所有访问者都会消耗同一组服务端 API Key。
- SQLite、uploads、vector_store 仍是单机本地存储。
- 文件和聊天记录没有用户隔离。
- 缺少生产环境日志、反向代理、HTTPS 和进程守护方案。

## 2. 为什么现在不能直接粗暴上线

如果现在直接把前端和后端暴露到公网，会出现几个问题。

### 2.1 API Key 成本风险

后端 `.env` 中保存 LLM 和 Embedding API Key。

如果网站公开访问，任何人都可以：

- 发送聊天请求。
- 上传文件。
- 触发 embedding。
- 消耗你的 API 额度。

所以部署前至少需要最小访问保护。

### 2.2 文件隐私风险

当前上传文件保存在：

```text
backend/uploads/
```

向量索引保存在：

```text
backend/vector_store/
```

其中 vector_store JSON 里包含文档 chunk 原文，不只是向量。

如果没有访问保护和数据清理策略，上传内容会长期留在服务器上。

### 2.3 SQLite 单机风险

SQLite 适合本地 MVP，但线上使用有边界：

- 不适合高并发写入。
- 不适合多实例部署。
- 备份需要额外设计。
- 如果部署平台磁盘不持久，数据可能丢失。

### 2.4 免费平台持久化风险

很多免费 PaaS 平台存在：

- 服务休眠。
- 文件系统不持久。
- 上传文件重启后丢失。
- SQLite 数据库无法稳定保存。
- 后端冷启动慢。

这和当前项目依赖本地 uploads、vector_store、SQLite 的形态不完全匹配。

### 2.5 前后端地址和 CORS 风险

本地运行时，前端通过 Vite proxy 调后端。

正式部署时，需要明确：

- 前端生产 API 地址。
- 后端 CORS 允许域名。
- HTTPS。
- 反向代理路径。

不能继续依赖本地开发代理。

## 3. 部署方案选项

### 3.1 方案 A：免费前端平台 + 免费后端平台

示例：

- 前端：Vercel / Netlify / Cloudflare Pages。
- 后端：Render / Railway / Fly.io 免费层。

优点：

- 成本低。
- 上手快。
- 适合静态前端。

缺点：

- 免费后端可能休眠。
- 文件系统可能不持久。
- SQLite 和 uploads 风险较大。
- 平台限制多，调试成本不一定低。

适合：

- 纯前端项目。
- 无上传文件或无本地持久化的后端 Demo。

不太适合当前阶段的北辰agent。

### 3.2 方案 B：前端平台 + 小型云服务器后端

示例：

- 前端：Vercel / Cloudflare Pages。
- 后端：小型 VPS。
- 数据、uploads、vector_store 都在 VPS。

优点：

- 前端部署简单。
- 后端文件和 SQLite 可控。
- 可以配置域名、HTTPS、备份和进程守护。

缺点：

- 前后端跨域配置稍复杂。
- 需要维护 VPS。
- 仍需保护 API Key。

适合：

- 个人项目 MVP。
- 需要文件上传和后端持久化。

### 3.3 方案 C：前端静态构建 + 后端同一台小型服务器

示例：

```text
Nginx
-> /        前端静态文件
-> /api     FastAPI 后端
```

优点：

- 一个服务器即可。
- 一个域名即可。
- 前端和后端同源，CORS 简单。
- uploads、vector_store、SQLite 都在同一台机器上，最贴合当前架构。
- 成本可控。

缺点：

- 需要配置 Nginx。
- 需要配置 HTTPS。
- 需要使用 systemd / supervisor 守护后端。
- 需要自己做服务器基础维护。

适合当前项目。

### 3.4 方案 D：Docker Compose 单机部署

优点：

- 环境一致性更好。
- 后续迁移方便。

缺点：

- 当前用户明确不希望引入 Docker。
- 对当前 MVP 来说增加复杂度。

暂不推荐。

## 4. 推荐方案

推荐采用：

```text
小型云服务器 + 域名 + Nginx + FastAPI + 前端静态构建 + SQLite + 本地 uploads/vector_store
```

理由：

- 你可以接受购买小型服务器和域名。
- 当前项目依赖本地文件、SQLite、本地 JSON VectorStore。
- 单机部署最贴合当前工程形态。
- 不需要复杂微服务。
- 不需要 Kubernetes。
- 不需要马上迁移 PostgreSQL / pgvector。
- 成本可控，适合个人 MVP。

推荐部署形态：

```text
用户浏览器
-> https://你的域名
-> Nginx
   -> /      frontend/dist
   -> /api   FastAPI 127.0.0.1:8000
```

后端运行：

```text
systemd
-> uvicorn app.main:app --host 127.0.0.1 --port 8000
```

数据目录：

```text
backend/data/
backend/uploads/
backend/vector_store/
```

必须配置备份。

## 5. 前端部署设计

当前前端是 Vite React。

生产部署流程应为：

```powershell
cd frontend
npm install
npm run build
```

生成：

```text
frontend/dist/
```

在服务器上由 Nginx 提供静态文件。

如果采用同域名部署，前端 API 请求可以继续使用相对路径：

```text
/api/v1/...
```

这样最简单。

不推荐在 v1.5 立刻做：

- 多环境前端配置系统。
- 复杂构建流水线。
- 多域名前后端分离。

如果未来前后端分离部署，再引入：

```text
VITE_API_BASE_URL=https://api.example.com
```

## 6. 后端部署设计

当前后端是 FastAPI。

生产运行建议：

- 使用虚拟环境。
- 安装 `requirements.txt`。
- 使用 systemd 守护进程。
- 后端只监听 `127.0.0.1:8000`。
- 由 Nginx 暴露 HTTPS。

后端启动命令示例：

```bash
python -m uvicorn app.main:app --host 127.0.0.1 --port 8000
```

v1.5 暂不引入：

- Gunicorn 多 worker。
- Celery。
- Redis。
- Kubernetes。
- Docker。

后续如果访问量上升，再评估：

- Gunicorn + Uvicorn worker。
- PostgreSQL。
- 对象存储。
- pgvector。

## 7. 数据库方案

当前使用 SQLite：

```text
backend/data/beichen.db
```

### 7.1 v1.5 推荐

短期继续使用 SQLite。

原因：

- MVP 小规模试用足够。
- 不引入 PostgreSQL 可以降低部署复杂度。
- 当前 Repository / Service 分层已经为后续迁移留出边界。

### 7.2 SQLite 线上风险

风险：

- 并发写入能力有限。
- 不能多实例部署。
- 数据库文件需要备份。
- 文件损坏时恢复成本较高。

### 7.3 备份策略

最低要求：

- 定期备份 `backend/data/beichen.db`。
- 部署前不要覆盖服务器上的数据库。
- 更新代码时不要删除 `backend/data/`。

### 7.4 后续迁移

如果出现以下情况，应迁移 PostgreSQL：

- 多人同时使用。
- 数据越来越重要。
- 需要用户登录。
- 需要正式备份和恢复。
- 需要更可靠的事务能力。

## 8. 文件存储方案

当前上传文件保存在：

```text
backend/uploads/
```

### 8.1 v1.5 推荐

短期继续使用服务器本地磁盘。

原因：

- 单机部署最简单。
- 当前文件删除 API 已能同步删除原始文件。
- 小规模试用成本最低。

### 8.2 风险

- 磁盘空间可能增长。
- 上传文件可能包含隐私。
- 服务器迁移时需要迁移文件。
- 没有对象存储的高可用能力。

### 8.3 最低要求

部署前应补充：

- 上传文件大小限制已存在，但需要在 README / 部署文档中说明。
- 文件目录权限。
- 定期清理策略。
- 备份策略。

后续可以迁移：

- S3。
- 阿里云 OSS。
- 腾讯云 COS。
- Cloudflare R2。

## 9. `vector_store` 方案

当前向量索引保存在：

```text
backend/vector_store/
```

JSON 文件中包含：

- chunk 内容。
- embedding。
- embedding model。
- 文件 ID。

### 9.1 v1.5 推荐

短期继续使用本地 JSON VectorStore。

原因：

- 单文件 RAG 足够。
- 已经实现删除闭环。
- 不引入 pgvector 可以降低部署复杂度。

### 9.2 风险

- JSON 查询效率有限。
- 不适合大量文件。
- 不适合多用户隔离。
- 包含文档原文 chunk，属于敏感数据。

### 9.3 后续迁移

以下情况应迁移 pgvector 或向量数据库：

- 多文件 RAG。
- 文件量增大。
- 多用户。
- 权限隔离。
- 更复杂检索策略。

## 10. 环境变量和 API Key 安全

线上必须通过服务器环境变量或服务器 `.env` 管理：

- `LLM_PROVIDER`
- `LLM_MODEL`
- `OPENAI_API_KEY`
- `OPENAI_BASE_URL`
- `EMBEDDING_PROVIDER`
- `EMBEDDING_MODEL`
- `EMBEDDING_DIMENSION`
- `EMBEDDING_API_KEY`
- `EMBEDDING_BASE_URL`
- `DATABASE_PATH`
- `UPLOAD_DIR`
- `VECTOR_STORE_DIR`

原则：

- 不把真实 `.env` 提交 GitHub。
- 不把真实 `.env` 打包进发布包。
- 不在前端保存 API Key。
- 不在浏览器暴露 API Key。
- 服务端统一调用外部模型。

建议：

- 服务商控制台设置 API Key 用量限制。
- 如果 Key 怀疑泄露，立即轮换。
- 部署前先用低额度 Key。

## 11. 最小访问保护方案

部署前建议至少实现一种访问保护。

### 11.1 为什么需要

没有访问保护时：

- 任何人都能上传文件。
- 任何人都能消耗你的 LLM 和 Embedding API。
- 任何人都能写入 SQLite。
- 服务器磁盘可能被占满。

### 11.2 v1.5 推荐

推荐先做“单口令访问保护”。

形式：

- 后端 `.env` 设置 `APP_ACCESS_PASSWORD`。
- 前端首次访问要求输入访问口令。
- 口令保存在浏览器本地。
- API 请求携带一个简单 header。
- 后端校验 header。

优点：

- 实现简单。
- 适合个人 MVP。
- 不引入用户系统。
- 不需要多租户。

限制：

- 不是正式用户系统。
- 不能区分不同用户。
- 不能做权限审计。

但足够保护你的 API Key 不被公网随便消耗。

### 11.3 暂不推荐

暂不做：

- 完整注册登录。
- JWT refresh token。
- OAuth。
- 多用户权限。
- 企业登录。

这些后续再做。

## 12. 部署前必须完成事项

上线前最低必须完成：

1. 最小访问保护。
2. 生产环境 CORS / 同源反向代理方案。
3. Nginx 路由设计：
   - `/`
   - `/api`
4. 后端进程守护：
   - systemd 或等价方案。
5. HTTPS：
   - 域名证书。
6. 服务器 `.env` 配置。
7. 确认 API Key 不在 GitHub。
8. 确认 `backend/uploads/`、`backend/vector_store/`、`backend/data/` 不被部署脚本覆盖。
9. 文件和数据库备份策略。
10. README 增加部署说明。

## 13. 部署后可以再做事项

可以部署后再逐步做：

- PostgreSQL 迁移。
- pgvector。
- 对象存储。
- 多文件 RAG。
- 会话摘要。
- 历史消息语义检索。
- Agent Workflow。
- 用户系统。
- 管理后台。
- 自动化 CI/CD。
- 更完善日志和监控。

## 14. 风险和技术债

### 14.1 SQLite 技术债

短期可用，长期需要迁移。

### 14.2 本地文件存储技术债

服务器磁盘容量和备份需要自己负责。

### 14.3 JSON VectorStore 技术债

适合单文件和小规模，不适合多文件知识库。

### 14.4 无用户系统

最小访问口令只能防止公开滥用，不等于正式权限。

### 14.5 无任务队列

上传大文件、embedding 较慢时，请求可能等待较久。

当前 MVP 可以接受，后续再考虑后台任务。

### 14.6 日志不足

线上排查需要更清晰日志。

后续应增加：

- request id。
- 错误日志。
- LLM 调用耗时。
- embedding 调用耗时。

## 15. 验收标准

v1.5 Deployment Readiness 规划完成标准：

- 明确推荐部署方案。
- 明确为什么不直接粗暴上线。
- 明确 SQLite、uploads、vector_store 的线上风险。
- 明确 API Key 安全方案。
- 明确部署前必须补齐最小访问保护。
- 明确低成本服务器 + 域名路线。
- 明确第一阶段实现 prompt。

后续实现阶段验收标准：

- 本地仍可运行。
- GitHub 不包含敏感文件。
- 前端可生产构建。
- 后端可通过生产命令启动。
- 最小访问保护可防止未授权访问。
- 部署文档清晰。

## 16. 第一阶段实现 Prompt

```text
当前项目已完成 v1.5 Deployment Readiness 规划。

现在进入 v1.5.1 Minimal Access Protection 最小访问保护阶段。

目标：
1. 增加最小访问口令保护，避免公网部署后任何人都能消耗 API Key
2. 使用 backend/.env 配置访问口令
3. 不实现完整用户系统
4. 不实现注册登录
5. 不实现多用户
6. 不实现 JWT refresh token
7. 不引入数据库表
8. 不改变 RAG 主链路
9. 不改变会话和消息持久化结构

建议设计：
1. backend/.env.example 新增：
   - APP_ACCESS_PASSWORD=
   - APP_ACCESS_HEADER=X-Beichen-Access
2. 后端新增简单访问校验：
   - 如果 APP_ACCESS_PASSWORD 为空，则本地开发不启用访问保护
   - 如果 APP_ACCESS_PASSWORD 非空，则 /api/v1/* 请求必须携带正确 header
   - /health 可以不校验
3. 前端新增轻量访问口令输入：
   - 首次访问输入口令
   - 保存到 localStorage
   - API client 请求自动带 header
   - 支持清除口令重新输入
4. README 和 docs 更新访问保护说明

要求：
- 不新增 AI 业务功能
- 不修改 RAG 主链路
- 不修改数据库结构
- 不引入复杂认证系统
- 不引入企业权限
- 不引入多租户
- 不提交真实访问口令
- 保持 MVP 简单

完成后：
1. 说明工程效果
2. 说明修改文件职责
3. 说明访问保护调用链
4. 说明为什么这不是正式登录系统
5. 说明部署时如何配置 APP_ACCESS_PASSWORD
6. 运行 scripts/check-local.ps1
7. 运行 python -m compileall app
8. 运行 npm exec tsc -- --noEmit
9. 更新 docs/status.md
10. 生成 docs/v1.5_minimal_access_report.md
```

## 17. 如果暂时不部署，下一步应该优化什么

如果暂时不买服务器或不部署，建议优先优化：

1. 最小访问保护。
2. RAG query rewrite。
3. RAG 空结果提示。
4. 文件处理错误提示。
5. README 部署章节。
6. 自动化测试目录。

其中最小访问保护仍然建议先做。

因为它既服务于未来部署，也能让本地临时分享更安全。
