# v1.7.4 Frontend Error UX and Request ID 规划

## 1. 当前状态

当前项目已完成 v1.7.3 Backend Baseline Tests。

后端已经具备：

- request_id 日志。
- 响应 header 返回 `X-Request-Id`。
- AppError 响应 body 返回 `request_id`。
- `/health` 和 `/health/config`。
- 后端基础 pytest 测试。

前端已经具备：

- 聊天页。
- 文件中心。
- 文件自动处理。
- RAG 问答。
- 会话恢复。
- 邀请码入口。
- 匿名 client_id 隔离。

当前不足：

- 用户看到错误时，很多情况下只能看到比较泛的提示。
- `Failed to fetch`、`Unexpected token`、`文件处理失败` 这类提示不够可定位。
- 前端没有统一展示 request_id。
- 用户无法判断问题发生在上传、解析、切块、向量化、索引、检索还是 LLM 调用。
- 开发者排查线上问题时，需要手动在浏览器 Network 和服务器日志之间对照。

## 2. 为什么 v1.7.4 做错误体验

当前项目已经进入公网小范围试用阶段。

真实试用中，用户最常遇到的问题不是“功能不存在”，而是：

- 网络失败。
- 邀请码错误。
- 文件格式不支持。
- 文档解析失败。
- embedding 配置错误。
- RAG 索引不存在。
- LLM API 超时或失败。
- 后端返回 500。

如果前端提示不清楚，用户会觉得“整个系统坏了”。

v1.7.4 的目标是让错误更可理解、更可定位。

这不是新增 AI 功能，而是产品稳定性和可维护性建设。

## 3. 目标状态

v1.7.4 完成后，前端应具备：

1. 统一 API 错误解析。
2. 能从响应 body 或 header 中提取 request_id。
3. 用户提示中能看到简短错误原因。
4. 开发者能拿 request_id 去服务器日志查问题。
5. 文件自动处理失败时能说明失败阶段。
6. RAG 问答失败时能区分检索失败、模型失败或权限/文件状态问题。
7. 邀请码错误和访问保护错误提示更明确。

## 4. 修改范围

优先修改前端：

- `frontend/src/api/`
- `frontend/src/stores/`
- `frontend/src/components/`
- `frontend/src/types/index.ts`

必要时小幅修改后端错误响应文档，但不修改后端主链路。

不修改：

- RAG 主链路。
- Embedding 主链路。
- VectorStore 主链路。
- Retrieval 主链路。
- 数据库结构。
- 后端 Provider。
- Nginx / systemd。

## 5. API 错误解析设计

建议新增或整理统一错误类型：

```ts
type ApiErrorInfo = {
  message: string
  code?: number
  status?: number
  requestId?: string
  raw?: unknown
}
```

统一解析来源：

1. HTTP status。
2. 响应 JSON body：
   - `code`
   - `message`
   - `request_id`
3. 响应 header：
   - `X-Request-Id`
4. fetch 网络异常。
5. JSON parse 异常。

设计原则：

- 不把完整响应直接暴露给用户。
- 不显示 API Key、prompt、chunks 或服务器路径。
- 用户看简短错误。
- 开发者能看到 request_id。

## 6. 文件处理错误展示方案

文件自动处理流程：

```text
upload -> parse -> chunks -> embeddings -> vector-store
```

每一步失败时建议提示：

### 上传失败

用户文案：

```text
文件上传失败，请检查文件大小、格式或网络连接。
```

### 解析失败

用户文案：

```text
文档解析失败。请确认文件不是扫描件、未损坏，并且格式为 TXT / DOCX / 可复制文本型 PDF。
```

### 切块失败

用户文案：

```text
文本切块失败，可能是解析出的文本为空或格式异常。
```

### 向量化失败

用户文案：

```text
向量化失败，请检查 embedding 配置或稍后重试。
```

### 索引保存失败

用户文案：

```text
索引保存失败，请检查服务器存储状态或稍后重试。
```

每类错误附加：

```text
request_id: xxx
```

如果没有 request_id，则只显示普通错误。

## 7. RAG 问答错误展示方案

RAG 错误建议分层：

### 没有当前 indexed 文件

```text
当前对话还没有可问答的文件，请先上传并等待处理完成。
```

### 文件不属于当前 client_id

```text
无法访问该文件，请确认这是当前浏览器上传的文件。
```

### 检索失败

```text
文档检索失败，可能是索引不存在或文件尚未处理完成。
```

### LLM 调用失败

```text
AI 回答生成失败，可能是模型服务暂时不可用或配置异常。
```

### 网络失败

```text
无法连接服务器，请检查网络或稍后重试。
```

## 8. 访问保护错误展示方案

当前邀请码错误可能表现为 401。

建议前端：

- 401 时提示邀请码无效或已失效。
- 清除本地错误邀请码的选项。
- 不展示后端内部细节。

用户文案：

```text
邀请码无效，请重新输入。
```

## 9. request_id 展示方案

建议展示位置：

- Ant Design message / notification 里简短显示。
- 文件失败状态里显示小号 request_id。
- RAG 错误消息里显示 request_id。

展示格式：

```text
错误追踪 ID：xxxxxxxx
```

作用：

- 用户可以把 ID 发给开发者。
- 开发者在服务器日志中搜索这个 request_id。

服务器排查：

```bash
journalctl -u beichen-agent -n 200 --no-pager | grep <request_id>
tail -f /opt/beichen-agent/logs/app.log | grep <request_id>
```

## 10. 前端状态设计

建议在文件状态或 store 中保留：

```ts
type OperationError = {
  stage: "upload" | "parse" | "chunk" | "embedding" | "index" | "retrieval" | "rag" | "chat"
  message: string
  requestId?: string
}
```

用途：

- 文件中心展示失败阶段。
- 聊天侧展示简短失败提示。
- 调试时能定位到具体 API。

## 11. 不做范围

v1.7.4 不做：

- 不新增 AI 功能。
- 不修改 RAG 主链路。
- 不修改数据库结构。
- 不新增后端错误码体系大重构。
- 不引入 Sentry。
- 不引入 OpenTelemetry。
- 不做浏览器自动化测试。
- 不做大型 UI 改版。
- 不做多语言错误文案系统。

## 12. 测试方案

完成后需要运行：

```powershell
cd backend
python -m compileall app
python -m pytest

cd ../frontend
npm exec tsc -- --noEmit
```

手动验证：

1. 输入错误邀请码，提示明确。
2. 关闭后端后发起请求，显示网络错误。
3. 上传不支持格式文件，显示格式错误。
4. 让 RAG 在没有 indexed 文件时提问，显示文件状态提示。
5. 如果后端返回 request_id，前端能展示。

## 13. 风险和技术债

### 13.1 风险

- 如果前端 API client 分散，统一错误解析可能需要小幅整理多个调用点。
- 如果后端某些异常不是 AppError，可能 request_id 只在 header 中出现，不在 body 中出现。
- 部分浏览器网络错误不会提供 HTTP response，因此不会有 request_id。

### 13.2 可接受技术债

- 本阶段不做完整前端错误边界系统。
- 不做 Sentry。
- 不做集中式前端日志。
- 不做前端自动化测试。
