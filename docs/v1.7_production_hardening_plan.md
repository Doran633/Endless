# v1.7.0 Production Hardening 规划

## 1. 当前项目状态

当前项目已完成 v1.6.3 Anonymous Client Isolation，并已经通过公网 IP 完成部署验证。

当前项目定位是：

**面向 1-5 人可信试用的独立网页版 AI 助手 MVP。**

已经完成的核心能力包括：

- 普通 AI 聊天。
- 当前会话最近 6 条消息作为普通聊天上下文。
- 文件上传。
- TXT / DOCX / 可复制文本型 PDF 解析。
- 文本切块。
- OpenAI-compatible Embedding Provider。
- 本地 JSON VectorStore。
- 单文件 Retrieval。
- 单文件 RAG 问答。
- RAG 连续追问。
- SQLite 文件、会话和消息持久化。
- 文件生命周期管理。
- 邀请码访问保护。
- 匿名 `client_id` 隔离文件、会话和消息。
- Nginx + systemd + Ubuntu VPS 部署验证。
- `/health` 和 `/health/config` 健康检查。
- request_id 日志。
- 本地 smoke test 脚本。

当前项目已经不是纯本地 Demo，而是进入了公网小范围试用阶段。

## 2. 当前线上试用风险

### 2.1 数据风险

当前运行时数据分散在：

- SQLite 数据库。
- uploads 原始上传文件。
- vector_store 本地 JSON 索引。
- logs 日志文件。

如果服务器误操作、磁盘故障、部署覆盖目录或手动删除文件，可能导致：

- 聊天历史丢失。
- 文件列表丢失。
- RAG 索引丢失。
- 文件问答无法继续使用。

当前缺少固定备份脚本和恢复流程。

### 2.2 部署风险

当前部署已经跑通，但仍依赖手动操作：

- `git pull`
- 后端依赖检查。
- 前端 build。
- Nginx reload。
- systemd restart。
- smoke test 验证。

如果步骤遗漏，可能出现：

- 前端是新版本，后端还是旧版本。
- 后端服务已重启但读取旧配置。
- Nginx 配置未生效。
- 上传目录或 vector_store 路径错误。

### 2.3 安全风险

当前已经有邀请码保护和匿名 client_id 隔离，但仍不是正式用户系统。

主要风险：

- 邀请码泄露后，任何拿到邀请码的人都可以访问。
- 没有正式账号、权限、审计和封禁能力。
- 没有速率限制，理论上可能被消耗 API Key。
- 匿名 client_id 依赖浏览器 localStorage，清除浏览器数据后身份会变化。

在 1-5 人可信试用范围内可以接受，但不适合公开传播。

### 2.4 文档和品牌风险

当前部分历史文档存在乱码或旧阶段描述。

已知风险：

- `docs/status.md` 存在历史乱码内容。
- 部分文档可能仍残留早期 WorkBuddy 命名或企业助手定位。
- GitHub 展示和后续维护容易被历史信息干扰。

这不会直接影响运行，但会影响项目专业度、求职展示和未来协作。

### 2.5 回归风险

当前有 smoke test，但后端缺少系统化自动化测试。

风险包括：

- 后续修改 Repository 或 Service 时破坏 client_id 隔离。
- 修改文件生命周期时破坏上传、删除或状态持久化。
- 修改 RAG 时破坏普通聊天或历史消息保存。

## 3. 为什么 v1.7 不继续新增 AI 功能

v1.7 不建议继续新增 Agent、多文件 RAG、数据分析或复杂记忆功能。

原因：

1. 当前核心 AI 链路已经可用。
2. 项目刚刚进入公网试用，真实风险从“功能缺失”转向“稳定性、数据、安全和部署”。
3. 如果继续扩张功能，会增加调试面和回归风险。
4. ICP 备案和域名正式上线前，最适合做低风险整理。
5. 先把现有能力稳定下来，后续新增功能才有可靠基础。

v1.7 的目标不是让北辰agent“更聪明”，而是让它“更稳、更干净、更容易维护、更适合展示”。

### 4.2 清理 README

目标：

- 保留当前功能、运行方式、部署入口、安全边界。

### 4.3 清理部署文档

重点核对：

- `docs/deployment_guide.md`

确保文档说明：

## 5. 品牌命名清理方案

当前产品命名应统一为：

**北辰agent / Beichen Agent**

需要检查：

- `README.md`
- `frontend/package.json`
- `frontend/package-lock.json`
- `backend/.env.example`
- `docs/*.md`
- 前端页面展示文本。
- 后端 `APP_NAME` 默认值。

清理原则：

- 不为了命名清理修改业务逻辑。
- 不改动 RAG 主链路。
- 不扩大项目定位。
- 如果发现 `WorkBuddy` 残留，应替换为 `Beichen Agent` 或 `北辰agent`。

注意：

- `package-lock.json` 如因 package name 修改而变化，是可接受的工程元数据变化。
- 不应在 v1.7 中重新设计 UI 品牌系统。

## 6. 备份与恢复方案

### 6.1 需要备份的数据

生产服务器需要备份：

- SQLite 数据库：`runtime/data/beichen.db`
- 上传文件：`runtime/uploads/`
- 本地向量索引：`runtime/vector_store/`
- 生产配置示例说明：不备份真实 `.env` 到 Git，但服务器本地应有安全备份。

可选备份：

- `runtime/logs/`

日志通常不作为核心业务数据，但排查线上问题时有价值。

### 6.2 建议新增脚本

建议新增：

- `deploy/scripts/backup-runtime.sh.example`
- `deploy/scripts/restore-runtime.sh.example`

脚本保持模板性质，不写真实服务器路径以外的敏感信息。

备份脚本职责：

- 创建时间戳目录。
- 停止或提示暂停后端写入。
- 打包 SQLite、uploads、vector_store。
- 输出备份文件路径。
- 不打印 API Key。

恢复脚本职责：

- 提示确认风险。
- 停止后端服务。
- 解压备份文件。
- 恢复 SQLite、uploads、vector_store。
- 重启后端服务。
- 提示运行 smoke test。

### 6.3 备份频率建议

当前 1-5 人小规模试用：

- 手动备份：每次部署前。
- 定期备份：每天一次或每周数次。
- 重要文件测试前：手动备份。

暂不需要复杂对象存储和自动异地灾备。

## 7. 后端测试方案

### 7.1 为什么需要测试

当前项目已经包含：

- 文件生命周期。
- RAG 主链路。
- 会话持久化。
- client_id 隔离。
- 邀请码保护。

这些模块后续都容易被小改动影响。

v1.7 应引入基础后端测试，目标不是追求高覆盖率，而是保护最关键链路。

### 7.2 建议测试范围

优先测试：

1. `/health`
2. `/health/config`
3. 邀请码访问保护
4. `X-Beichen-Client-Id` 缺失或非法时的响应
5. 文件上传写入 client_id
6. 文件列表按 client_id 隔离
7. 删除文件不能删除其他 client_id 的文件
8. 创建会话写入 client_id
9. 会话列表按 client_id 隔离
10. 普通聊天携带 session_id 时消息落库

可暂缓测试：

- 真实 LLM API。
- 真实 embedding API。
- 大文件解析。
- Nginx 部署。

外部 API 相关测试可以使用 Mock Provider 或跳过。

### 7.3 建议新增文件

建议后续新增：

- `backend/tests/conftest.py`
- `backend/tests/test_health.py`
- `backend/tests/test_access_control.py`
- `backend/tests/test_client_isolation.py`
- `backend/tests/test_files_api.py`
- `backend/tests/test_chat_sessions.py`

测试数据库建议使用临时 SQLite 文件，不使用生产数据库。

## 8. 前端错误体验优化方案

### 8.1 当前问题

当前前端在遇到异常时，用户可能只看到：

- Failed to fetch
- Unexpected token
- 文件处理失败
- RAG 问答失败

这些提示对用户和开发者都不够友好。

### 8.2 优化目标

前端错误提示应做到：

- 用户知道发生在哪一步。
- 用户知道能否重试。
- 开发者能拿到 request_id 查日志。
- 不暴露 API Key、prompt、chunks 或服务器敏感路径。

### 8.3 建议展示方式

文件处理错误：

- 上传失败：提示文件大小、格式或网络问题。
- 解析失败：提示文档可能为空、损坏、扫描件 PDF 或格式不支持。
- 切块失败：提示解析文本异常。
- embedding 失败：提示向量化服务配置或外部 API 问题。
- 索引失败：提示服务器存储或路径问题。

RAG 问答错误：

- 没有 indexed 文件：提示先上传并等待处理完成。
- 检索失败：提示索引可能不存在或文件未处理完成。
- LLM 调用失败：提示模型服务暂时不可用。

所有后端错误尽量显示：

- 简短用户文案。
- request_id。
- 可重试建议。

## 9. 部署更新流程

### 9.1 推荐更新流程

服务器更新建议固定为：

1. SSH 登录服务器。
2. 进入项目目录。
3. 备份 runtime 数据。
4. `git pull origin main`
5. 检查后端依赖。
6. 运行后端 compile 检查。
7. 前端安装依赖或确认依赖。
8. `npm run build`
9. 重启后端 systemd 服务。
10. reload Nginx。
11. 请求 `/health`。
12. 请求 `/health/config`。
13. 执行 smoke test 或手动验证关键链路。

### 9.2 回滚流程

MVP 阶段建议使用简单回滚：

1. 记录部署前 commit hash。
2. 记录部署前 runtime 备份文件。
3. 如果新版本异常，`git checkout <previous_commit>`。
4. 重新 build 前端。
5. 重启后端。
6. 如涉及数据结构变更，恢复备份。

注意：

如果数据库结构发生变化，回滚风险会明显提高。因此 v1.7 不应做数据库结构大改。
