# v0.3 文件上传报告

> 本报告记录 v0.3 最小文件上传闭环的实现结果。
> 本阶段不包含 RAG、Embedding、文档解析、数据库、复杂任务队列或企业权限。

## 1. 本次完成内容

v0.3 已完成最小文件上传闭环：

```text
前端选择文件
  -> frontend/src/stores/fileStore.ts
  -> frontend/src/api/fileApi.ts
  -> POST /api/v1/files
  -> backend/app/api/v1/files.py
  -> backend/app/services/file_service.py
  -> 保存到 backend/uploads/
  -> 返回上传结果
  -> 前端文件中心展示真实上传结果
```

当前接口返回字段：

- `id`
- `original_name`
- `status`
- `size_bytes`
- `extension`
- `created_at`

当前文件状态只使用 `uploaded`。文档解析完成态、RAG 可问答态会留到后续阶段。

## 2. 修改文件说明

### 2.1 后端

`backend/app/api/v1/files.py`

- 新增文件上传路由。
- 接收 `multipart/form-data` 中的 `file` 字段。
- 调用 `FileService` 完成保存逻辑。
- 使用统一响应结构返回结果。

`backend/app/services/file_service.py`

- 新增文件上传业务服务。
- 负责文件名清理、扩展名校验、大小限制、生成 `file_id`、保存文件和返回元数据。
- 保留 FileService 边界，避免 API 层直接处理存储细节。
- 后续文档解析、RAG 索引和数据库持久化都可以从这里继续向后扩展。

`backend/app/schemas/file.py`

- 新增 `UploadedFileResponse`。
- 统一后端返回给前端的文件元数据结构。

`backend/app/core/config.py`

- 增加文件上传配置：
  - `UPLOAD_DIR`
  - `MAX_UPLOAD_SIZE_MB`
  - `ALLOWED_UPLOAD_EXTENSIONS`
- 让上传路径、大小限制和扩展名限制通过配置管理，避免硬编码散落在业务代码中。

`backend/app/core/errors.py`

- 增加文件相关错误：
  - `FileValidationError`
  - `FileStorageError`
- 上传失败时返回稳定 JSON，而不是抛出未处理异常。

`backend/app/main.py`

- 注册文件上传路由。
- 暴露正式接口：`POST /api/v1/files`。

`backend/requirements.txt`

- 增加 `python-multipart`。
- FastAPI 接收文件上传表单时需要该依赖。

`backend/.env.example`

- 增加文件上传配置示例。
- 帮助其他开发者复制 `.env` 后直接配置上传目录、大小和允许后缀。

### 2.2 前端

`frontend/src/api/fileApi.ts`

- 新增文件上传 API Client。
- 使用 `FormData` 调用 `POST /api/v1/files`。
- 解析统一响应结构。
- 将后端错误转成前端可展示的异常消息。

`frontend/src/stores/fileStore.ts`

- 将原来的本地模拟上传改为真实调用 `fileApi.uploadFile()`。
- 上传成功后，把后端返回的文件记录插入文件列表顶部。
- 保留本地删除逻辑，v0.3 暂不做后端删除。

`frontend/src/components/FileCenter.tsx`

- 保留原有文件中心 UI。
- 上传成功提示改为“上传成功”。
- 上传失败展示后端返回错误。
- 问答入口提示改为下一阶段开放，避免误导用户认为 RAG 已完成。

`docs/status.md`

- 更新当前版本为 `v0.3.0`。
- 记录真实文件上传闭环已完成。
- 明确文档解析、Embedding、RAG、数据库仍未开始。

## 3. 当前文件上传调用链路

前端：

```text
FileCenter.handleUpload()
  -> useFileStore.uploadFile(file)
  -> fileApi.uploadFile(file)
  -> fetch("/api/v1/files", FormData)
```

后端：

```text
POST /api/v1/files
  -> files.py upload_file()
  -> FileService.upload()
  -> 校验扩展名和大小
  -> 保存到 backend/uploads/{file_id}.{extension}
  -> UploadedFileResponse
  -> ok(response)
```

返回前端后：

```text
fileStore 将返回文件插入 files 列表顶部
  -> FileCenter 重新渲染
  -> 用户看到真实上传结果
```

已运行：


结果：通过。

结果：通过。

结果：通过。

已通过 FastAPI TestClient 验证上传 TXT：

```text
POST /api/v1/files
file=sample.txt
```

结果：

- HTTP 200。
- `code=0`。
- `data.status=uploaded`。
- 返回 `id`、`original_name`、`size_bytes`、`extension`、`created_at`。
- 文件保存到 `backend/uploads/`。

已通过 FastAPI TestClient 验证不支持格式：

```text
POST /api/v1/files
file=bad.exe
```

结果：

- HTTP 400。
- `code=42001`。
- 返回不支持文件类型错误。

测试过程中发现运行时依赖缺口：

- FastAPI 文件上传需要 `python-multipart`。
- 已加入 `backend/requirements.txt` 并安装到当前环境。

## 5. 当前剩余问题

- 文件元数据尚未持久化到数据库。
- 服务重启后，前端无法从后端恢复真实文件列表。
- 当前只保存文件，不解析内容。
- 当前不支持文件列表 API。
- 当前不支持文件删除 API。
- 当前不支持文件下载 API。
- 当前没有自动化测试目录。
- 上传文件只校验扩展名和大小，尚未做 MIME 深度识别、病毒扫描或 OCR。
- 前端文件中心仍保留部分历史 Mock 文件列表，用于展示 UI。

## 6. 下一阶段 v0.4 建议

v0.4 建议进入文档解析阶段，而不是直接进入 RAG。

建议目标：

- 增加 `DocumentParserService`。
- 首先支持 TXT 解析。
- 再按需支持 PDF 和 DOCX。
- 为上传文件生成可被后续 RAG 使用的纯文本内容。
- 暂时仍不引入复杂任务队列。

建议链路：

```text
FileService 保存文件
  -> DocumentParserService 解析文本
  -> 返回 parsed 状态或解析结果
  -> 后续阶段再做 chunk、embedding、vector search
```

这样可以继续保持 MVP 简单，同时为 v0.5 RAG 打好基础。
