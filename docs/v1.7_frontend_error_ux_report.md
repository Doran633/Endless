# v1.7.4 Frontend Error UX and Request ID 报告

## 1. 本阶段目标

v1.7.4 不新增 AI 业务功能，不修改 RAG、Embedding、VectorStore、Retrieval 主链路，也不修改数据库结构。

本阶段目标是让公网小范围试用中的错误更容易被用户理解，也更容易被开发者定位：

- 前端统一解析 API 错误。
- 从响应 body 或 `X-Request-Id` header 中提取 `request_id`。
- 文件处理失败时展示更明确的失败阶段。
- 聊天、RAG、会话恢复和邀请码相关失败时展示更清晰的错误文案。
- 不显示 API Key、prompt、chunks、服务器敏感路径等敏感信息。

## 2. 修改文件职责

### `frontend/src/api/http.ts`

新增统一 HTTP 错误处理能力：

- `ApiError`：统一承载错误信息、HTTP status、业务 code 和 request_id。
- `fetchWithAccess()`：继续自动携带邀请码和匿名 `client_id`，并把网络异常转换为可读错误。
- `parseApiResponse()`：统一解析后端标准响应，优先从 body 的 `request_id` 获取错误追踪 ID，其次读取 `X-Request-Id` header。
- `formatApiError()`：把错误格式化为用户可读文案，并在存在 request_id 时附加错误追踪 ID。

### `frontend/src/api/chatApi.ts`

聊天和会话 API client 改为统一调用 `parseApiResponse()`：

- 普通聊天。
- 会话列表。
- 创建会话。
- 删除会话。
- 查询会话消息。
- 绑定或解除会话文件。

### `frontend/src/api/fileApi.ts`

文件相关 API client 改为统一调用 `parseApiResponse()`：

- 文件列表。
- 文件上传。
- 文件删除。
- 文档解析。
- 文本切块。
- embedding。
- vector-store 保存和读取。
- 检索。
- 文件问答。

每个 API 保留阶段化 fallback 文案，方便区分上传、解析、切块、向量化、索引、检索和 RAG 问答。

### `frontend/src/types/index.ts`

- `stage` 标识失败阶段。

`FileIngestionState` 增加 `error` 字段，用于聊天侧和文件中心展示更具体的失败信息。

### `frontend/src/stores/fileStore.ts`

## 3. 错误解析流程

前端 API 调用现在遵循统一流程：

```text
Component / Store
-> api/*.ts
-> fetchWithAccess()
-> 后端 API
-> parseApiResponse()
-> 成功返回 data
-> 失败抛出 ApiError
-> formatApiError()
-> message / 聊天消息 / 文件状态展示
```

`parseApiResponse()` 会处理四类情况：

- 网络失败：例如后端未启动、Nginx 断开、浏览器无法连接。
- 非 JSON 响应：例如 Nginx 或后端返回了 HTML / plain text 500 页面。
- HTTP 错误：例如 401、404、500。
- 业务错误：后端标准响应中 `code !== 0`。

## 4. request_id 如何展示和排查

后端已经为请求生成 request_id，并通过响应 header `X-Request-Id` 或错误 body 的 `request_id` 返回。

前端会在可用时展示：

```text
错误追踪 ID：xxxx
```

排查时可以在服务器上搜索：

```bash
journalctl -u beichen-agent -n 200 --no-pager | grep <request_id>
```

如果启用了文件日志，也可以搜索：

```bash
grep <request_id> /opt/beichen-agent/runtime/logs/app.log
```

## 5. 文件处理错误如何定位阶段

文件自动处理链路是：

```text
upload -> parse -> chunk -> embedding -> vector-store
```

`fileStore` 会根据当前 `ingestion.status` 把失败映射到：

- `upload`
- `parse`
- `chunk`
- `embedding`
- `index`

这样用户不会只看到“文件处理失败”，开发者也能更快判断是文档解析问题、embedding 配置问题，还是本地索引保存问题。

## 6. 仍无法自动定位的错误

当前方案仍保持 MVP 简单，因此有些问题不能完全自动定位：

- 浏览器网络层直接失败时，通常没有后端 request_id。
- 如果 Nginx 在请求进入 FastAPI 前直接返回错误，可能只有 Nginx 日志，没有 FastAPI request_id。
- 如果第三方 LLM / embedding 服务返回模糊错误，前端只能展示后端整理后的摘要。
- 当前没有 Sentry、OpenTelemetry 或前端日志上报，因此无法自动收集用户浏览器环境。
- 当前不展示完整 prompt、chunks、上传文件内容，因此排查语义质量问题仍需要开发者结合文件、日志和用户复现步骤判断。

## 7. 安全边界

本阶段不会展示或记录：

- API Key。
- 真实邀请码列表。
- prompt 全文。
- chunks 全文。
- embeddings。
- 上传文件内容。
- 服务器敏感路径。

request_id 只用于定位日志，不是用户身份，也不是权限凭证。
