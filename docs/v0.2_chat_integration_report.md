# v0.2 聊天集成报告

> 本报告记录 v0.2 真实 LLM 聊天闭环的完成情况。
> 本阶段不新增文件上传、RAG、企业功能或复杂架构。

## 1. 本次完成的功能

v0.2 已完成真实聊天闭环：

```text
Frontend Chat UI
  -> frontend/src/api/chatApi.ts
  -> POST /api/v1/chat
  -> FastAPI Chat API
  -> ChatService
  -> LLMService
  -> MockLLMProvider / OpenAIProvider
  -> 返回 answer
  -> 前端展示 assistant 消息
```

已完成能力：

- 后端保留 `LLMProvider` 抽象。
- 后端保留 `MockLLMProvider`。
- 后端保留并增强 `OpenAIProvider`。
- `LLM_PROVIDER` 支持 `mock` 和 `openai`。
- 未知 `LLM_PROVIDER` 不再静默回退 Mock。
- `OPENAI_API_KEY` 缺失时返回明确错误。
- OpenAI-compatible 请求失败和响应异常会返回统一错误。
- 前端聊天发送消息时调用后端 `/api/v1/chat`。
- 前端收到后端 answer 后展示为 assistant 消息。
- 前端 API 调用失败时展示错误消息。

## 2. 修改文件说明

### 2.1 `backend/app/core/config.py`

修改原因：

- v0.2 需要稳定 LLM 调用配置。

修改内容：

- 增加 `llm_timeout_seconds`。
- 继续保留 `llm_provider`、`llm_model`、`openai_api_key`、`openai_base_url`。

影响：

- OpenAI-compatible 调用不再使用硬编码 timeout。
- 后续 LLM Provider 可复用同一配置入口。

### 2.2 `backend/app/core/errors.py`

修改原因：

- 当前缺少应用级错误类型，LLM 错误会以普通异常冒泡。

修改内容：

- 新增 `AppError`。
- 新增 `LLMConfigError`。
- 新增 `LLMProviderError`。

影响：

- v0.2 的 LLM 配置错误和调用错误有稳定错误码。
- 后续文件上传和 RAG 可以沿用同样的错误边界。

### 2.3 `backend/app/core/exception_handlers.py`

修改原因：

- API 需要把应用错误统一转换为 JSON 响应。

修改内容：

- 新增 `register_exception_handlers(app)`。
- 捕获 `AppError` 并返回 `{ code, message, data }`。

影响：

- 前端可以稳定处理后端业务错误。
- 避免 LLM 配置问题直接暴露为未处理 500。

### 2.4 `backend/app/main.py`

修改原因：

- 需要注册全局异常处理器。

修改内容：

- 调用 `register_exception_handlers(app)`。

影响：

- 所有路由中抛出的 `AppError` 都会统一返回 JSON。

### 2.5 `backend/app/services/llm_service.py`

修改原因：

- 旧逻辑会在 provider 配置错误时静默回退 Mock。

修改内容：

- 增加简单 provider registry：
  - `mock`
  - `openai`
- 未知 provider 抛出 `LLMConfigError`。

影响：

- 演示和联调时可以确认是否真的走真实 LLM。
- 保持 `ChatService` 不关心具体 Provider。

### 2.6 `backend/app/llm/openai_provider.py`

修改原因：

- 旧实现错误处理较粗，timeout 硬编码。

修改内容：

- API key 缺失时抛出 `LLMConfigError`。
- 请求失败时抛出 `LLMProviderError`。
- JSON 解析失败时抛出 `LLMProviderError`。
- 上游响应结构异常时抛出 `LLMProviderError`。
- 使用 `settings.llm_timeout_seconds`。

影响：

- OpenAI-compatible 调用更稳定。
- 前端能收到可理解的失败原因。

### 2.7 `frontend/src/api/chatApi.ts`

修改原因：

- 前端缺少真实聊天 API client。

修改内容：

- 新增 `sendChatMessage(message)`。
- 调用 `POST /api/v1/chat`。
- 解析统一响应结构。
- 后端错误转换为前端异常。

影响：

- 前端聊天不再直接依赖 Mock AI 回复。

### 2.8 `frontend/src/stores/chatStore.ts`

修改原因：

- 旧逻辑使用 `generateAIResponse()` 模拟回复。

修改内容：

- 改为调用 `sendChatMessage(content)`。
- 成功时追加 assistant 消息。
- 失败时追加错误 assistant 消息。

影响：

- 页面聊天开始走真实后端链路。
- Mock 会话数据仍保留用于原型初始化。

### 2.9 `frontend/src/vite-env.d.ts`

修改原因：

- TypeScript 缺少 `import.meta.env` 类型。

修改内容：

- 引入 `vite/client` 类型。

影响：

- `VITE_API_BASE_URL` 能通过 TypeScript 类型检查。

## 3. 当前聊天调用链路

当前成功链路：

```text
用户输入
  -> chatStore.sendMessage()
  -> sendChatMessage()
  -> POST http://localhost:8000/api/v1/chat
  -> backend/app/api/v1/chat.py
  -> ChatService.answer()
  -> LLMService.chat()
  -> MockLLMProvider.chat() 或 OpenAIProvider.chat()
  -> ChatService 返回 answer/model/usage
  -> ok(result)
  -> 前端追加 assistant 消息
```

当前仍保留的临时路径：

- `POST /chat`
- `POST /api/v1/chat`

正式业务路径建议继续使用：

- `POST /api/v1/chat`

## 4. Mock Provider 和 OpenAI Provider 使用方式

### 4.1 Mock Provider

用途：

- 本地无 API key 开发。
- 前后端联调。
- 自动化测试。

配置：

```text
LLM_PROVIDER=mock
```

特点：

- 不依赖网络。
- 不需要 API key。
- 返回本地模拟回答。

### 4.2 OpenAI Provider

用途：

- 真实 LLM 聊天。
- 演示真实模型能力。

配置：

```text
LLM_PROVIDER=openai
LLM_MODEL=gpt-4o-mini
OPENAI_API_KEY=your_api_key
OPENAI_BASE_URL=https://api.openai.com/v1
LLM_TIMEOUT_SECONDS=30
```

错误行为：

- 缺少 `OPENAI_API_KEY`：返回 `43001`。
- 上游请求失败：返回 `43002`。
- 上游响应格式异常：返回 `43002`。

## 7. 下一阶段 v0.3 文件上传建议

v0.3 应进入最小文件上传闭环。

目标：

```text
Frontend FileCenter
  -> POST /api/v1/files
  -> FastAPI
  -> FileService
  -> local uploads/
  -> 返回 file_id/original_name/status
  -> Frontend 展示真实上传结果
```

建议范围：

- 新增 `backend/app/api/v1/files.py`。
- 新增 `backend/app/services/file_service.py`。
- 新增 `backend/app/schemas/file.py`。
- 新增本地 `uploads/` 存储目录。
- 新增 `frontend/src/api/fileApi.ts`。
- 修改 `frontend/src/stores/fileStore.ts` 真实上传。

v0.3 暂不做：

- RAG。
- Embedding。
- 向量数据库。
- 数据库持久化。
- 企业权限。
- PPT。
- 复杂任务队列。

建议验收：

- 用户可以从前端选择文件。
- 后端保存文件到本地。
- 后端返回文件 ID 和状态。
- 前端展示真实上传结果。
- 不支持的格式和过大文件有明确错误。
