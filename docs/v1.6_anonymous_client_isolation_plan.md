# v1.6.3 Anonymous Client Isolation Plan

## 1. 当前问题

项目已经通过公网 IP 完成服务器部署验证，手机和其他设备可以访问应用。

但当前所有访问者会共享同一套数据：

- 会话列表共享。
- 聊天消息共享。
- 文件列表共享。
- 当前会话绑定文件可能互相影响。
- RAG 文件问答历史会被其他访问者看到。

这在单人本地开发阶段可以接受，但公网试用阶段会带来明显的隐私和体验问题。

当前问题不是邀请码失效，而是邀请码只解决“谁可以进入应用”，没有解决“进入后数据属于谁”。

## 2. 为什么会共享历史记录

当前后端已经有 SQLite 持久化：

- `files`
- `chat_sessions`
- `chat_messages`

但这些表没有用户隔离字段，例如：

- `user_id`
- `client_id`
- `invite_code_id`

因此接口查询时只能返回全局数据。例如：

```text
GET /api/v1/chat/sessions
-> 查询 chat_sessions 全表
-> 所有访问者看到同一批会话
```

文件中心也是同理：

```text
GET /api/v1/files
-> 查询 files 全表
-> 所有访问者看到同一批文件
```

这说明当前项目已经从“单人本地 MVP”进入“公网多人试用”阶段，必须补齐最小数据隔离。

## 3. 为什么选择匿名 client_id

本阶段不适合直接实现完整用户系统，因为完整用户系统会引入：

- 注册登录。
- 密码存储。
- JWT。
- refresh token。
- 用户表。
- 权限模型。
- 登录态过期处理。
- 密码找回。
- 多用户安全策略。

这些会显著扩大 v1.6 部署整理阶段的范围。

更适合当前 MVP 的方案是匿名客户端隔离：

```text
浏览器首次访问
-> 前端生成 client_id
-> 保存到 localStorage
-> 每次 API 请求携带 X-Beichen-Client-Id
-> 后端按 client_id 过滤文件、会话和消息
```

它的优点：

- 不需要注册登录。
- 不需要新增复杂认证系统。
- 不影响现有邀请码访问。
- 不改变 RAG 主链路。
- 对公网小范围试用已经足够。
- 未来可以迁移到正式用户系统。

它的限制：

- 换浏览器、清理 localStorage 或换设备后，会变成新的匿名客户端。
- 不能跨设备同步历史。
- 不能证明真实用户身份。
- 不是正式权限系统。

## 4. 邀请码和 client_id 的职责区别

邀请码和 client_id 不能混为一谈。

邀请码职责：

```text
判断访问者是否允许进入应用
```

例如：

- 是否可以调用 `/api/v1/*`。
- 是否可以消耗后端配置的 LLM / Embedding API Key。
- 是否可以访问应用功能。

client_id 职责：

```text
判断这条数据属于哪个匿名客户端
```

例如：

- 当前客户端能看到哪些文件。
- 当前客户端能看到哪些会话。
- 当前客户端能看到哪些消息。
- 当前客户端能绑定哪些文件。

推荐边界：

```text
邀请码 = 门票
client_id = 匿名数据空间
```

不建议使用邀请码直接隔离数据，因为多个可信任用户可能共用同一个邀请码。如果邀请码直接等同用户身份，后续会变得难管理。

## 5. 后端数据模型调整

建议在现有 SQLite 表中增加 `client_id` 字段。

### 5.1 files 表

新增字段：

```text
client_id TEXT NOT NULL
```

用途：

- 标识文件属于哪个匿名客户端。
- `GET /api/v1/files` 只返回当前 `client_id` 的文件。
- `DELETE /api/v1/files/{file_id}` 只能删除当前 `client_id` 的文件。
- 文件解析、切块、向量化、索引、检索、问答都需要校验文件归属。

### 5.2 chat_sessions 表

新增字段：

```text
client_id TEXT NOT NULL
```

用途：

- 标识会话属于哪个匿名客户端。
- `GET /api/v1/chat/sessions` 只返回当前 `client_id` 的会话。
- 切换、删除、绑定文件时只允许操作当前 `client_id` 的会话。

### 5.3 chat_messages 表

可选方案有两种：

方案 A：不新增 `client_id`

- 通过 `session_id` 间接归属到 `chat_sessions.client_id`。
- 查询消息时先校验 session 属于当前 client。
- 数据冗余少。

方案 B：新增 `client_id`

- 消息表也直接保存 `client_id`。
- 查询更直接。
- 冗余字段更多。

推荐方案 A：

```text
chat_messages 不新增 client_id
通过 session_id -> chat_sessions.client_id 做归属校验
```

理由：

- 保持 MVP 简单。
- 避免同一条消息出现两个归属来源。
- 当前消息永远属于某个会话，间接隔离足够。

## 6. API header 设计

新增请求头：

```text
X-Beichen-Client-Id: <uuid>
```

前端生成格式建议：

```text
crypto.randomUUID()
```

如果浏览器不支持，可降级为：

```text
client_<timestamp>_<random>
```

后端行为：

- 对 `/api/v1/*` 业务接口读取 `X-Beichen-Client-Id`。
- 缺少 header 时返回明确错误。
- header 为空时返回明确错误。
- 不把 `client_id` 当作安全凭证，只作为数据分区标识。
- `/health` 和 `/health/config` 不需要 `client_id`。

建议新增错误：

```text
MissingClientIdError
InvalidClientIdError
ResourceNotFoundError 或沿用现有 NotFound
```

安全边界：

- `client_id` 不是密码。
- `client_id` 不应显示在页面主要 UI 中。
- 日志中可以记录截断后的 client_id 前缀，避免完整暴露。

## 7. Repository 查询隔离方案

Repository 层需要把 `client_id` 作为查询条件的一部分。

### 7.1 FileRepository

建议调整：

- `create_file(..., client_id)`
- `list_files(client_id)`
- `get_file(file_id, client_id)`
- `delete_file(file_id, client_id)`
- `update_parsed(file_id, client_id, ...)`
- `update_chunked(file_id, client_id, ...)`
- `update_embedded(file_id, client_id, ...)`
- `update_indexed(file_id, client_id, ...)`
- `touch_failed(file_id, client_id, ...)`

原则：

```text
任何按 file_id 操作 files 表的方法，都必须同时带 client_id。
```

### 7.2 ChatRepository

建议调整：

- `create_session(..., client_id)`
- `list_sessions(client_id)`
- `get_session(session_id, client_id)`
- `delete_session(session_id, client_id)`
- `update_bound_file(session_id, client_id, file_id)`
- `clear_bound_file(session_id, client_id)`
- `list_recent_messages(session_id, client_id, limit)`

原则：

```text
任何按 session_id 操作会话的方法，都必须同时校验 client_id。
```

### 7.3 ConversationService

ConversationService 负责业务编排：

- 创建会话时写入 client_id。
- 查询会话列表时传入 client_id。
- 查询消息前校验 session 属于 client_id。
- 普通聊天持久化时确认 session 属于 client_id。
- RAG 问答持久化时确认 session 和 file 都属于 client_id。
- 绑定文件时确认 file 属于同一 client_id 且状态为 indexed。

### 7.4 FileService

FileService 负责文件归属：

- 上传文件时写入 client_id。
- 删除文件时只删除当前 client_id 的文件。
- 删除文件后只清理当前 client_id 下绑定该文件的会话。
- 解析、切块、向量化、索引时校验文件归属。

## 8. 前端状态设计

前端新增匿名客户端状态。

### 8.1 client_id 生成

新增本地工具函数或 store 字段：

```text
getOrCreateClientId()
```

逻辑：

```text
读取 localStorage.beichen_client_id
-> 如果存在，复用
-> 如果不存在，生成新 id
-> 写入 localStorage
```

### 8.2 API Client 自动携带 header

所有业务 API 请求都携带：

```text
X-Beichen-Access: <邀请码>
X-Beichen-Client-Id: <匿名客户端 ID>
```

建议在统一 API client 中处理，不要在每个组件里手动拼 header。

### 8.3 会话恢复

前端启动流程调整为：

```text
读取或生成 client_id
-> 读取邀请码
-> 调用 GET /api/v1/chat/sessions
-> 后端只返回当前 client_id 的会话
-> 无会话时创建默认“新对话”
```

### 8.4 文件中心恢复

文件中心加载流程调整为：

```text
调用 GET /api/v1/files
-> 后端只返回当前 client_id 的文件
```

### 8.5 清除本地身份

退出邀请码时建议只清除邀请码，不清除 client_id。

原因：

- 用户退出后再次输入邀请码，仍希望看到自己的历史。

可以预留开发调试入口：

```text
重置本机数据身份
```

但本阶段不建议做成明显 UI 功能，避免误删用户本地身份。

## 9. 旧数据处理方案

用户明确要求清空旧历史记录。

推荐处理方式：

```text
部署 v1.6.3 后，清空服务器旧 SQLite 数据、uploads、vector_store
```

原因：

- 当前线上数据刚开始试用，历史价值低。
- 旧数据没有 client_id，迁移意义不大。
- 保留旧共享历史会继续造成隐私风险。
- 清空后每个设备重新生成 client_id，数据隔离更干净。

### 9.1 清空范围

建议清空：

```text
/opt/beichen-agent/runtime/data/beichen.db
/opt/beichen-agent/runtime/uploads/*
/opt/beichen-agent/runtime/vector_store/*
```

保留：

```text
/opt/beichen-agent/runtime/backend.env
/opt/beichen-agent/logs/
/opt/beichen-agent/app/
/opt/beichen-agent/venv/
/opt/beichen-agent/frontend_dist/
```

### 9.2 清空时机

不要在规划阶段执行。

建议在代码部署完成后执行：

```text
1. stop beichen-agent
2. 备份当前 runtime
3. 删除旧 db、uploads、vector_store
4. start beichen-agent
5. 重新访问应用并验证
```

### 9.3 是否需要 migration

当前阶段不建议引入复杂 migration 系统。

原因：

- 项目仍是个人 MVP。
- 当前数据库结构仍在快速演进。
- 线上真实用户数据还没有正式沉淀。

可以采用简单策略：

```text
v1.6.3 部署时清空旧数据
v1.7 或正式公测前再设计 migration
```

## 10. 安全边界

匿名 client_id 是数据隔离机制，不是安全认证机制。

它可以解决：

- 不同浏览器默认不共享文件和会话。
- 不同设备默认不共享聊天历史。
- 文件删除和文件问答不会误操作别人的文件。
- 会话列表不会互相暴露。

它不能解决：

- 恶意用户伪造别人的 client_id。
- 邀请码泄露后的滥用。
- 正式账号权限管理。
- 用户跨设备同步。
- 多人协作空间。
- 审计和封禁。

当前安全边界仍然是：

```text
邀请码负责挡住非授权访问
client_id 负责小范围可信用户的数据隔离
```

这适合当前 2-5 人可信试用，不适合开放公测。

## 11. 测试方案

### 11.1 本地测试

准备两个浏览器环境：

- 浏览器 A：正常 Chrome。
- 浏览器 B：无痕窗口或另一个浏览器。

测试项：

1. A 输入邀请码后进入应用，创建会话并发送消息。
2. B 输入邀请码后进入应用，不应看到 A 的会话。
3. A 上传文件并完成 indexed。
4. B 文件中心不应看到 A 的文件。
5. A 基于文件提问后刷新，A 能恢复自己的会话和消息。
6. B 刷新后仍不应看到 A 的历史。
7. A 删除文件，不应影响 B 的文件列表。
8. 缺少 `X-Beichen-Client-Id` 的 API 请求应返回明确错误。
9. 缺少邀请码的 API 请求仍应被访问保护拦截。

### 11.2 后端 API 测试

使用两个不同 client_id：

```text
client-a
client-b
```

验证：

- client-a 创建会话后，client-b 查询不到。
- client-a 上传文件后，client-b 查询不到。
- client-b 不能绑定 client-a 的 file_id。
- client-b 不能删除 client-a 的 file_id。
- client-b 不能读取 client-a 的 session messages。

### 11.3 部署后测试

部署到 VPS 后：

1. 手机访问公网地址。
2. 电脑浏览器访问公网地址。
3. 两端输入同一个邀请码。
4. 分别发送消息。
5. 确认历史互不可见。
6. 分别上传文件。
7. 确认文件互不可见。

## 12. 部署注意事项

### 12.1 数据清空

本阶段计划清空旧历史记录。

部署前应先备份：

```bash
mkdir -p /opt/beichen-agent/backups/v1.6.3-before-isolation
cp -r /opt/beichen-agent/runtime/data /opt/beichen-agent/backups/v1.6.3-before-isolation/
cp -r /opt/beichen-agent/runtime/uploads /opt/beichen-agent/backups/v1.6.3-before-isolation/
cp -r /opt/beichen-agent/runtime/vector_store /opt/beichen-agent/backups/v1.6.3-before-isolation/
```

然后清空旧共享数据。

### 12.2 数据库结构变化

因为新增 `client_id` 字段，旧 SQLite 数据库不适合直接复用。

当前推荐：

```text
删除旧 beichen.db，让应用按新模型重新创建表。
```

这比手写临时 ALTER TABLE 更简单，也符合当前公网试用早期状态。

### 12.3 前端缓存

前端上线后，已有访问者浏览器会首次生成 client_id。

如果某个浏览器出现异常，可以让用户清除：

```text
localStorage.beichen_client_id
localStorage 中的邀请码
```

然后刷新页面。

### 12.4 回滚

如果 v1.6.3 出现问题：

1. `git checkout` 回到上一版本。
2. 重启后端。
3. 重新构建前端。
4. 如需恢复旧数据，从 backup 恢复 `runtime/data`、`uploads`、`vector_store`。
