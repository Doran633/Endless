# v0.8 Retrieval 检索服务计划

> 本计划用于 v0.8 开发阶段。目标是在不实现 RAG、不实现文件问答、不调用 LLM、不调用真实 embedding API、不引入数据库的前提下，实现最小检索闭环。

## 1. 当前状态

当前项目已经完成到 v0.7：

```text
文件上传
  -> 文档解析
  -> 文本切块
  -> mock 向量化
  -> 本地 VectorStore 保存
```

当前后端已经具备：

- `FileService`：保存上传文件。
- `DocumentParserService`：解析 TXT / DOCX / 可复制文本型 PDF。
- `ChunkService`：生成文本 chunks。
- `EmbeddingService`：基于 `MockEmbeddingProvider` 生成稳定 mock vectors。
- `VectorStoreService`：把 chunks 和 mock embeddings 保存到 `backend/vector_store/{file_id}.json`。

当前前端已经具备：

- 聊天侧文件上传入口。
- 上传后自动解析、切块、mock 向量化和本地索引保存。
- 文件中心展示 `indexed` 状态和索引摘要。

当前仍然缺失：

- 根据用户 query 生成 query embedding。
- 从 VectorStore 中读取文件索引并做相似度计算。
- 返回 top_k 相关 chunks。
- RetrievalService 检索边界。
- RAG 文件问答。

v0.8 要补齐的是：

```text
query
  -> query embedding
  -> vector search
  -> top_k chunks
```

不是：

```text
top_k chunks
  -> prompt
  -> LLM answer
```

## 2. 为什么 v0.8 只做 Retrieval，不做 RAG

RAG 可以拆成两层：

```text
Retrieval
  -> 找到相关上下文

Generation
  -> 基于上下文生成回答
```

当前项目还没有验证“能不能从已索引文件中找出相关 chunks”。如果直接做文件问答，回答效果不好时，很难判断问题来自哪里：

- chunk 切分是否合理？
- mock embedding 是否稳定？
- query embedding 是否生成正确？
- cosine similarity 是否计算正确？
- top_k 是否太小或太大？
- RAG prompt 是否写得不好？
- LLM 是否没有遵守上下文？

因此 v0.8 只做 Retrieval，目标是先验证：

```text
给一个 query，系统能返回最相关的 chunks
```

这样 v0.9 做 RAG 时，输入上下文来源已经清楚，问题定位也更简单。

## 3. RetrievalService 的作用

建议新增：

```text
backend/app/services/retrieval_service.py
```

`RetrievalService` 负责：

- 接收 `file_id`、`query`、`top_k`。
- 调用 embedding provider 为 query 生成 query vector。
- 调用 `VectorStoreService.load_file_vectors(file_id)` 读取已保存索引。
- 计算 query vector 与每个 chunk embedding 的相似度。
- 排序并返回 top_k chunks。

`RetrievalService` 不负责：

- 文件上传。
- 文档解析。
- 文本切块。
- 向量索引保存。
- 调用 LLM。
- 构造 RAG prompt。
- 生成最终答案。

推荐方法：

```text
retrieve(file_id: str, query: str, top_k: int) -> RetrieveResponse
```

内部辅助方法：

```text
_cosine_similarity(a: list[float], b: list[float]) -> float
_rank_items(query_vector, items, top_k)
```

## 4. 检索数据流

后端数据流：

```text
POST /api/v1/files/{file_id}/retrieve
  -> request: query + top_k
  -> RetrievalService.retrieve()
  -> EmbeddingService / MockEmbeddingProvider 生成 query vector
  -> VectorStoreService.load_file_vectors(file_id)
  -> 遍历 index.items
  -> 计算 cosine similarity
  -> 按 score 降序排序
  -> 返回 top_k chunks
```

输入示例：

```json
{
  "query": "这个文档主要讲了什么？",
  "top_k": 3
}
```

输出示例：

```json
{
  "code": 0,
  "message": "ok",
  "data": {
    "file_id": "uuid",
    "query": "这个文档主要讲了什么？",
    "top_k": 3,
    "result_count": 3,
    "results": [
      {
        "chunk_id": "uuid-0",
        "chunk_index": 0,
        "content": "chunk text",
        "char_count": 320,
        "score": 0.82
      }
    ]
  }
}
```

注意：

- v0.8 返回的是 chunks 和 score。
- 不返回 LLM answer。
- 不把 chunks 放进 prompt。
- 不调用 `/api/v1/chat`。

## 5. 相似度算法选择

v0.8 建议使用 cosine similarity。

公式：

```text
cosine_similarity(a, b)
  = dot(a, b) / (norm(a) * norm(b))
```

原因：

- 向量检索中最常用。
- 实现简单。
- 不依赖数据库或外部库。
- 后续迁移 pgvector 时概念一致。

边界处理：

- 如果两个向量维度不同，返回错误。
- 如果任一向量为空，返回错误。
- 如果任一向量 norm 为 0，score 可返回 `0.0` 或抛出稳定错误。

推荐实现：

```text
dot = sum(x * y for x, y in zip(a, b))
norm_a = sqrt(sum(x * x for x in a))
norm_b = sqrt(sum(y * y for y in b))
score = dot / (norm_a * norm_b)
```

排序：

```text
score 降序
chunk_index 升序作为稳定次级排序
```

这样当 score 相同时，返回顺序稳定。

## 6. API 设计

### 6.1 检索文件 chunks

新增接口：

```text
POST /api/v1/files/{file_id}/retrieve
```

请求体：

```json
{
  "query": "用户问题",
  "top_k": 3
}
```

字段规则：

- `query`：必填，非空字符串。
- `top_k`：可选，默认 3。
- `top_k` 最小 1，最大建议 10。

成功响应：

```json
{
  "file_id": "uuid",
  "query": "用户问题",
  "top_k": 3,
  "result_count": 3,
  "results": [
    {
      "chunk_id": "uuid-0",
      "chunk_index": 0,
      "content": "chunk text",
      "char_count": 320,
      "score": 0.82
    }
  ]
}
```

错误情况：

- 文件尚未索引：返回 `VectorStoreNotFoundError`。
- query 为空：返回检索参数错误。
- top_k 超出范围：返回检索参数错误。
- vector 维度不一致：返回检索错误。

### 6.2 暂不新增全局检索

v0.8 不建议实现：

```text
POST /api/v1/retrieve
```

原因：

- 当前没有用户、权限、文件列表和数据库。
- 全局检索会涉及多文件范围、排序合并和权限边界。
- MVP 阶段先按 `file_id` 检索最清晰。

## 7. 前端展示方案

v0.8 前端建议只在文件中心提供“检索测试”入口。

原因：

- 聊天区如果直接出现“问文件”，用户会以为已经支持 RAG 文件问答。
- 文件中心更适合展示调试型结果：query、score、chunk 内容。

建议改动：

- `frontend/src/api/fileApi.ts`
  - 新增 `retrieveFileChunks(fileId, query, topK)`。

- `frontend/src/stores/fileStore.ts`
  - 新增 `retrieveFile(fileId, query, topK)` 或由组件直接调用 API。

- `frontend/src/types/index.ts`
  - 新增 `RetrievalResult`、`RetrieveFileResponse` 类型。

- `frontend/src/components/FileCenter.tsx`
  - 对 `indexed` 文件增加“检索”按钮。
  - 弹窗里输入 query。
  - 可选择 top_k，默认 3。
  - 展示 chunk 内容和 score。

展示建议：

```text
Query: 这个文档主要讲了什么？

Top 1 · score 0.82
chunk content...

Top 2 · score 0.76
chunk content...
```

文案边界：

```text
当前仅展示检索结果，不代表已经生成文件问答答案。
```

不建议：

- 在聊天区自动插入检索结果。
- 自动调用 LLM。
- 显示“你现在可以问文件”。

## 8. 与 VectorStoreService / EmbeddingService 的关系

v0.8 后端服务关系：

```text
EmbeddingService
  -> 生成 query vector

VectorStoreService
  -> 读取 file_id 对应的本地索引

RetrievalService
  -> 编排 query vector + stored vectors
  -> 计算 similarity
  -> 返回 top_k chunks
```

职责边界：

- `EmbeddingService` 不关心检索。
- `VectorStoreService` 不计算相似度。
- `RetrievalService` 不读上传文件、不解析文档、不生成 embedding provider。
- API 层只负责接收请求和返回响应。

推荐实现方式：

```text
RetrievalService(
  embedding_service=EmbeddingService(),
  vector_store_service=VectorStoreService()
)
```

后续如果引入真实 embedding provider 或 pgvector：

- `EmbeddingService` 替换 provider。
- `VectorStoreService` 替换存储实现。
- `RetrievalService` 的外部接口尽量不变。

## 9. 风险和技术债

### 9.1 mock embedding 不代表真实语义

当前 query embedding 和 chunk embedding 都来自 `MockEmbeddingProvider`。

这只能验证工程链路：

```text
query -> vector -> similarity -> top_k
```

不能用于评估真实语义检索质量。

### 9.2 本地 JSON 检索性能有限

v0.8 会把 JSON 文件读入内存，然后遍历每个 chunk 计算相似度。

适合：

- 单文件。
- 少量 chunks。
- MVP 学习和调试。

不适合：

- 大规模知识库。
- 多文件全局检索。
- 高并发。

### 9.3 top_k 与 chunk 策略仍然粗糙

当前 chunk 策略是字符数切块，不是 tokenizer-aware 或 semantic chunk。

因此检索结果的 chunk 边界可能不理想。

v0.8 暂不优化 chunk 策略，避免范围扩大。

### 9.4 没有权限和文件列表

当前没有用户权限和文件元数据数据库。

所以 v0.8 只做：

```text
按 file_id 检索
```

不做全局检索和多用户隔离。

### 9.5 还不能回答问题

v0.8 只能返回 chunks，不能生成自然语言答案。

这是刻意控制范围，不是功能遗漏。

## 11. 后续如何接入 RagService 和文件问答

v0.8 完成后，链路会变成：

```text
file_id + query
  -> RetrievalService
  -> top_k chunks
```

v0.9 可以新增：

```text
RagService
  -> 调用 RetrievalService
  -> 组装 context
  -> 调用 LLMService
  -> 返回基于文件内容的答案
```

建议 v0.9 API：

```text
POST /api/v1/files/{file_id}/rag-chat
```

请求：

```json
{
  "question": "用户问题",
  "top_k": 3
}
```

后端链路：

```text
question
  -> RetrievalService.retrieve()
  -> top_k chunks
  -> RagService.build_prompt()
  -> LLMService.generate()
  -> answer + source chunks
```

未来迁移方向：

- mock embedding 替换为真实 embedding。
- 本地 JSON VectorStore 替换为 pgvector。
- 单文件检索扩展为多文件或知识库检索。
- Retrieval 结果作为 RAG source citations 返回前端。
