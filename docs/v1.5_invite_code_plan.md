# v1.5.4 Invite Code Access Plan

## 1. 当前访问保护状态

当前项目在 v1.5.1 已完成最小访问保护：

- 后端通过 `backend/.env` 读取 `APP_ACCESS_PASSWORD`。
- 后端通过 `APP_ACCESS_HEADER` 指定访问口令请求头，默认是 `X-Beichen-Access`。
- 当 `APP_ACCESS_PASSWORD` 为空时，本地开发不启用访问保护。
- 当 `APP_ACCESS_PASSWORD` 非空时，`/api/v1/*` 请求必须携带正确访问口令。
- `/health` 不受保护，便于本地检查和线上健康检查。
- 前端入口页支持输入访问口令。
- 前端将口令保存到 `localStorage`，并通过统一 API client 自动携带 header。
- 退出时会清除本地保存的访问口令。

当前访问保护仍然是单个共享口令，适合自己本地部署或给极少数可信任试用者使用。

## 2. 为什么需要邀请码

单个共享口令在小范围试用时很快会遇到问题：

- 所有人使用同一个口令，无法区分发给了谁。
- 如果口令泄露，只能整体更换，所有试用者都受影响。
- 无法单独撤销某个试用者的访问资格。
- 体验上更像“后台密码”，不如“邀请码”自然。

多个 6 位数字邀请码更适合当前 MVP：

- 可以给不同试用者分发不同邀请码。
- 某个邀请码泄露后，可以从 `.env` 中移除。
- 不需要用户注册、数据库表或完整认证系统。
- 仍然能保护 LLM / Embedding API Key 不被陌生人随意消耗。

## 3. 单访问口令和多个邀请码的区别

单访问口令：

```env
APP_ACCESS_PASSWORD=839204
```

特点：

- 所有人共用一个码。
- 配置简单。
- 适合本地部署初期。

多个邀请码：

```env
APP_INVITE_CODES=839204,102938,775421
```

特点：

- 可给不同人不同码。
- 可以单独移除某个邀请码。
- 仍然不识别真实用户身份。
- 仍然没有权限隔离、审计和用户数据隔离。

v1.5.4 推荐采用“多个邀请码 + 保留旧口令兼容”的方案。

## 4. .env 配置方案

新增：

```env
APP_INVITE_CODES=
```

示例：

```env
APP_INVITE_CODES=839204,102938,775421
```

保留：

```env
APP_ACCESS_PASSWORD=
APP_ACCESS_HEADER=X-Beichen-Access
```

兼容策略：

- 如果 `APP_INVITE_CODES` 非空，优先使用邀请码列表。
- 如果 `APP_INVITE_CODES` 为空但 `APP_ACCESS_PASSWORD` 非空，继续使用旧单口令模式。
- 如果两者都为空，本地开发不启用访问保护。

邀请码规则：

- 只接受 6 位数字。
- `.env` 中用英文逗号分隔。
- 后端启动时过滤空项和不合法项。
- 不在 `.env.example` 中写真实邀请码。

## 5. 后端校验方案

推荐在现有 `access_control_middleware` 中扩展，不新增复杂认证模块。

后端配置层：

- `settings.app_invite_codes: tuple[str, ...]`
- 从 `APP_INVITE_CODES` 读取。
- 按逗号拆分。
- 只保留符合 `^\d{6}$` 的邀请码。

后端校验逻辑：

1. 如果请求路径不是 `/api/v1/*`，直接放行。
2. 如果 `APP_INVITE_CODES` 和 `APP_ACCESS_PASSWORD` 都为空，直接放行。
3. 从 `APP_ACCESS_HEADER` 指定的 header 中读取用户输入码。
4. 如果配置了 `APP_INVITE_CODES`：
   - 用户输入必须命中邀请码列表。
5. 如果没有配置 `APP_INVITE_CODES`，但配置了 `APP_ACCESS_PASSWORD`：
   - 用户输入必须等于旧访问口令。
6. 校验失败返回 `401`。

不新增：

- 不新增用户表。
- 不记录邀请码使用次数。
- 不生成 token。
- 不做 JWT。
- 不做 session cookie。
- 不改 RAG、聊天、文件、数据库主链路。

## 6. 前端交互方案

前端入口页文案调整：

- 从“访问口令，本地开发可留空”
- 改为“邀请码，本地开发可留空”

本地存储：

- 继续使用 `localStorage`。
- 可以保留当前 key，减少迁移成本。
- 或改名为 `beichen_invite_code`，同时读取旧 key 做兼容。

API 请求：

- 继续通过 `fetchWithAccess()` 自动携带 header。
- header 名仍使用 `X-Beichen-Access`。
- 前端不需要知道后端当前是单口令模式还是多邀请码模式。

退出：

- 退出时清除本地邀请码。
- 用户下次进入需要重新输入。

错误处理：

- 如果后端返回 `401`，前端应提示“邀请码无效或已失效”。
- 不暴露具体是“不存在”“格式错误”还是“已被移除”，避免泄露有效性细节。

## 7. 安全边界

邀请码不是正式登录系统。

它能做到：

- 降低公网 API 被陌生人随意调用的风险。
- 支持给不同可信任试用者分发不同入口码。
- 支持通过修改 `.env` 移除某个邀请码。

它不能做到：

- 不能证明用户真实身份。
- 不能防止邀请码被转发。
- 不能做用户级数据隔离。
- 不能统计每个人的使用行为。
- 不能限制每个人的调用次数。
- 不能替代 HTTPS。

因此部署时仍然必须：

- 使用 HTTPS。
- 不公开真实 API Key。
- 不暴露 uploads、vector_store、SQLite。
- 小范围可信任试用。

## 8. 风险和技术债

主要风险：

- 邀请码保存在浏览器 `localStorage`，如果用户设备不安全，邀请码可能被读取。
- 邀请码是共享门禁，不是个人账号。
- 邀请码泄露后，只能手动修改 `.env` 并重启后端。
- 没有使用次数、过期时间和审计记录。
- 没有请求限流，仍可能被持有码的人大量调用。

可接受原因：

- 当前目标是个人 MVP 小范围试用。
- 不希望过早引入用户系统、JWT、权限和数据库表。
- 邀请码方案能用很小工程量换来更合理的试用分发体验。

后续如果需要更正式的访问控制，可以演进为：

- invite_codes 表。
- 邀请码过期时间。
- 邀请码使用次数限制。
- 简单账号登录。
- 每用户文件和会话隔离。
- 请求限流和成本统计。

## 9. 测试方案

后端测试：

- `APP_INVITE_CODES=` 且 `APP_ACCESS_PASSWORD=`：`/api/v1/*` 放行。
- `APP_INVITE_CODES=123456,654321`：无 header 返回 `401`。
- `APP_INVITE_CODES=123456,654321`：错误 header 返回 `401`。
- `APP_INVITE_CODES=123456,654321`：正确 header 返回正常响应。
- `APP_INVITE_CODES=abc,12345,123456`：只有 `123456` 生效。
- `APP_INVITE_CODES=` 且 `APP_ACCESS_PASSWORD=legacy-pass`：旧单口令仍可用。
- `/health` 始终不需要邀请码。

前端测试：

- 入口页显示“邀请码”。
- 输入正确邀请码后可以进入并正常调用聊天、文件、RAG API。
- 输入错误邀请码后 API 返回失败提示。
- 退出后本地邀请码被清除。
- 刷新页面后，如果 localStorage 中仍有邀请码，API 请求继续可用。

验证命令：

- `scripts/check-local.ps1`
- `python -m compileall app`
- `npm exec tsc -- --noEmit`

安全检查：

- 确认 `.env.example` 不包含真实邀请码。
- 确认 `backend/.env` 未被 Git 跟踪。
- 确认 docs 中只写示例邀请码，不写真实邀请码。
