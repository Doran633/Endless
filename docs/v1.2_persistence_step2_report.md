# v1.2.2 Conversation Session API 报告

## 1. 工程效果

v1.2.2 将 v1.2.1 已完成的会话数据库表和 `ChatRepository` 开放为后端 API 能力。

本阶段完成：

- 新增 `ConversationService`。
- 新增会话管理 API。
- 支持创建默认“新对话”。
- 支持查询会话列表。
- 支持查询会话消息。
- 支持删除会话，并同步删除其消息。
- 支持当前会话绑定或解除单个 `file_id`。
- 绑定文件时校验文件存在且状态为 `indexed`。
- 删除文件时清除数据库中绑定该文件的会话字段。

本阶段仍不接入前端，也不修改普通聊天和 RAG 主链路。

## 2. 修改文件职责

### `backend/app/core/errors.py`

新增会话相关业务错误：

- `ChatSessionNotFoundError`：会话不存在。
- `ChatSessionStorageError`：会话或消息存储失败。
- `ChatFileBindingError`：文件绑定失败，例如文件不存在或未 indexed。

### `backend/app/schemas/chat.py`

新增会话 API 所需 Schema：

- `ChatSessionCreateRequest`
- `ChatSessionResponse`
- `ChatSessionListResponse`
- `ChatMessageResponse`
- `ChatMessageListResponse`
- `BindSessionFileRequest`
- `DeleteChatSessionResponse`

这些 Schema 固定了 API 输入输出结构，避免前端直接依赖 ORM 字段。

### `backend/app/repositories/chat_repository.py`

新增绑定相关方法：

- `update_bound_file()`：为会话绑定一个文件。
- `clear_bound_file()`：解除单个会话的文件绑定。
- `clear_bound_file_for_file()`：删除文件时批量清理所有绑定该文件的会话。

Repository 仍只负责数据库读写，不处理文件状态校验和业务规则。

### `backend/app/services/conversation_service.py`

新增 `ConversationService`，负责会话业务编排：

- `create_session()`
- `list_sessions()`
- `get_messages()`
- `delete_session()`
- `bind_file()`
- `clear_file_binding_for_deleted_file()`

其中 `bind_file()` 会同时读取 `files` 表，确认目标文件存在且状态为 `indexed`。

### `backend/app/api/v1/chat.py`

新增 `session_router`，提供会话 API。

现有 `POST /chat` 和 `POST /api/v1/chat` 行为保持不变，仍由 `ChatService().answer()` 直接处理。

### `backend/app/main.py`

将 `session_router` 挂载到 `/api/v1`。

这样新会话接口只暴露为 `/api/v1/chat/sessions...`，不会额外暴露历史兼容路径。

### `backend/app/services/file_service.py`

删除文件成功后调用 `ConversationService().clear_file_binding_for_deleted_file(file_id)`，清理数据库中绑定该文件的会话字段。

文件删除的主流程仍保持：

```text
删除原始文件 -> 删除 JSON 索引 -> 删除 files 表记录
```

## 3. 新增 API

### `GET /api/v1/chat/sessions`

查询会话列表。

### `POST /api/v1/chat/sessions`

创建会话。

请求示例：

```json
{
  "title": "新对话",
  "mode": "chat"
}
```

### `DELETE /api/v1/chat/sessions/{session_id}`

删除会话，并同步删除该会话下的消息。

### `GET /api/v1/chat/sessions/{session_id}/messages`

查询某个会话下的消息列表。

### `PATCH /api/v1/chat/sessions/{session_id}/file`

绑定或解除当前会话文件。

绑定文件：

```json
{
  "file_id": "file_xxx"
}
```

解除绑定：

```json
{
  "file_id": null
}
```

## 4. ConversationService 和 ChatRepository 边界

`ChatRepository`：

- 只操作数据库。
- 不知道文件是否 indexed。
- 不调用 LLM。
- 不调用 RAG。
- 不处理 API 响应格式之外的业务规则。

`ConversationService`：

- 编排业务规则。
- 负责把 Repository 结果转换成 Schema。
- 负责绑定文件时检查 `files` 表。
- 负责把 SQLAlchemy 异常转换成稳定业务错误。

这个分层保证后续接入普通聊天和 RAG 消息落库时，不需要让 `ChatService` 或 `RagService` 直接操作 ORM。

## 5. 文件绑定校验逻辑

绑定文件时：

```text
ConversationService.bind_file(session_id, file_id)
-> ChatRepository.get_session(session_id)
-> FileRepository.get_file(file_id)
-> 校验 file_record.status == "indexed"
-> ChatRepository.update_bound_file(session_id, file_id)
```

如果文件不存在，返回文件绑定错误。

如果文件存在但未 indexed，也返回文件绑定错误。

这样可以避免前端把尚未完成处理的文件绑定到会话，导致后续 RAG 问答失败。

## 6. 删除文件时如何清除会话绑定

删除文件成功后：

```text
FileService.delete_file(file_id)
-> 删除 backend/uploads/ 原始文件
-> 删除 backend/vector_store/ JSON 索引
-> 删除 files 表记录
-> ConversationService.clear_file_binding_for_deleted_file(file_id)
-> ChatRepository.clear_bound_file_for_file(file_id)
```

这个流程保证数据库中不会留下指向已删除文件的 `bound_file_id`。

## 7. 为什么仍不接入前端和聊天消息落库

本阶段的目标是把会话管理 API 做稳。

如果同时接入前端和普通聊天/RAG消息落库，会同时改变：

- API 行为。
- 前端 Zustand 状态来源。
- 聊天发送流程。
- RAG 消息展示流程。

那样一旦出现问题，很难判断是 API、数据库、前端恢复还是 RAG metadata 的问题。

因此 v1.2.2 只完成后端会话 API。下一步 v1.2.3 再接普通聊天和 RAG 消息落库。

- RAG 问答尚未写入 `chat_messages.metadata_json`。
- 前端尚未使用会话 API 恢复会话列表和消息。
- 当前会话文件绑定已经有后端 API，但前端尚未接入刷新恢复。
- SQLite 表结构仍依赖 `create_all`，暂未引入 migration 系统。
