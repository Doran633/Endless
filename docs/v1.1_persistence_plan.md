# v1.1.0 数据库持久化规划

## 1. 当前问题

当前项目已经完成 v1.0.1 发布前整理，并具备真实 embedding RAG MVP 能力：

- 普通 AI 聊天可以调用真实 LLM。
- 文件可以上传到 `backend/uploads/`。
- 文件可以完成 TXT / DOCX / PDF 解析。
- 解析文本可以切块。
- chunks 可以生成 mock 或真实 embedding。
- chunks 和 embeddings 可以保存到 `backend/vector_store/` 本地 JSON VectorStore。
- RetrievalService 可以基于本地 JSON 索引检索 top_k chunks。
- RagService 可以完成单文件 RAG 问答。
- 聊天侧可以上传文件，并绑定最近一个 indexed 文件进行问答。

但当前仍有一个关键短板：**应用状态没有数据库持久化**。

具体表现：

- 刷新页面后，前端文件列表不能从后端恢复。
- 文件上传、解析、切块、向量化、索引状态主要依赖前端内存状态。
- 后端虽然保存了原始文件和本地 JSON 索引，但缺少统一的文件元数据记录。
- 聊天会话和聊天消息仍主要保存在前端状态中。
- 当前会话绑定的 RAG 文件刷新后不能可靠恢复。
- 文件删除没有形成完整闭环，无法同时清理文件元数据、上传文件和本地向量索引。

v1.1 的核心目标不是提升 RAG 智能程度，而是让当前 v1.0 的功能从“可演示闭环”升级为“可持续使用的 MVP”。

## 2. 为什么 v1.1 要做数据库持久化

数据库持久化是独立网页版 AI 助手从 Demo 走向可用产品的必要一步。

当前 RAG 主链路已经打通，但用户体验仍有明显断点：

- 用户上传过的文件刷新后看不到。
- 用户之前的对话刷新后丢失。
- 用户无法管理历史文件。
- 系统无法知道一个文件当前处理到哪个阶段。
- 后续如果要增加数据分析、历史对话、重新索引、批量管理，都需要稳定的数据记录。

因此 v1.1 要优先补齐：

- 文件元数据持久化。
- 文件处理状态持久化。
- 文件列表恢复。
- 聊天会话持久化。
- 聊天消息持久化。
- 会话绑定文件恢复。
- 文件删除闭环。

这会让项目从“功能链路可跑”进入“状态可恢复、数据可管理”的阶段。

## 3. 技术方案选择

### 3.1 选择 SQLite + SQLAlchemy

v1.1 推荐使用：

- SQLite：MVP 本地数据库。
- SQLAlchemy：Python ORM。
- Pydantic Schema：继续作为 API 输入输出结构。

选择原因：

- SQLite 不需要单独安装数据库服务，适合本地 MVP 和 GitHub 分享。
- SQLAlchemy 可以保持 Repository 层和数据库实现解耦，未来迁移 PostgreSQL 成本较低。
- 当前项目还没有多用户、多租户和高并发要求，不需要提前引入 PostgreSQL。
- 当前 embeddings 已经保存在本地 JSON VectorStore，不需要为了 v1.1 引入 pgvector。

### 3.2 暂不引入 Alembic

v1.1 暂不引入复杂 migration 系统。

原因：

- 当前仍是单人/本地 MVP 阶段。
- 数据模型数量少。
- 初期可以通过 `create_all()` 初始化表结构。
- 过早引入 Alembic 会增加学习和维护成本。

后续当数据模型稳定、准备多人协作或线上部署时，再引入 Alembic。

### 3.3 保留本地 JSON VectorStore

v1.1 不把 embeddings 存入数据库。

当前保持：

- SQLite 保存文件元数据、处理状态、会话、消息。
- `backend/vector_store/` 保存 chunks + embeddings JSON 索引。

这样做的好处：

- 不改变现有 RAG 主链路。
- 不引入 pgvector。
- 不增加向量数据库维护成本。
- 仍然为后续迁移 PostgreSQL / pgvector 保留接口边界。

## 6. 数据模型设计

### 6.1 files 表

用途：保存文件元数据和处理状态。

建议字段：

```text
id                string primary key
original_name     string
extension         string
size_bytes        integer
storage_path      string
status            string
text_preview      text nullable
char_count        integer nullable
chunk_count       integer nullable
embedding_count   integer nullable
embedding_dimension integer nullable
embedding_model   string nullable
vector_store_path string nullable
error_message     text nullable
created_at        datetime
updated_at        datetime
```

状态建议：

```text
uploaded
parsed
chunked
embedded
indexed
failed
deleted
```

MVP 可以先用一个 `status` 字段表达主状态，不拆分多个阶段状态表。

### 6.2 chat_sessions 表

用途：保存聊天会话。

建议字段：

```text
id              string primary key
title           string
mode            string
bound_file_id   string nullable
created_at      datetime
updated_at      datetime
```

说明：

- `bound_file_id` 用于恢复当前会话最近绑定的 indexed 文件。
- `mode` 可先保留为 `chat`，未来可扩展 `rag`、`data_analysis`。
- 不引入用户字段，因为 v1.1 不实现多用户。

### 6.3 chat_messages 表

用途：保存聊天消息。

建议字段：

```text
id              string primary key
session_id      string
role            string
content         text
metadata_json   text nullable
created_at      datetime
```

说明：

- `role` 可取 `user`、`assistant`、`system`。
- `metadata_json` 用于保存 RAG used_chunks 摘要、file_id、query 等扩展信息。
- MVP 阶段用 JSON 字符串即可，暂不拆成复杂引用表。

## 8. Service / Repository 分层设计

v1.1 推荐形成清晰分层：

```text
Frontend
  -> API Client
  -> FastAPI Router
  -> Service
  -> Repository
  -> SQLite
```

### 8.1 Router 职责

- 接收 HTTP 请求。
- 做请求参数校验。
- 调用 Service。
- 返回 Schema。
- 不直接写数据库。
- 不直接处理文件系统细节。

### 8.2 Service 职责

- 负责编排业务流程。
- 文件上传、解析、切块、向量化、索引仍由对应 Service 负责。
- 在关键节点调用 Repository 更新状态。
- 文件删除时协调多个资源清理。
- 聊天和 RAG 问答时负责保存消息记录。

### 8.3 Repository 职责

- 封装数据库 CRUD。
- 不调用 LLM。
- 不解析文件。
- 不做 RAG prompt。
- 不写复杂业务逻辑。

### 8.4 为什么不让 Service 直接操作 ORM

短期直接操作 ORM 会更快，但会带来问题：

- Service 会混入数据库细节。
- 后续迁移 PostgreSQL 时修改面扩大。
- 测试 Service 时更难替换数据层。
- 文件、聊天、RAG 的业务逻辑会和 SQLAlchemy 细节耦合。

Repository 是 v1.1 值得增加的最小抽象。

## 9. 前端接入方案

### 9.1 文件中心

页面加载时：

```text
FileCenter mounted
  -> fileStore.loadFiles()
  -> GET /api/v1/files
  -> 展示后端持久化文件列表
```

用户删除文件时：

```text
点击删除
  -> DELETE /api/v1/files/{file_id}
  -> 后端清理数据库记录、上传文件、本地 JSON 索引
  -> 前端移除该文件
```

### 9.2 聊天侧

页面加载时：

```text
App mounted
  -> chatStore.loadSessions()
  -> GET /api/v1/chat/sessions
  -> 展示历史会话列表
```

切换会话时：

```text
选择会话
  -> GET /api/v1/chat/sessions/{session_id}/messages
  -> 恢复消息列表
  -> 使用 session.bound_file_id 恢复当前会话文件绑定
```

聊天侧上传文件完成索引后：

```text
upload -> parse -> chunks -> embeddings -> vector-store
  -> PATCH /api/v1/chat/sessions/{session_id}/file
  -> 当前会话绑定 indexed file_id
```

发送消息时：

- 如果当前会话有 `bound_file_id`，继续调用 `/api/v1/files/{file_id}/ask`。
- 如果当前会话没有绑定文件，继续调用 `/api/v1/chat`。
- 后端保存 user message 和 assistant message。

## 10. 刷新恢复流程

刷新页面后目标状态：

```text
Frontend App 启动
  -> 加载会话列表
  -> 加载当前会话消息
  -> 恢复当前会话 bound_file_id
  -> 加载文件列表
  -> 文件中心显示历史文件和处理状态
```

恢复后用户应该看到：

- 左侧最近对话仍在。
- 当前会话历史消息仍在。
- 如果当前会话之前绑定过文件，聊天输入区仍显示该文件已可用于 RAG。
- 文件中心仍能看到已上传文件和 indexed 状态。
- 用户可以继续基于已 indexed 文件提问。

## 11. 文件删除流程

文件删除需要同时处理三类资源：

```text
DELETE /api/v1/files/{file_id}
  -> 查询 files 表
  -> 删除 backend/uploads/ 中的原始文件
  -> 删除 backend/vector_store/ 中的 JSON 索引
  -> 清除 chat_sessions.bound_file_id 中对该文件的绑定
  -> 删除或标记 files 表记录
  -> 返回删除结果
```

MVP 建议采用“物理删除文件 + 数据库记录标记 deleted 或直接删除”二选一。

建议 v1.1 初期选择：

- 原始文件物理删除。
- JSON 索引物理删除。
- 数据库文件记录保留为 `deleted` 状态或直接删除。

更推荐保留 `deleted` 状态，原因：

- 便于排查历史消息引用过的文件。
- 不会让历史 RAG 消息中的 file_id 变成完全不可追踪。
- 后续可以做回收站或审计。

但如果为了最小实现，也可以先直接删除数据库记录。实现阶段应在报告中明确选择。

## 12. 分步开发计划

### Step 1：数据库基础与文件元数据持久化

目标：

- 引入 SQLite + SQLAlchemy。
- 建立 `db` 和 `repositories` 目录。
- 创建 files 表。
- 上传文件成功后写入数据库。
- 新增 `GET /api/v1/files`。
- 刷新后文件中心可以恢复文件列表。

验收标准：

- 后端启动时自动创建 SQLite 数据库文件。
- 上传文件后，数据库中出现文件记录。
- 调用 `GET /api/v1/files` 能返回真实文件列表。
- 前端刷新后仍能看到已上传文件。
- 不影响现有上传、解析、切块、embedding、vector-store、RAG 问答链路。

### Step 2：文件处理状态持久化

目标：

- 解析成功后更新 `parsed` 状态、`text_preview`、`char_count`。
- 切块成功后更新 `chunked` 状态、`chunk_count`。
- 向量化成功后更新 `embedded` 状态、`embedding_count`、`embedding_dimension`、`embedding_model`。
- 索引保存成功后更新 `indexed` 状态、`vector_store_path`。
- 处理失败时记录 `failed` 和 `error_message`。

验收标准：

- 文件中心展示的状态来自后端数据库。
- 刷新后仍能看到文件处理进度。
- 已 indexed 文件刷新后仍可继续 RAG 问答。

### Step 3：文件删除 API

目标：

- 新增 `DELETE /api/v1/files/{file_id}`。
- 删除上传文件。
- 删除本地 JSON VectorStore。
- 清理或标记数据库文件记录。
- 清除会话中的文件绑定。
- 前端文件中心增加删除按钮。

验收标准：

- 删除后文件中心不再显示该文件，或显示为 deleted 状态。
- `backend/uploads/` 对应文件被删除。
- `backend/vector_store/` 对应索引被删除。
- 如果当前会话绑定了该文件，绑定状态被清除。
- 后续提问不会继续使用已删除文件。

### Step 4：聊天会话持久化

目标：

- 创建 `chat_sessions` 表。
- 新增会话列表 API。
- 新增创建会话 API。
- 前端侧边栏会话列表从后端恢复。
- 当前会话 id 由后端生成或持久确认。

验收标准：

- 新建会话后刷新页面仍能看到。
- 切换会话时能够定位到对应会话。

### Step 5：聊天消息持久化

验收标准：

验收标准：

## 15. 风险和技术债

### 15.1 SQLite 并发能力有限

SQLite 适合本地 MVP，但不适合高并发生产环境。

影响：

- 多用户同时写入时可能出现锁竞争。
- 后续部署到真实线上服务时需要迁移 PostgreSQL。

应对：

- v1.1 只面向本地和轻量使用。
- Repository 层隔离数据库访问，降低迁移成本。

### 15.2 没有复杂 migration 系统

v1.1 暂不引入 Alembic。

影响：

- 数据表结构变更时需要手动处理本地数据库。
- 早期开发可能需要删除本地 SQLite 文件重新创建。

应对：

- 在 README 中说明 MVP 阶段数据库重建方式。
- v1.2 或准备部署时再引入 Alembic。

### 15.3 文件系统与数据库可能不一致

例如：

- 数据库有记录，但上传文件被手动删除。
- JSON 索引存在，但数据库记录不存在。
- 删除过程中部分资源删除成功、部分失败。

应对：

- FileService 作为文件删除的统一协调者。
- 文件详情接口遇到缺失文件时返回明确错误。
- 后续可增加数据一致性检查脚本。

### 15.4 消息 metadata_json 缺少强类型

MVP 使用 JSON 字符串保存 RAG 引用信息。

影响：

- 查询和统计不方便。
- metadata 结构变化时缺少数据库层约束。

应对：

- 当前先保持简单。
- 后续如果需要复杂引用、审计和多文件 RAG，再拆分 message_references 表。

### 15.5 当前仍不支持多用户

v1.1 不引入用户系统。

影响：

- 所有本地数据都属于同一个默认用户环境。
- 不适合多人共享同一个服务实例。

应对：

- v1.1 明确定位为单用户本地 MVP。
- 等产品主链路稳定后再设计 Auth 和 User 表。

## 16. 后续如何迁移到 PostgreSQL / pgvector

v1.1 的设计要为后续迁移留出接口，但不提前实现。

### 16.1 PostgreSQL 迁移路径

未来可以将：

```text
SQLite
  -> PostgreSQL
```

需要调整：

- `DATABASE_URL` 从 SQLite 改为 PostgreSQL。
- SQLAlchemy engine 配置替换。
- 引入 Alembic 管理 migration。
- Repository 层大部分调用保持不变。

### 16.2 pgvector 迁移路径

当前：

```text
VectorStoreService
  -> backend/vector_store/*.json
```

未来：

```text
VectorStoreService
  -> PgVectorStoreRepository
  -> PostgreSQL + pgvector
```

迁移时可新增：

- `backend/app/repositories/vector_repository.py`
- `backend/app/vector_store/pgvector_store.py`
- `document_chunks` 表。
- `chunk_embeddings` 表或带 vector 字段的 chunks 表。

需要保持：

- RetrievalService 仍只关心“给我 top_k chunks”。
- RagService 仍只关心“拿 chunks 组 prompt 再调用 LLM”。
- 前端不需要知道底层是 JSON 还是 pgvector。

### 16.3 为什么现在不做 pgvector

当前不做 pgvector 的原因：

- v1.0 的单文件 RAG 已经能用本地 JSON 完成 MVP 闭环。
- v1.1 的主要矛盾是状态丢失，不是向量检索性能。
- pgvector 会引入 PostgreSQL 安装、配置、迁移和部署复杂度。
- 过早引入会让项目学习成本变高。

因此 v1.1 应先完成数据库持久化，再在后续版本升级 VectorStore。
