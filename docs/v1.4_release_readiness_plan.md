# v1.4.0 Release Readiness / Local Trial Package 规划

## 1. 当前项目状态

当前项目已完成 v1.3.2 RAG Context Follow-up，已经具备一个独立网页版 AI 助手 MVP 的核心闭环：

- 普通 AI 聊天。
- 真实 LLM API 调用。
- 文件上传。
- TXT / DOCX / 可复制文本型 PDF 文档解析。
- 文本切块。
- Mock / OpenAI-compatible Embedding。
- 本地 JSON VectorStore。
- Retrieval 检索。
- 单文件 RAG 问答。
- 聊天侧上传文件后自动处理并绑定当前会话。
- 普通聊天短上下文窗口。
- RAG 文件问答连续追问。
- SQLite + SQLAlchemy 文件、会话、消息持久化。

当前项目已经不是单纯 Demo，而是一个可以继续整理为“本地试运行 MVP”的工程。

但它还不是正式线上产品：

- 没有用户登录。
- 没有权限隔离。
- 没有生产级部署方案。
- 没有云端对象存储。
- 没有 pgvector 或生产级向量数据库。
- 没有完整自动化测试体系。
- 没有面向非技术用户的一键安装包。

## 2. 当前本地运行痛点

当前运行方式对开发者可接受，但对非技术用户仍然困难：

- 需要分别启动后端和前端。
- 需要理解 Python、Node、npm、端口和 `.env`。
- 端口 `8000`、`5173` 容易被旧进程占用。
- Vite 在当前沙箱里有时需要提升权限启动。
- 后端 `.env` 配置错误时，用户不容易判断是 API Key、base url 还是模型名错误。
- 前端请求失败时，用户容易只看到 `Failed to fetch`，不知道是后端没启动还是 API 地址不对。
- README 部分内容已落后于当前状态，例如当前已经有 SQLite 持久化，但 README 仍写“不包含数据库”。
- `backend/.env.example` 中 `APP_NAME=WorkBuddy Backend` 已不符合当前“北辰agent”定位。
- 临时公网隧道不稳定，不适合作为项目分享的主要方式。

## 3. 为什么 v1.4 不继续加 AI 功能

v1.3 已经连续加入了：

- 会话持久化。
- 消息持久化。
- 普通聊天上下文。
- RAG 连续追问。

这些已经让核心智能体验明显提升。

如果现在继续加 Agent、多文件 RAG、历史语义检索或数据分析，会带来两个问题：

- 项目可运行性和可分享性会继续落后。
- 后续调试成本会变高，因为基础启动、配置和错误定位还不够稳定。

因此 v1.4 的重点不是“更聪明”，而是“更稳、更容易运行、更容易交付”。

这符合 MVP 原则：

- 先保证核心闭环稳定。
- 再增加复杂能力。
- 不让部署和配置问题拖累用户体验。

## 5. 预计新增文件

### `scripts/start-local.ps1`

作用：

- 检查后端 `.env` 是否存在。
- 检查后端和前端依赖是否大致存在。
- 清理或提示端口占用。
- 启动 FastAPI 后端。
- 启动 Vite 前端。

## 7. 启动脚本设计

建议脚本：`scripts/start-local.ps1`

启动策略：

1. 定位项目根目录。
2. 检查 `backend/.env` 是否存在。
3. 检查端口 `8000` 和 `5173`。
4. 如果端口被占用，提示用户先运行 `stop-local.ps1`，或在脚本中提供可选清理。
5. 启动后端：

```powershell
cd backend
python -m uvicorn app.main:app --host 127.0.0.1 --port 8000 --reload
```

6. 启动前端：

```powershell
cd frontend
npm run dev -- --host 127.0.0.1 --port 5173 --strictPort
```

7. 输出：

```text
北辰agent 已启动
本机访问：http://127.0.0.1:5173/
后端健康检查：http://127.0.0.1:8000/health
```

注意：

- PowerShell 脚本应尽量保持透明，不隐藏关键错误。
- 前后端可以分别打开新窗口，方便用户看到日志。
- 不建议在 v1.4 中做复杂后台守护进程。

## 8. 停止脚本设计

建议脚本：`scripts/stop-local.ps1`

停止策略：

1. 查找监听 `8000` 的进程。
2. 查找监听 `5173` 的进程。
3. 显示将要停止的 PID。
4. 只停止明确监听这两个固定端口的进程。
5. 不递归删除文件。
6. 不清空数据库。
7. 不删除 uploads 或 vector_store。

安全原则：

- 只处理固定端口。
- 不使用模糊进程名批量杀进程，例如不要直接杀所有 `node` 或所有 `python`。
- 输出停止结果。

## 10. 端口清理策略

固定端口：

- 后端：`8000`
- 前端：`5173`

为什么固定：

- 前端 Vite proxy 当前指向 `http://127.0.0.1:8000`。
- 固定端口减少非技术用户理解成本。
- 避免每次启动换端口导致浏览器访问错误。

清理原则：

- 优先提示，再清理。
- 只清理监听固定端口的进程。
- 不按进程名批量清理。
- 清理前输出 PID。

常见状态解释：

- `LISTENING`：有进程正在监听端口，可能需要清理。
- `ESTABLISHED`：已有连接正在使用。
- `TIME_WAIT`：连接刚关闭后的系统状态，通常不用处理。
- `CLOSE_WAIT`：可能有程序未正常关闭连接，重启服务通常可解决。

## 11. `.env` 配置检查方案

v1.4 不读取或输出真实 API Key。

检查规则：

- 确认 `backend/.env` 文件存在。
- 确认 `LLM_PROVIDER` 存在。
- 如果 `LLM_PROVIDER=openai`：
  - 检查 `OPENAI_API_KEY` 是否非空。
  - 检查 `OPENAI_BASE_URL` 是否非空。
  - 检查 `LLM_MODEL` 是否非空。
- 如果 `EMBEDDING_PROVIDER=openai`：
  - 检查 `EMBEDDING_API_KEY` 或 `OPENAI_API_KEY` 至少一个存在。
  - 检查 `EMBEDDING_BASE_URL` 或 `OPENAI_BASE_URL` 至少一个存在。
  - 检查 `EMBEDDING_MODEL` 是否非空。
  - 检查 `EMBEDDING_DIMENSION` 是否与模型匹配。

只输出：

```text
[OK] LLM API Key 已配置
```

不要输出：

```text
sk-xxxx
```

## 13. 常见问题文档方案

建议新增：`docs/troubleshooting.md`

内容包括：

### 端口被占用

现象：

```text
Port 5173 is already in use
```

处理：

```powershell
scripts/stop-local.ps1
scripts/start-local.ps1
```

### 前端打不开

检查：

```text
http://127.0.0.1:5173/
```

如果打不开：

- 前端未启动。
- 端口被占用。
- 依赖未安装。

### 后端不可用

检查：

```text
http://127.0.0.1:8000/health
```

如果不返回 `ok`：

- 后端未启动。
- `.env` 配置错误。
- Python 依赖未安装。

### `Failed to fetch`

可能原因：

- 后端没启动。
- 前端代理没生效。
- 访问了错误端口。
- 临时公网隧道只暴露了前端但没有代理 API。

### 上传后不能问答

检查：

- 文件是否为 TXT / DOCX / 可复制文本型 PDF。
- 文件状态是否为 `indexed`。
- embedding provider 是否配置正确。
- 是否重新索引了文件。

### API Key 错误

处理：

- 检查 `backend/.env`。
- 检查 base url。
- 检查模型名。
- 检查余额和服务商权限。

可以包含：

- `backend/`
- `frontend/`
- `docs/`
- `README.md`
- `.gitignore`
- `backend/.env.example`
- `scripts/`

不应包含：

- `backend/.env`
- `backend/uploads/`
- `backend/vector_store/`
- `backend/data/`
- `frontend/node_modules/`
- `backend/__pycache__/`
- `.git/`
- `.claude/`

如果对方被允许使用你的 API Key：

- 不建议把 `.env` 放进压缩包。
- 可以单独私发 `.env`。
- 明确告诉对方不要上传 GitHub、网盘公开链接或转发给第三人。

对非技术用户的现实帮助程度：

- v1.4 可以把启动难度从“需要理解前后端”降到“按文档运行脚本”。
- 但第一次安装 Python、Node 和依赖仍可能需要你远程协助。
- 如果希望完全零配置，应进入正式部署，而不是本地试运行。

## 15. 临时公网分享为什么暂缓

本轮已验证免费临时隧道存在明显不稳定：

- 地址可能频繁变化。
- 本机可运行，但公网地址可能打不开。
- HTTPS / TLS 在部分 Windows 环境中可能出现兼容问题。
- 对方访问时，文件和 API 调用仍落到你的本机。
- 谁拿到链接，谁就能间接消耗你的 API Key。
- 上传文件会进入你的本机目录。

因此临时公网分享只适合短时间演示，不适合作为 v1.4 的主要目标。

更稳的路线：

1. v1.4 完成本地试运行整理。
2. v1.5 做部署前配置和安全边界。
3. 再选择正式部署平台。

## 16. 安全风险和 API Key 注意事项

必须保护：

- `backend/.env`
- LLM API Key
- Embedding API Key
- 上传的文件内容
- SQLite 数据库中的聊天记录和文件元数据
- 本地 JSON VectorStore 中的 chunk 文本和 embedding

风险说明：

- API Key 泄露会导致费用损失。
- 上传文件可能包含隐私内容。
- `backend/vector_store/` 中保存了原文 chunk，不只是向量。
- `backend/data/beichen.db` 中保存了会话消息。
- 给别人临时网址时，对方使用的是你本机和你的 API 配置。

v1.4 应明确：

- 默认不分享 `.env`。
- 默认不分享数据库。
- 默认不分享上传文件和索引。
- 如果共享 API Key，只能给可信任对象，并且应设置用量限制。
