# v1.2.0 Persistent Conversations 持久会话开发计划

## 1. 当前问题

当前项目已经完成 v1.1.4 File Lifecycle，文件侧已经具备较完整的工程闭环：

- 文件上传后可自动解析、切块、生成 embedding、保存本地 JSON VectorStore。
- 文件元数据和处理状态已经写入 SQLite。
- 文件中心刷新后可以恢复文件列表和文件处理状态。
- 文件可以真实删除，删除范围包括原始文件、本地 JSON 索引和 SQLite 文件记录。
- 普通聊天和单文件 RAG 问答已经可用。

当前最大缺口已经从“文件处理链路”转移到“聊天状态持久化”：

- 聊天会话列表仍主要保存在前端内存或 Mock 状态中。
- 聊天消息刷新页面后会丢失。
- 聊天侧绑定的 RAG 文件只保存在当前前端状态中，刷新后无法恢复。
- 普通聊天和 RAG 问答结果没有统一保存到后端。
- RAG 回答中使用的 `used_chunks` 只在当前响应里展示，没有作为消息 metadata 保存。
- 删除文件时，虽然会清除当前前端绑定，但数据库中还没有会话绑定字段可同步清理。

## 2. v1.2.0 目标状态

v1.2.0 的目标是让“对话”从临时前端状态升级为可恢复的后端状态。

完成后应达到：

- 后端新增 `chat_sessions` 表。
- 后端新增 `chat_messages` 表。
- 用户刷新页面后，可以恢复会话列表。
- 切换会话时，可以恢复该会话的历史消息。
- 普通聊天消息可以持久化。
- 单文件 RAG 问答消息可以持久化。
- RAG 回答关联的 `used_chunks`、`rag_file_id`、`rag_file_name` 等信息可以保存在消息 metadata 中。
- 每个会话可以绑定一个最近 indexed 的文件。
- 刷新后可以恢复当前会话绑定的 RAG 文件。
- 删除文件时，会清除所有绑定该文件的会话字段。
- 现有普通聊天和 RAG 主链路保持不变，只在调用链外围增加持久化编排。

## 3. 为什么现在进行会话持久化

现在进入会话持久化是合适的，因为项目已经具备三个前提：

1. 文件链路已经闭环。
   上传、解析、切块、embedding、VectorStore、Retrieval、RAG 都已经存在，聊天持久化可以直接围绕这些能力记录结果。

2. SQLite 已经接入。
   v1.1 已经建立 `db/` 和 `repositories/` 基础目录，文件表已经运行。继续加入会话和消息表，工程成本低，技术路线一致。

3. 用户体验瓶颈已经明显。
   当前 AI 助手可以回答，但刷新就丢失聊天历史，这会让产品不像一个真实应用。v1.2 解决的是“能持续使用”的问题。

本阶段仍不做历史消息语义检索和长期记忆。持久化只解决“保存和恢复”，不等于让 LLM 自动理解全部历史上下文。

## 4. 数据模型设计

### 4.1 chat_sessions

建议字段：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | `String(64)` | 会话 ID，主键 |
| `title` | `String(255)` | 会话标题，默认“新对话”，可后续根据首条消息更新 |
| `mode` | `String(32)` | 会话模式，MVP 可使用 `chat` |
| `bound_file_id` | `String(64) nullable` | 当前会话绑定的单个 indexed 文件 |
| `created_at` | `DateTime` | 创建时间 |
| `updated_at` | `DateTime` | 更新时间 |

设计说明：

- `bound_file_id` 先不做外键强约束，避免删除文件时被 SQLite 外键配置阻塞。
- 当前会话只绑定一个文件，符合 v0.9.1 的产品原则。
- `mode` 暂时保留简单字符串，未来可以区分普通聊天、文件问答、数据分析等会话类型。

### 4.2 chat_messages

建议字段：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | `String(64)` | 消息 ID，主键 |
| `session_id` | `String(64)` | 所属会话 ID |
| `role` | `String(32)` | `user` 或 `assistant` |
| `content` | `Text` | 消息正文 |
| `metadata_json` | `Text nullable` | JSON 字符串，保存 RAG 引用等扩展信息 |
| `created_at` | `DateTime` | 创建时间 |

`metadata_json` 建议保存：

```json
{
  "rag_file_id": "file_xxx",
  "rag_file_name": "example.pdf",
  "used_chunks": [
    {
      "chunk_id": "chunk_xxx",
      "chunk_index": 0,
      "content": "reference preview",
      "score": 0.82
    }
  ],
  "token_count": null
}
```

设计说明：

- SQLite MVP 阶段用 `Text` 保存 JSON 字符串即可，不引入 JSON 字段兼容问题。
- `used_chunks` 属于消息展示 metadata，不进入向量数据库。
- `token_count` 先预留，可为空，不在本阶段统计真实 token。

## 5. Repository 和 Service 职责

### 5.1 ChatRepository

预计新增：`backend/app/repositories/chat_repository.py`

职责：

- 创建会话。
- 查询会话列表。
- 查询单个会话。
- 删除会话及其消息。
- 更新会话标题。
- 更新会话绑定文件。
- 清除绑定某个 `file_id` 的所有会话。
- 创建消息。
- 查询某个会话下的消息列表。

设计原则：

- 只负责数据库读写。
- 不调用 LLM。
- 不调用 RAG。
- 不拼装 prompt。
- 不处理前端展示格式之外的业务编排。

### 5.2 ConversationService

预计新增：`backend/app/services/conversation_service.py`

职责：

- 编排会话创建和默认会话逻辑。
- 编排消息保存。
- 在普通聊天完成后保存 user 和 assistant 消息。
- 在 RAG 问答完成后保存 user 和 assistant 消息，并写入 metadata。
- 处理会话绑定文件。
- 删除文件时清除会话绑定。

设计原则：

- `ChatService` 继续负责普通聊天回答。
- `RagService` 继续负责 RAG 问答。
- `ConversationService` 负责“把聊天/RAG结果落库”。
- API 层可以调用 `ConversationService`，但不直接操作 ORM。

## 6. API 设计

### 6.1 获取会话列表

`GET /api/v1/chat/sessions`

返回：

```json
{
  "items": [
    {
      "id": "session_xxx",
      "title": "新对话",
      "mode": "chat",
      "bound_file_id": "file_xxx",
      "created_at": "2026-07-29T00:00:00Z",
      "updated_at": "2026-07-29T00:00:00Z"
    }
  ]
}
```

### 6.2 创建会话

`POST /api/v1/chat/sessions`

请求：

```json
{
  "title": "新对话",
  "mode": "chat"
}
```

返回单个 session。

### 6.3 删除会话

`DELETE /api/v1/chat/sessions/{session_id}`

返回：

```json
{
  "session_id": "session_xxx",
  "deleted": true,
  "message_count_deleted": 6
}
```

### 6.4 获取会话消息

`GET /api/v1/chat/sessions/{session_id}/messages`

返回：

```json
{
  "session_id": "session_xxx",
  "items": [
    {
      "id": "message_xxx",
      "role": "user",
      "content": "这份文档讲了什么？",
      "metadata": null,
      "created_at": "2026-07-29T00:00:00Z"
    }
  ]
}
```

### 6.5 绑定会话文件

`PATCH /api/v1/chat/sessions/{session_id}/file`

请求：

```json
{
  "file_id": "file_xxx"
}
```

说明：

- 只允许绑定一个文件。
- 建议后端检查文件存在且状态为 `indexed`。
- 传入 `null` 可解除绑定。

### 6.6 普通聊天增加 session_id

`POST /api/v1/chat`

请求增加可选字段：

```json
{
  "message": "你好",
  "session_id": "session_xxx"
}
```

兼容原则：

- `session_id` 为空时，保持现有普通聊天行为。
- `session_id` 存在时，后端保存 user 和 assistant 消息。
- 不改变 `ChatService.answer(message)` 的核心职责。

### 6.7 RAG 问答增加 session_id

`POST /api/v1/files/{file_id}/ask`

请求增加可选字段：

```json
{
  "query": "这份文档的核心结论是什么？",
  "top_k": 3,
  "session_id": "session_xxx"
}
```

兼容原则：

- `session_id` 为空时，保持现有文件问答行为。
- `session_id` 存在时，后端保存 user 和 assistant 消息。
- assistant 消息的 `metadata_json` 保存 `rag_file_id`、`rag_file_name`、`used_chunks`。

## 7. 普通聊天消息保存流程

调用链：

```text
Frontend ChatInput
-> POST /api/v1/chat
-> API Router
-> ConversationService.answer_and_persist_chat()
-> ChatService.answer()
-> LLMService
-> LLMProvider
-> ConversationService 保存 user message
-> ConversationService 保存 assistant message
-> 返回 answer
```

流程说明：

1. 前端发送 `{ message, session_id }`。
2. 如果没有 session，前端先创建默认会话。
3. API 层判断存在 `session_id` 时走 `ConversationService`。
4. `ConversationService` 调用现有 `ChatService` 获取回答。
5. 回答成功后，保存用户消息和 AI 消息。
6. 更新会话 `updated_at`。
7. 返回原有聊天响应结构，尽量减少前端改动。

失败处理：

- 如果 LLM 调用失败，不保存 assistant 消息。
- 是否保存 user 消息建议保守处理：本阶段先不保存失败请求，避免历史记录出现无回答孤立消息。
- 如果消息保存失败，应返回明确错误，不伪装成聊天成功。

## 8. RAG 消息保存流程

调用链：

```text
Frontend ChatInput 或 FileCenter
-> POST /api/v1/files/{file_id}/ask
-> API Router
-> ConversationService.ask_file_and_persist()
-> RagService.ask_file()
-> RetrievalService.retrieve()
-> VectorStoreService.load_file_vectors()
-> EmbeddingService embed query
-> LLMProvider
-> ConversationService 保存 user message
-> ConversationService 保存 assistant message + metadata_json
-> 返回 answer + used_chunks
```

流程说明：

1. 前端在当前会话存在 `bound_file_id` 时，继续调用现有 RAG API。
2. 请求中带上 `session_id`。
3. `RagService` 仍只负责 retrieval、prompt 组装和 LLM 调用。
4. `ConversationService` 在 RAG 成功后保存两条消息。
5. assistant 消息 metadata 中保存引用片段。
6. 前端刷新后从消息 metadata 恢复“参考片段”展示。

失败处理：

- 检索失败、索引不存在、LLM 失败时不保存 assistant 消息。
- 文件未 indexed 时返回明确错误，前端提示重新处理文件。
- metadata 序列化失败应视为服务端错误，不影响原始 RAG 主链路设计，但不能静默丢失引用。

## 9. 会话文件绑定与清除流程

### 9.1 绑定流程

聊天侧文件自动处理完成后：

```text
Frontend ingestFile()
-> 文件 indexed
-> PATCH /api/v1/chat/sessions/{session_id}/file
-> ConversationService.bind_file()
-> ChatRepository.update_bound_file()
-> 前端更新 activeRagFile
```

规则：

- 当前会话只能绑定最近一个 indexed 文件。
- 新文件 indexed 后覆盖旧绑定。
- 绑定文件前，后端应检查 `files` 表中该文件存在。
- 建议检查 `status == indexed`，避免绑定未完成处理的文件。

### 9.2 清除流程

文件删除时：

```text
DELETE /api/v1/files/{file_id}
-> FileService.delete_file()
-> 删除原始文件
-> 删除 vector_store JSON
-> 删除 files 表记录
-> ConversationService 或 ChatRepository 清除 bound_file_id
```

工程选择：

- 推荐由 `FileService` 调用 `ChatRepository.clear_bound_file(file_id)`。
- 这样删除文件的业务编排仍集中在 `FileService`，数据库细节仍在 Repository。
- 后续如果引入用户或权限，可以再把文件删除扩展成更完整的事务编排服务。

## 10. 前端恢复流程

页面加载后：

```text
App / ChatStore 初始化
-> GET /api/v1/chat/sessions
-> 如果无会话：POST /api/v1/chat/sessions 创建“新对话”
-> 设置 currentSessionId
-> GET /api/v1/chat/sessions/{session_id}/messages
-> 渲染历史消息
-> 如果 session.bound_file_id 存在：
   -> 从 fileStore 文件列表中查找
   -> 设置 activeRagFile
```

切换会话时：

```text
点击侧边栏会话
-> 设置 currentSessionId
-> GET /messages
-> 恢复 messages
-> 根据 bound_file_id 恢复当前 RAG 文件提示
```

注意：

- 前端仍然可以保留 Zustand，但它应从“唯一数据源”变成“页面缓存”。
- 后端数据库成为会话和消息的真实来源。
- 文件中心仍由 `GET /api/v1/files` 恢复文件状态。

## 13. 分阶段开发顺序

### Phase 1：数据库表与 Repository

目标：

- 新增 `chat_sessions` 表。
- 新增 `chat_messages` 表。
- 新增 `ChatRepository`。
- 提供最小 CRUD 能力。

验收：

- 后端启动时自动创建新表。
- 可以通过临时脚本或 API 层调用创建会话、创建消息、查询消息。
- 不影响现有文件上传、RAG 和聊天接口。

### Phase 2：会话 API

目标：

- 新增会话列表、创建会话、删除会话、获取消息、绑定文件 API。

验收：

- `GET /api/v1/chat/sessions` 可返回列表。
- `POST /api/v1/chat/sessions` 可创建默认会话。
- `DELETE /api/v1/chat/sessions/{session_id}` 可删除会话和消息。
- `GET /api/v1/chat/sessions/{session_id}/messages` 可恢复消息。
- `PATCH /api/v1/chat/sessions/{session_id}/file` 可绑定或清除文件。

### Phase 3：普通聊天持久化

目标：

- `POST /api/v1/chat` 支持可选 `session_id`。
- 有 `session_id` 时保存 user 和 assistant 消息。

验收：

- 普通聊天成功后，刷新页面可恢复消息。
- 无 `session_id` 的旧调用仍可工作。
- LLM Provider、ChatService 主职责不变。

### Phase 4：RAG 问答持久化

目标：

- `POST /api/v1/files/{file_id}/ask` 支持可选 `session_id`。
- RAG 回答保存 `used_chunks` metadata。

验收：

- 文件问答成功后，刷新页面可恢复回答和参考片段。
- 文件中心原问答入口仍可用。
- 聊天侧 RAG 问答仍复用现有 RAG API。

### Phase 5：前端恢复与绑定

目标：

- 前端启动时加载会话。
- 无会话时自动创建默认“新对话”。
- 切换会话恢复消息。
- 当前会话恢复绑定文件。
- 文件删除后清除绑定。

验收：

- 刷新页面后会话列表仍存在。
- 切换会话可以看到不同历史消息。
- 当前会话绑定文件刷新后仍显示。
- 删除绑定文件后，该会话不再进入 RAG 问答模式。

## 14. 每阶段验收标准

整体 v1.2.0 验收标准：

- 后端编译检查通过：`python -m compileall app`。
- 前端类型检查通过：`npm exec tsc -- --noEmit`。
- 创建新会话成功。
- 删除会话成功，并同步删除消息。
- 普通聊天后刷新页面，消息仍存在。
- 聊天侧上传并 indexed 文件后，当前会话绑定文件。
- 刷新页面后，当前会话可以恢复绑定文件。
- RAG 问答后刷新页面，回答和参考片段仍存在。
- 删除文件后，所有绑定该文件的会话都被清除绑定。
- 现有文件上传、自动处理、删除、RAG 主链路不回退。

## 15. 错误处理方案

建议新增错误类型：

- `ChatSessionNotFoundError`
  - 会话不存在。

- `ChatMessageStorageError`
  - 消息保存失败。

- `ChatSessionStorageError`
  - 会话创建、更新、删除失败。

- `ChatFileBindingError`
  - 绑定文件不存在、未 indexed 或绑定失败。

处理原则：

- API 层只捕获已定义业务异常并返回统一 JSON。
- Repository 层遇到数据库异常时抛出稳定业务错误。
- Service 层不吞掉 LLM、RAG、数据库原始失败语义。
- 前端展示用户可理解的提示，例如“会话恢复失败，请刷新重试”。

## 17. 风险和技术债

1. 无 migration 系统。
   本阶段仍依赖 SQLAlchemy `create_all` 创建表。开发期简单，但后续字段变更会不方便。进入更正式版本前应考虑 Alembic。

2. SQLite 并发能力有限。
   单人本地 MVP 足够，多用户和高并发时应迁移 PostgreSQL。

3. 消息历史不等于 LLM 上下文。
   即使消息保存了，发送新问题时也不会自动把所有历史消息传给 LLM。上下文策略需要后续单独设计。

4. metadata_json 缺少强类型数据库约束。
   SQLite Text 简单可靠，但字段结构变更需要应用层兼容。

5. 文件删除与会话绑定清除不是完整分布式事务。
   当前只在单进程 SQLite + 本地文件系统中可接受。后续对象存储、异步任务或多用户场景需要更严格事务设计。

6. 会话标题生成暂时简单。
   可以先默认“新对话”或截取首条用户消息，暂不调用 LLM 生成标题。

## 18. 持久化与 LLM 上下文记忆的区别

会话持久化解决的是：

- 消息保存在哪里。
- 刷新页面后能否恢复。
- 切换会话后能否看到历史记录。
- RAG 引用片段能否再次展示。

LLM 上下文记忆解决的是：

- 模型回答时是否能看到历史消息。
- 要带多少历史消息。
- 超长历史如何截断、摘要或检索。
- 哪些历史信息应该进入 prompt。

v1.2.0 只做前者。

后续如果要提升“智能程度”，可以在会话持久化稳定后进入：

- v1.3：基础上下文窗口，发送最近 N 轮历史消息给 LLM。
- v1.4：会话摘要，长对话压缩成 summary。
- v1.5：历史消息检索，将历史消息 embedding 后用于语义召回。

这样推进更稳，因为没有持久化就谈不上可靠的历史上下文。
