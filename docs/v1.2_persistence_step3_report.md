# v1.2.3 普通聊天与 RAG 问答消息持久化报告

## 1. 工程效果

v1.2.3 将普通聊天和单文件 RAG 问答接入 `chat_messages`。

完成后：

- `POST /api/v1/chat` 支持可选 `session_id`。
- 有 `session_id` 时，普通聊天成功后会保存 user 和 assistant 两条消息。
- 无 `session_id` 时，普通聊天保持旧行为，不写入数据库。
- `POST /api/v1/files/{file_id}/ask` 支持可选 `session_id`。
- 有 `session_id` 时，RAG 问答成功后会保存 user query 和 assistant answer。
- RAG assistant 消息会在 `metadata_json` 中保存引用片段等信息。
- 无 `session_id` 时，RAG 问答保持旧行为，不写入数据库。

本阶段没有修改前端，没有改变 Retrieval、RAG prompt 或 LLM Provider 主链路。

## 2. 修改文件职责

### `backend/app/schemas/chat.py`

`ChatRequest` 新增可选 `session_id`。

这让同一个聊天 API 同时兼容：

- 旧调用：只传 `message`，不持久化。
- 新调用：传 `message + session_id`，回答后持久化消息。

### `backend/app/schemas/file.py`

`AskFileRequest` 新增可选 `session_id`。

这让文件问答 API 同时兼容：

- 旧调用：只传 `query/top_k`，不持久化。
- 新调用：传 `query/top_k/session_id`，回答后持久化 RAG 消息。

### `backend/app/services/conversation_service.py`

新增：

- `answer_and_persist_chat()`：调用现有 `ChatService.answer()`，成功后保存普通聊天消息。
- `ask_file_and_persist()`：调用现有 `RagService.ask_file()`，成功后保存 RAG 问答消息。
- `_save_message()`：内部消息保存方法。
- `_build_rag_metadata()`：组装 RAG assistant 消息 metadata。
- `_dump_metadata()`：将 metadata 转成 JSON 字符串。
- `_sum_token_count()`：从 `usage` 中计算简单 token 总数。

`ConversationService` 负责业务编排，`ChatService` 和 `RagService` 仍不直接操作 ORM。

### `backend/app/api/v1/chat.py`

`POST /chat` 根据 `session_id` 选择调用路径：

- 无 `session_id`：继续调用 `ChatService().answer()`。
- 有 `session_id`：调用 `ConversationService().answer_and_persist_chat()`。

由于该 router 同时挂载到 `/chat` 和 `/api/v1/chat`，正式业务路径 `/api/v1/chat` 已支持会话消息持久化。

### `backend/app/api/v1/files.py`

`POST /files/{file_id}/ask` 根据 `session_id` 选择调用路径：

- 无 `session_id`：继续调用 `RagService().ask_file()`。
- 有 `session_id`：调用 `ConversationService().ask_file_and_persist()`。

### `docs/status.md`

同步当前版本到 v1.2.3，并明确普通聊天/RAG 消息落库已完成，前端刷新恢复仍未接入。

## 3. 普通聊天消息保存调用链

```text
POST /api/v1/chat
-> ChatRequest(message, session_id)
-> API 判断 session_id 存在
-> ConversationService.answer_and_persist_chat()
-> ChatService.answer()
-> LLMService
-> LLMProvider
-> ChatRepository.create_message(role="user")
-> ChatRepository.create_message(role="assistant")
-> 返回原 ChatResponse 结构
```

保存结果：

- user 消息保存用户输入。
- assistant 消息保存模型回答。
- assistant metadata 中保存 `token_count`。

## 4. RAG 问答消息保存调用链

```text
POST /api/v1/files/{file_id}/ask
-> AskFileRequest(query, top_k, session_id)
-> API 判断 session_id 存在
-> ConversationService.ask_file_and_persist()
-> RagService.ask_file()
-> RetrievalService.retrieve()
-> VectorStoreService
-> LLMProvider
-> ChatRepository.create_message(role="user")
-> ChatRepository.create_message(role="assistant", metadata_json=...)
-> 返回原 AskFileResponse 结构
```

保存结果：

- user 消息保存用户问题。
- assistant 消息保存 RAG 回答。
- assistant metadata 保存 RAG 引用信息。

## 5. metadata_json 保存内容

普通聊天 assistant metadata：

```json
{
  "token_count": 123
}
```

RAG assistant metadata：

```json
{
  "rag_file_id": "file_xxx",
  "rag_file_name": "example.pdf",
  "used_chunks": [
    {
      "chunk_id": "chunk_xxx",
      "chunk_index": 0,
      "content": "引用片段内容",
      "char_count": 128,
      "score": 0.82
    }
  ],
  "token_count": 456
}
```

## 6. 为什么前端暂不接入

本阶段只验证后端持久化路径。

前端接入会同时改变：

- 会话列表来源。
- 当前会话 ID 管理。
- 消息发送请求体。
- 历史消息恢复。
- RAG 绑定文件恢复。

这些属于下一阶段 v1.2.4 的范围。先把后端消息写入跑通，可以降低前端接入时的排查难度。

## 7. 这一步和 LLM 记忆的区别

本阶段实现的是“消息保存”，不是“模型记忆”。

现在数据库会保存历史消息，但新的 LLM 请求仍不会自动携带历史消息。也就是说：

- 刷新后可以恢复历史记录，是持久化能力。
- 模型回答时参考历史上下文，是上下文管理能力。
- 长期记忆或历史语义检索，是更后面的能力。

后续可以在前端恢复和消息持久化稳定后，再设计最近 N 轮上下文、会话摘要或历史消息检索。

- `POST /api/v1/chat` 携带 `session_id` 后保存 user 和 assistant。
- 不带 `session_id` 调用普通聊天，保持旧行为且不写入消息。

## 9. 当前剩余问题

- 前端尚未传递 `session_id`。
- 前端刷新后尚未恢复会话列表和消息。
- 当前会话绑定文件的前端恢复尚未接入。
- 新请求仍不会自动携带历史上下文给 LLM。
- 仍未引入 migration 系统。
