# v1.7.3 Backend Baseline Tests 规划

## 1. 当前状态

当前项目已完成 v1.7.2 Runtime Backup and Restore。

后端已经具备较完整的 MVP 能力：

- FastAPI API 层。
- Service 层。
- Repository 层。
- SQLite + SQLAlchemy。
- 文件上传、解析、切块、embedding、vector-store、retrieval、RAG。
- 会话和消息持久化。
- 邀请码访问保护。
- 匿名 `client_id` 隔离。
- `/health` 和 `/health/config`。
- request_id 日志。

但当前后端仍缺少系统化自动化测试。

目前主要依赖：

- 手动浏览器验证。
- PowerShell smoke test。
- `python -m compileall app`。
- 前端 `npm exec tsc -- --noEmit`。

这些检查能发现启动和类型问题，但不能稳定保护 Repository、Service、访问控制和 client_id 隔离等业务规则。

## 2. 为什么 v1.7.3 要做后端基础测试

项目已经进入公网小范围试用阶段，后续任何小改动都可能影响真实使用。

最容易出现回归的地方：

1. 邀请码保护失效。
2. `client_id` 隔离失效。
3. 文件列表泄露其他客户端数据。
4. 会话列表泄露其他客户端数据。
5. 文件删除误删其他客户端文件。
6. 会话消息恢复异常。
7. `/health/config` 暴露敏感配置。
8. 修改数据库模型后本地启动或测试污染真实数据。

因此，v1.7.3 应建立一组最小后端测试，用来保护当前最关键的稳定性和安全边界。

## 3. 测试目标

v1.7.3 的目标不是追求高覆盖率，而是建立后端测试骨架和关键链路保护。

测试应覆盖：

- 健康检查。
- 非敏感配置检查。
- 访问保护。
- 匿名 `client_id` 请求头。
- 文件 API 基础隔离。
- 会话 API 基础隔离。
- 消息持久化基础行为。

测试暂不覆盖：

- 真实 LLM API。
- 真实 embedding API。
- 大文件解析性能。
- Nginx。
- systemd。
- 真实公网部署。

## 4. 测试依赖选择

建议新增后端测试依赖：

```text
pytest
httpx
```

原因：

- FastAPI 官方测试客户端依赖 httpx。
- pytest 是 Python 后端最常见的轻量测试框架。
- 不引入复杂测试平台。
- 不引入数据库迁移系统。

是否新增 requirements 文件：

MVP 阶段有两个选择：

1. 直接加入 `backend/requirements.txt`
2. 新增 `backend/requirements-dev.txt`

推荐：

**新增 `backend/requirements-dev.txt`。**

原因：

- 生产部署不一定需要 pytest。
- 测试依赖和运行依赖分离更清晰。
- 不影响当前 VPS 生产依赖安装。

`backend/requirements-dev.txt` 可包含：

```text
-r requirements.txt
pytest
httpx
```

## 5. 测试数据和环境设计

### 5.1 不污染真实数据

测试必须避免使用：

- `backend/data/beichen.db`
- `backend/uploads/`
- `backend/vector_store/`
- 生产 `/opt/beichen-agent/runtime/`

测试应使用临时目录：

- 临时 SQLite 文件。
- 临时 uploads 目录。
- 临时 vector_store 目录。

### 5.2 配置覆盖策略

当前后端 settings 在导入时读取 `.env`，测试需要谨慎处理。

建议方案：

- 在测试 fixture 中创建临时目录。
- 使用 monkeypatch 覆盖环境变量。
- 尽量在导入 app 前准备测试环境。
- 如果现有 settings 不易重载，先优先测试 Repository 和 Service 的纯逻辑，再逐步覆盖 API。

更稳的后续方向：

- 让 settings 支持显式 reload。
- 或给 app 创建工厂函数 `create_app()`。

但 v1.7.3 暂不强制做大重构。

### 5.3 Provider 策略

测试中默认使用：

```env
LLM_PROVIDER=mock
EMBEDDING_PROVIDER=mock
APP_INVITE_CODES=111111
APP_ACCESS_HEADER=X-Beichen-Access
```

不要在测试中调用真实外部 LLM 或 embedding API。

## 6. 建议新增文件

### 6.1 `backend/requirements-dev.txt`

职责：

- 管理开发和测试依赖。
- 引入 pytest 和 httpx。
- 不影响生产最小依赖。

### 6.2 `backend/tests/conftest.py`

职责：

- 创建测试临时目录。
- 准备测试 SQLite。
- 准备测试 uploads 和 vector_store。
- 提供 FastAPI TestClient。
- 提供默认 headers：
  - `X-Beichen-Access`
  - `X-Beichen-Client-Id`

### 6.3 `backend/tests/test_health.py`

职责：

- 测试 `/health`。
- 测试 `/health/config`。
- 确认 `/health/config` 不返回 API Key、邀请码原文、文件内容、chunks 或 embeddings。

### 6.4 `backend/tests/test_access_control.py`

职责：

- 测试缺少邀请码时 `/api/v1/*` 被拒绝。
- 测试错误邀请码被拒绝。
- 测试正确邀请码可访问。
- 测试 `/health` 不需要邀请码。

### 6.5 `backend/tests/test_client_context.py`

职责：

- 测试缺少 `X-Beichen-Client-Id` 时的行为。
- 测试非法 client_id 被拒绝。
- 测试合法 client_id 可以进入业务 API。

### 6.6 `backend/tests/test_file_isolation.py`

职责：

- client A 上传文件后，client A 可在列表看到。
- client B 不应看到 client A 的文件。
- client B 不能删除 client A 的文件。

### 6.7 `backend/tests/test_session_isolation.py`

职责：

- client A 创建会话后，client A 可看到。
- client B 不应看到 client A 的会话。
- client B 不能读取 client A 的消息。
- 删除会话只影响当前 client_id。

## 7. API 测试范围

优先测试 API：

```text
GET /health
GET /health/config
GET /api/v1/files
POST /api/v1/files
DELETE /api/v1/files/{file_id}
GET /api/v1/chat/sessions
POST /api/v1/chat/sessions
DELETE /api/v1/chat/sessions/{session_id}
GET /api/v1/chat/sessions/{session_id}/messages
```

暂缓测试：

```text
POST /api/v1/files/{file_id}/parse
POST /api/v1/files/{file_id}/chunks
POST /api/v1/files/{file_id}/embeddings
POST /api/v1/files/{file_id}/vector-store
POST /api/v1/files/{file_id}/ask
```

原因：

- 这些链路更长，容易引入外部 Provider 或文件解析依赖。
- v1.7.3 首先保护访问、隔离、持久化和基础生命周期。
- RAG 链路后续可在 v1.7.4 或独立阶段补集成测试。

## 8. Repository / Service 测试范围

如果 API 测试受 settings 初始化影响较大，可以先补 Repository 和 Service 测试。

优先测试：

- `FileRepository`
- `ChatRepository`
- `ConversationService` 会话创建、列表、绑定文件校验。

测试重点：

- 查询必须按 `client_id` 过滤。
- 更新必须按 `client_id` 校验归属。
- 删除不能跨 client_id。

## 9. 运行方式

新增测试后，建议在本地运行：

```powershell
cd backend
pip install -r requirements-dev.txt
pytest
```

也可以先运行单个文件：

```powershell
pytest tests/test_health.py
```

后续部署前检查顺序：

```powershell
python -m compileall app
pytest
cd ../frontend
npm exec tsc -- --noEmit
```

## 10. 风险和技术债

### 10.1 当前可能遇到的风险

1. settings 在导入时读取 `.env`，测试配置隔离可能不够优雅。
2. app 是全局实例，不是 `create_app()` 工厂函数，测试环境切换不够灵活。
3. 数据库初始化可能默认指向本地真实 SQLite。
4. 访问控制 middleware 会影响 API 测试准备。

### 10.2 MVP 处理策略

本阶段不强制重构为 app factory。

优先策略：

- 使用 monkeypatch 和临时目录。
- 尽量在测试导入前设置环境。
- 如果部分 API 测试受限，先用 Repository / Service 测试覆盖核心规则。

### 10.3 后续可优化方向

未来可考虑：

- `create_app(settings)` 应用工厂。
- 测试专用 settings。
- Alembic migration。
- PostgreSQL 测试容器。
- RAG 集成测试。

## 11. 不做范围

v1.7.3 不做：

- 不新增 AI 功能。
- 不修改 RAG 主链路。
- 不修改数据库结构。
- 不调用真实 LLM。
- 不调用真实 embedding。
- 不引入 Docker。
- 不引入 CI/CD。
- 不做浏览器自动化测试。
- 不追求完整覆盖率。

## 12. 验收标准

v1.7.3 完成后应满足：

1. 新增后端测试依赖说明。
2. 可运行 `pytest`。
3. `/health` 和 `/health/config` 测试通过。
4. 访问保护测试通过。
5. client_id 基础校验测试通过。
6. 文件列表或文件删除隔离测试通过。
7. 会话列表或会话消息隔离测试通过。
8. 测试不污染真实 SQLite、uploads、vector_store。
9. `python -m compileall app` 通过。
10. `npm exec tsc -- --noEmit` 通过。
11. `git status` 不包含真实数据库、uploads、vector_store、logs 或敏感配置。
