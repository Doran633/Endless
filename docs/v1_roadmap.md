# v1.0 开发路线

> 本路线基于第一次 Git commit 之后的当前代码状态。
> 项目目标已调整：v1.0 先开发一个独立网页版 AI 助手，不接入企业系统。
> 本文档只做路线规划，不修改代码。

## 1. 当前状态

当前项目已经完成第一次 Git commit，处于 **前端 Mock 原型 + 最小后端聊天骨架** 阶段。

已完成：

- 前端已存在 React + TypeScript + Vite + Ant Design + Zustand 工程。
- 前端已有登录页、聊天页、文件中心、PPT 任务中心等原型页面。
- 前端聊天、文件、PPT 仍然是本地 Mock 数据。
- 后端已创建 FastAPI 基础结构。
- 后端已实现 `GET /health`。
- 后端已实现基础聊天接口：
  - `POST /chat`
  - `POST /api/v1/chat`
- 后端已抽象出基础 LLM Provider：
  - `MockLLMProvider`
  - `OpenAIProvider`
- 已有后端设计文档、聊天模块说明和代码审查报告。

当前限制：

- 前端尚未调用后端聊天接口。
- 没有真实会话存储。
- 没有数据库。
- 没有文件真实上传。
- 没有文档解析。
- 没有 embedding。
- 没有向量检索。
- 没有 RAG 问答。
- 没有统一错误处理和自动化测试。

当前不再作为 v1.0 目标的内容：

- 钉钉登录。
- 企业权限。
- 多租户。
- 微服务。
- 复杂任务队列。
- PPT 生成。

## 2. 目标状态

v1.0 目标是交付一个可本地运行、可演示、可继续扩展的独立网页版 AI 助手。

v1.0 必须支持：

1. Web 聊天。
2. LLM API 调用。
3. 文件上传。
4. 文档解析。
5. RAG 问答。

v1.0 暂不支持：

1. 钉钉登录。
2. 企业权限。
3. 多租户。
4. 微服务。
5. 复杂任务队列。

目标用户体验：

```text
打开网页
  -> 进入聊天界面
  -> 发送普通问题
  -> 后端调用 LLM 返回回答
  -> 上传文档
  -> 系统解析文档
  -> 用户围绕文档提问
  -> 后端基于 RAG 返回回答
```

v1.0 最小验收闭环：

- 用户可以在网页上发送消息并看到 LLM 回复。
- 用户可以上传 TXT/PDF/DOCX 中至少一种文档格式，推荐首期先从 TXT/PDF 开始。
- 后端可以解析文档文本。
- 后端可以对文档进行 chunk、embedding、向量检索。
- 用户可以针对上传文件进行问答。
- 普通聊天和文件问答在 UI 上有清晰区分。

## 3. 开发阶段

### 阶段一：前端接入后端聊天

目标：

- 让当前 Web 聊天界面真正调用 FastAPI 后端。

范围：

- 新增前端 `chatApi`。
- 将 `chatStore.sendMessage()` 从 Mock 回复切换到 `POST /api/v1/chat`。
- 保留 Mock 数据作为开发 fallback，但默认路径走后端。
- 补充聊天错误提示。
- 保持当前 UI 不大改。

验收标准：

- 前端输入一条消息后，请求到达 FastAPI。
- 后端返回 `{ code, message, data.answer }`。
- 前端展示后端返回的 answer。
- 后端关闭或请求失败时，前端有明确错误提示。
- 现有前端类型检查通过。

### 阶段二：LLM API 调用稳定化

目标：

- 将后端聊天从 Mock Provider 切换为可配置的真实 LLM API 调用。

范围：

- 明确 `LLM_PROVIDER` 配置。
- 完善 OpenAI-compatible Provider。
- 增加 provider 配置错误的快速失败。
- 增加统一 LLM 错误处理。
- 增加 timeout 配置。
- 增加基础调用日志，不记录完整敏感内容。

验收标准：

- 配置 `LLM_PROVIDER=openai` 和 `OPENAI_API_KEY` 后，可以得到真实 LLM 回复。
- 未配置 API Key 时，系统给出明确错误或自动使用开发 Mock，行为必须可预期。
- LLM 请求失败不会返回未处理的 500 堆栈。
- 后端仍支持 Mock Provider 进行本地无网络开发。

### 阶段三：文件上传模块

目标：

- 实现独立 AI 助手的文件上传能力。

范围：

- 后端新增文件上传接口。
- 前端文件中心接入真实上传接口。
- 本地文件系统保存原始文件。
- 建立最小文件元数据记录。
- v1.0 可以先用轻量本地存储或 SQLite，暂不强制 PostgreSQL。
- 限制文件大小和格式。

建议首批格式：

- TXT：必须支持。
- PDF：推荐支持。
- DOCX：可在阶段四补齐。

验收标准：

- 用户可以从网页上传文件。
- 后端保存文件。
- 前端可以看到文件列表和文件状态。
- 不支持格式会被拒绝。
- 超过大小限制的文件会被拒绝。
- 后端不向前端暴露内部存储路径。

### 阶段四：文档解析模块

目标：

- 将上传文件解析为可用于 RAG 的纯文本。

范围：

- 实现 Parser 抽象。
- 实现 TXT parser。
- 实现 PDF parser。
- 视进度实现 DOCX parser。
- 保存解析结果和解析状态。
- 解析失败时展示明确原因。

验收标准：

- 上传 TXT 后可以解析出文本。
- 上传文本型 PDF 后可以解析出文本。
- 文件状态可以从 uploaded / processing 变为 ready / failed。
- 解析结果可以被后续 chunk 模块读取。

### 阶段五：Embedding 与向量索引

目标：

- 为 RAG 问答建立最小向量检索能力。

范围：

- 实现 chunk 切分。
- 实现 Embedding Provider 抽象。
- 接入一个 embedding 方案。
- 建立最小向量存储。
- 支持按文件范围检索相关 chunk。

推荐 v1.0 技术选择：

- 简单路线：SQLite / JSON 元数据 + 本地向量索引。
- 更接近生产路线：PostgreSQL + pgvector。
- 如果目标是最快跑通 v1.0，可先用本地轻量向量存储，再保留 `VectorStore` 抽象。

验收标准：

- 文档 ready 后可以生成 chunks。
- 每个 chunk 可以生成 embedding。
- 用户提问时可以检索到相关 chunks。
- 检索范围限定在当前文件。
- VectorStore 抽象不绑定具体向量库实现。

### 阶段六：RAG 问答闭环

目标：

- 用户可以围绕上传文档进行问答。

范围：

- Chat API 支持 `file_id`。
- ChatService 根据是否传入 `file_id` 区分普通聊天和文档问答。
- RAGService 负责检索上下文。
- LLMService 负责生成最终回答。
- 前端支持选择文件后提问。
- 回答中可展示简单来源信息。

验收标准：

- 用户选择一个已解析文件后可以提问。
- 后端按该文件检索 chunks。
- LLM 回答基于检索上下文。
- 没有上传文件时仍可以普通聊天。
- 文件未解析完成时不能进行 RAG 问答，并提示原因。

### 阶段七：v1.0 收敛与验收

目标：

- 将系统收敛为可演示的 v1.0。

范围：

- 补充关键错误处理。
- 补充最小自动化测试。
- 补充运行说明。
- 清理旧企业系统文案。
- 明确 v1.0 不包含钉钉、企业权限、多租户。
- 统一 API 文档和实际接口。

验收标准：

- 新开发者可以根据 README 或文档启动前后端。
- 普通聊天链路可用。
- 文件上传链路可用。
- 文档解析链路可用。
- RAG 问答链路可用。
- 前端没有依赖 Mock 才能演示核心能力。

## 4. 每阶段验收标准汇总

| 阶段 | 核心验收 |
| --- | --- |
| 阶段一 | 前端聊天真实调用后端 `/api/v1/chat` |
| 阶段二 | 后端可配置真实 LLM API，失败有明确错误 |
| 阶段三 | 用户可上传文件，前端可查看文件状态 |
| 阶段四 | 文件可解析为文本，失败状态可见 |
| 阶段五 | 文档可 chunk、embedding、向量检索 |
| 阶段六 | 用户可基于上传文档进行 RAG 问答 |
| 阶段七 | v1.0 可本地启动、可演示、文档一致 |

## 5. 技术风险

### 5.1 目标切换导致文档不一致

风险：

- 现有部分文档仍围绕企业内部 AI 助手、钉钉登录、权限隔离设计。
- v1.0 目标已经调整为独立网页版 AI 助手。

应对：

- `docs/v1_roadmap.md` 作为 v1.0 当前路线依据。
- 后续逐步更新 `requirements.md`、`api_design.md`、`backend_design.md` 中与企业系统强绑定的内容。

### 5.2 前端 Mock 状态切换风险

风险：

- 当前前端聊天、文件、PPT 都依赖 Mock store。
- 直接切换真实 API 可能导致状态管理混乱。

应对：

- 分模块替换：chat -> files -> rag。
- 保留现有 UI，优先替换数据来源。
- Mock 仅作为开发 fallback，不作为主路径。

### 5.3 LLM API 稳定性风险

风险：

- API Key、网络、模型响应格式、超时都可能导致调用失败。

应对：

- 保留 Mock Provider。
- 增加 timeout。
- 增加统一错误处理。
- 不在前端暴露 API Key。

### 5.4 文档解析质量风险

风险：

- PDF 解析质量不稳定。
- 扫描件 PDF 可能无法解析。
- DOCX 格式差异可能导致解析失败。

应对：

- v1.0 先明确支持文本型文档。
- TXT 优先，PDF 其次，DOCX 可后置。
- OCR 不进入 v1.0。

### 5.5 Embedding 与向量库选型风险

风险：

- PostgreSQL + pgvector 更接近生产，但初始化成本较高。
- 本地轻量向量存储开发快，但未来迁移成本较高。

应对：

- 无论选择哪种实现，都先抽象 `EmbeddingProvider` 和 `VectorStore`。
- v1.0 不做多向量库支持，只保留替换边界。

### 5.6 RAG 效果风险

风险：

- chunk 大小、检索数量、prompt 拼接都会影响回答质量。

应对：

- 先固定一套简单策略。
- 保留 chunk 来源 metadata。
- 回答中展示简单引用，便于调试。

### 5.7 过早引入复杂架构风险

风险：

- 过早引入登录、权限、多租户、微服务、复杂队列会拖慢 v1.0。

应对：

- v1.0 明确不做这些能力。
- 后端保持单体。
- 异步任务先用简单 BackgroundTasks 或同步流程。

## 6. v1.0 不做清单

v1.0 明确不做：

- 钉钉登录。
- 企业权限。
- 多租户。
- 微服务。
- 复杂任务队列。
- PPT 生成。
- Agent Workflow。
- 多模型选择 UI。
- 企业知识库。
- 多文件联合问答。
- OCR。
- 审计日志。

## 7. 推荐近期任务顺序

建议接下来按这个顺序推进：

1. 前端接入后端 `/api/v1/chat`。
2. 修正后端 Provider 选择和错误处理。
3. 加入最小后端测试。
4. 实现文件上传接口和前端真实上传。
5. 实现 TXT/PDF 解析。
6. 实现 chunk 和 embedding。
7. 实现 VectorStore 检索。
8. 将 ChatService 扩展为支持 `file_id` 的 RAG 问答。

这个顺序能最快把项目从“原型 + 骨架”推进到“可用 AI 助手 v1.0”。
