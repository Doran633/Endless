# v0.9.1 Chat-side RAG QA 体验优化计划

> 本计划用于 v0.9.1 开发阶段。目标是在不修改后端 RAG 主链路的前提下，让用户在聊天框上传文件后，可以直接在聊天窗口基于该文件提问并获得 RAG 回答。

## 1. 当前问题

v0.9.0 已经完成单文件 RAG 问答闭环：

```text
file_id + query
  -> RetrievalService.retrieve()
  -> top_k chunks
  -> RagService 组装 prompt
  -> LLMProvider
  -> answer + used_chunks
```

当前主要问题已经不在后端主链路，而在产品体验：

- 用户在聊天框上传文件后，文件可以自动完成上传、解析、切块、mock embedding 和本地索引保存。
- 但用户想基于该文件提问时，仍然需要进入“文件中心”点击“问答”。
- 聊天窗口没有明确绑定“当前可问答文件”。
- 普通聊天和文件问答在前端交互上仍是两个分离流程。
- 文件处理未完成时，用户如果直接提问，系统还不能给出清晰的等待或失败提示。

因此 v0.9.1 要解决的是：

```text
用户在聊天页上传文件
  -> 系统处理完成
  -> 用户直接在聊天输入框提问
  -> AI 在聊天消息流中回答
```

## 2. 产品体验判断

文档问答应该优先进入聊天窗口。

原因：

- 用户上传文件的自然目的通常是“马上围绕这个文件提问”。
- 聊天窗口是 AI 助手的主工作区，文件中心更适合作为管理和调试页面。
- 当前项目目标是独立网页版 AI 助手 MVP，而不是后台文件处理工具。
- v0.9.0 已经证明后端 RAG 链路可用，v0.9.1 正适合把能力接到主交互路径。

但 v0.9.1 不应升级为复杂知识库聊天。

本阶段只做：

```text
当前会话
  + 最近一个 indexed 文件
  + 用户问题
  -> 单文件 RAG 回答
```

暂不做：

- 多文件问答。
- 跨会话文件记忆。
- 历史对话检索。
- 数据库持久化。
- Agent 自动规划。
- 文件内容直接塞入普通聊天 prompt。

## 3. 技术方案

### 3.1 后端方案

优先复用现有 API：

```text
POST /api/v1/files
POST /api/v1/files/{file_id}/parse
POST /api/v1/files/{file_id}/chunks
POST /api/v1/files/{file_id}/embeddings
POST /api/v1/files/{file_id}/vector-store
POST /api/v1/files/{file_id}/ask
```

v0.9.1 不修改后端 RAG 主链路：

- 不改 `RagService` 的职责。
- 不改 `RetrievalService` 的职责。
- 不新增新的后端编排接口。
- 不引入数据库或队列。

如果实现中发现现有 `/ask` 响应字段不足，可以只做极小 schema 补充，但默认不需要。

### 3.2 前端方案

主要改动集中在聊天侧：

- `fileStore.ingestFile()` 继续负责上传和自动处理。
- 聊天页记录最近一个处理成功且 `status=indexed` 的文件。
- 用户发送消息时，判断当前会话是否存在可问答文件。
- 如果存在 indexed 文件，调用 `askFile(fileId, message, topK)`。
- 如果不存在 indexed 文件，保持原普通聊天调用。
- RAG 回答作为 assistant 消息进入消息流。
- assistant 消息 metadata 中保存引用 chunks 摘要。

建议调用选择逻辑：

```text
send message
  -> if currentRagFile.status === indexed
       call /api/v1/files/{file_id}/ask
     else
       call /api/v1/chat
```

## 4. 前端状态设计

建议扩展当前前端状态，而不是重建状态系统。

### 4.1 文件状态

当前已有：

```text
FileItem.status
FileIngestionState
fileStore.ingestFile()
```

建议新增或复用：

```ts
activeRagFileId?: string
activeRagFileName?: string
```

含义：

- 记录当前聊天会话最近一个 indexed 文件。
- 文件处理完成后自动设置。
- 文件处理失败时不设置。

### 4.2 聊天消息 metadata

当前消息已有：

```ts
metadata?: {
  chunk_ids?: string[];
  token_count?: number;
  cards?: MessageCard[];
}
```

建议扩展：

```ts
metadata?: {
  chunk_ids?: string[];
  token_count?: number;
  rag_file_id?: string;
  rag_file_name?: string;
  used_chunks?: {
    chunk_id: string;
    chunk_index: number;
    score: number;
    content_preview: string;
  }[];
  cards?: MessageCard[];
}
```

设计原因：

- 回答正文仍然作为普通 assistant message 展示。
- 引用 chunks 作为 metadata 展示摘要，不污染回答正文。
- 后续接数据库时可以直接持久化 message metadata。

### 4.3 状态提示

聊天区应该展示简洁状态：

```text
上传中
解析中
切块中
向量化中
建立索引中
已准备好，可以开始提问
```

如果用户在处理完成前提问：

```text
文件还在处理中，完成后可以基于该文件回答。
```

如果没有文件：

```text
保持普通聊天。
```

## 5. 聊天调用链路

### 5.1 上传文件

```text
ChatInput
  -> fileStore.ingestFile(file)
  -> POST /api/v1/files
  -> POST /api/v1/files/{file_id}/parse
  -> POST /api/v1/files/{file_id}/chunks
  -> POST /api/v1/files/{file_id}/embeddings
  -> POST /api/v1/files/{file_id}/vector-store
  -> set activeRagFileId
  -> UI 显示“文件已准备好”
```

### 5.2 基于文件提问

```text
ChatInput submit
  -> ChatStore.sendMessage()
  -> 判断 activeRagFileId 是否存在
  -> askFile(activeRagFileId, userMessage, topK)
  -> POST /api/v1/files/{file_id}/ask
  -> RagService
  -> RetrievalService
  -> LLMProvider
  -> AskFileResponse
  -> assistant message
  -> MessageRenderer 展示回答和引用 chunks
```

### 5.3 普通聊天

```text
ChatInput submit
  -> ChatStore.sendMessage()
  -> 无 activeRagFileId
  -> POST /api/v1/chat
  -> 普通 assistant message
```

## 6. 错误处理方案

### 6.1 文件上传失败

展示：

```text
文件上传失败，请检查文件格式和大小。
```

状态：

- 不设置 activeRagFileId。
- 文件可进入 failed 状态。

### 6.2 文档解析失败

展示：

```text
文档解析失败。当前仅支持 TXT、DOCX 和可复制文本型 PDF。
```

状态：

- 不设置 activeRagFileId。
- 提示用户可去文件中心查看详细状态。

### 6.3 索引失败

展示：

```text
文件索引失败，暂时不能基于该文件问答。
```

状态：

- 不设置 activeRagFileId。

### 6.4 文件处理未完成时提问

展示：

```text
文件还在处理中，请稍等片刻后再提问。
```

行为：

- 不调用 `/chat`。
- 不调用 `/ask`。
- 避免用户以为已经基于文件回答。

### 6.5 RAG 问答失败

可能原因：

- 本地 VectorStore 不存在。
- 检索结果为空。
- LLM 调用失败。
- `.env` 模型配置错误。

展示：

```text
基于文件回答失败，请稍后重试或到文件中心检查文件状态。
```

前端可保留用户问题，不丢失输入。

## 7. 风险和技术债

### 7.1 最近文件绑定可能不符合复杂场景

v0.9.1 只绑定最近一个 indexed 文件。

风险：

- 用户上传多个文件后，系统只会默认使用最后一个文件。
- 用户可能不清楚当前问题基于哪个文件。

缓解：

- 在聊天输入区附近展示当前文件名。
- 回答消息中展示 `基于：xxx`。
- 多文件选择留到后续版本。

### 7.2 前端状态刷新后丢失

当前没有数据库。

风险：

- 页面刷新后 activeRagFileId 丢失。
- 后端本地索引仍在，但前端不知道当前文件。

缓解：

- v0.9.1 接受。
- 后续数据库阶段统一恢复文件列表和会话状态。

### 7.3 Mock embedding 影响 RAG 质量

当前 embedding 仍是 mock。

风险：

- 检索到的 chunks 不一定语义相关。
- 文件问答答案质量可能不稳定。

缓解：

- v0.9.1 重点验证交互链路。
- v1.0 接真实 embedding。

### 7.4 普通聊天和文件问答切换需要清晰

风险：

- 用户不知道当前是在普通聊天还是文件问答。

缓解：

- 输入区展示当前模式。
- assistant 消息展示引用 chunks。
- 提供“清除当前文件”入口，恢复普通聊天。

### 7.5 不应提前引入 Agent

虽然体验像“自动处理文件”，但本阶段仍是确定性前端编排，不是 Agent。

原因：

- 步骤固定。
- 不需要 LLM 规划。
- 不需要工具注册和任务状态机。

## 8. 测试方案

### 8.1 基础验证

后端：

```text
cd backend
python -m compileall app
```

前端：

```text
cd frontend
npm exec tsc -- --noEmit
```

### 8.2 普通聊天回归

步骤：

1. 不上传文件。
2. 在聊天框输入普通问题。
3. 确认仍调用 `/api/v1/chat`。
4. 确认 AI 正常回答。

预期：

- 普通聊天不受 RAG 改动影响。

### 8.3 聊天侧文件 RAG

步骤：

1. 在聊天框上传 TXT / DOCX / PDF。
2. 等待自动处理完成。
3. 确认页面提示文件已准备好。
4. 在聊天框输入：

```text
这个文档主要讲了什么？
```

预期：

- 前端调用 `/api/v1/files/{file_id}/ask`。
- assistant 消息展示文件问答答案。
- 消息中展示引用 chunks 摘要。

### 8.4 处理中文档时提问

步骤：

1. 上传较大文件。
2. 在索引完成前立刻提问。

预期：

- 前端提示文件处理中。
- 不调用普通聊天伪装成文件回答。

### 8.5 文件中心回归

步骤：

1. 上传文件并完成索引。
2. 进入文件中心。
3. 点击“检索”。
4. 点击“问答”。

预期：

- 文件中心原有检索和问答入口仍可用。
- 文件状态仍能展示 indexed。

### 8.6 范围检查

确认本阶段没有引入：

- 数据库。
- pgvector。
- 多文件 RAG。
- 历史对话检索。
- Agent。
- 企业权限。
