# v1.8.3 Chunk Strategy Improvement 报告

## 1. 本阶段工程效果

本阶段优化了文本切块策略，让 RAG 的知识单元更接近文档真实结构。

新增能力：

- ChunkService 支持标题感知切块。
- 支持识别 Markdown 标题、中文章节标题和数字编号标题。
- `DocumentChunk` 增加 `section_title` 和 `section_path`。
- 本地 JSON VectorStore 保存 section metadata。
- RetrievalResult 返回 section metadata。
- 文件中心检索、文件问答和聊天侧引用片段可展示章节路径。
- 保留固定长度切块作为 fallback。

本阶段没有新增 AI 业务功能，没有修改数据库结构，没有引入 pgvector、rerank 或多文件 RAG。

## 3. 标题感知切块原理

原策略主要按字符长度切块：

```text
document text -> every chunk_size chars -> chunk
```

这种方式简单稳定，但容易把多个主题混在同一个 chunk 中。

新策略先识别标题：

```text
## Markdown 标题
一、中文章节标题
1. 数字编号标题
```

然后将标题和其下内容作为一个 section，再对 section 生成 chunk。

如果 section 超过 `CHUNK_SIZE`，会在该 section 内继续使用固定长度切块，并保留相同的 `section_title` 和 `section_path`。

如果文档没有明显标题，则继续使用原固定长度切块，避免无结构文档处理失败。

## 4. chunk metadata 如何帮助后续检索

`section_title` 和 `section_path` 暂时不改变 cosine similarity 的主检索算法，但它们带来三个价值：

1. 前端可以展示引用片段来自哪个章节，便于人工判断噪声来源。
2. 后续可以根据章节类型做轻量检索加权。
3. 后续可以支持 overview 问题优先检索章节摘要或功能章节。

例如：

```text
当前已完成功能 > 文件上传与自动处理
```

会比单纯的 `Chunk 3` 更容易判断该片段是否真的支撑答案。

## 5. 为什么这一步不做 rerank

当前主要问题是 chunk 本身主题混杂。如果直接引入 rerank，会增加外部模型依赖、成本和延迟，但仍然是在混杂 chunk 中重新排序。

本阶段优先让知识单元更干净，再进入检索排序优化。这个顺序更符合 MVP 的复杂度控制原则。

## 6. 如何重新索引文件测试效果

测试步骤：

1. 部署或本地启动最新代码。
2. 删除旧测试文件，或重新上传同一份测试文档。
3. 等待自动完成解析、切块、embedding 和 vector-store。
4. 在文件中心使用相同问题进行 RAG 问答。
5. 对比 v1.8.2 和 v1.8.3：
   - 正确依据是否更靠前。
   - 噪声片段是否减少。
   - `section_path` 是否显示在正确章节。
   - Citation Score 是否提升。

注意：旧文件已有的 vector_store 不会自动获得新的 section metadata，必须重新索引。
