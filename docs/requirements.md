# 独立网页版 AI 助手 MVP 需求说明

> 本文档定义当前 v1.0 的产品需求范围。
> 当前项目定位已经调整为独立网页版 AI 助手 MVP。
> 本文档只描述当前 MVP 和明确的规划能力，不记录历史企业系统计划。

## 1. 项目定位

本项目是一个独立网页版 AI 助手 MVP。

目标不是一次性建设完整 AI 平台，而是优先跑通用户在浏览器中使用 AI 的核心闭环：

1. 用户进入 Web 页面。
2. 用户进行普通 AI 聊天。
3. 用户上传文档。
4. 系统解析文档内容。
5. 用户基于文档内容进行 RAG 知识问答。

当前 v1.0 强调：

- MVP 优先。
- 保持代码简单。
- 先完成可用闭环。
- 不提前引入企业系统复杂度。
- 为后续 AI 数据分析和 Agent 能力保留扩展边界。

## 2. MVP 范围

### 2.1 一期必须实现的核心能力

一期必须完成以下能力：

- AI 聊天。
- 文件上传。
- RAG 知识问答。

文档解析、chunk、Embedding 和向量检索是 RAG 知识问答的支撑能力，必须围绕单文件 RAG 闭环实现，不单独扩大为通用知识库平台。

### 2.2 规划能力

AI 数据分析是规划能力，当前先定义产品边界，不作为一期核心验收前置条件。

规划能力包括：

- 上传结构化数据。
- 数据分析。
- 自动生成图表。
- 自然语言解释。

### 2.3 一期不包含

以下能力暂不进入一期范围：

- 钉钉。
- 企业登录。
- PPT 生成。
- 多租户。
- 企业权限。
- 微服务。
- 复杂任务队列。
- 多模型选择 UI。
- 企业级知识库。
- 多文件联合问答。
- OCR。

## 3. 用户角色

### 3.1 普通 Web 用户

普通 Web 用户是当前 v1.0 的主要用户。

能力范围：

- 进入 Web 聊天界面。
- 发送普通 AI 问题。
- 上传自己的文档。
- 查看上传文件状态。
- 基于已解析文档进行问答。

### 3.2 系统维护者

当前 v1.0 不实现独立管理后台。

系统维护者主要负责：

- 配置 LLM API。
- 启动前后端服务。
- 查看基础运行日志。
- 处理本地开发或演示环境中的配置问题。

## 4. 核心业务流程

### 4.1 普通 AI 聊天流程

1. 用户进入 Web 聊天界面。
2. 用户输入问题。
3. 前端调用后端聊天接口。
4. 后端 Chat Service 接收请求。
5. Chat Service 调用 LLM Service。
6. LLM Service 选择当前配置的 LLM Provider。
7. 后端返回 AI 回答。
8. 前端展示回答。

一期验收重点：

- 前端不再只依赖本地 Mock 聊天。
- 后端可以通过 Mock Provider 本地开发。
- 后端可以通过 OpenAI-compatible Provider 调用真实 LLM。
- LLM 调用失败时，前端能看到明确错误提示。

### 4.2 文件上传流程

1. 用户在 Web 页面选择文件。
2. 前端调用后端文件上传接口。
3. 后端校验文件大小和文件类型。
4. 后端保存原始文件。
5. 后端记录文件元数据和处理状态。
6. 前端展示文件上传结果和文件状态。

一期文件范围：

- TXT：必须支持。
- PDF：建议支持。
- DOCX：可根据实现进度纳入一期。

一期限制：

- 文件上传先面向单用户、本地演示场景。
- 不实现企业级文件权限。
- 不实现对象存储。
- 不实现多租户文件隔离。

### 4.3 文档解析流程

1. 文件上传成功后进入待解析状态。
2. 后端根据文件类型选择 Parser。
3. Parser 提取文档文本。
4. 后端保存解析结果或解析状态。
5. 解析成功后，文件进入可问答状态。
6. 解析失败时，前端展示失败状态。

一期解析重点：

- 先支持文本型文档。
- 扫描件 PDF 和 OCR 不进入一期。
- Parser 需要保留扩展边界，便于后续增加更多文件格式。

### 4.4 RAG 知识问答流程

1. 用户选择一个已解析文件。
2. 用户围绕该文件提问。
3. 后端根据文件内容进行 chunk 检索。
4. 后端将检索上下文和用户问题一起交给 LLM。
5. LLM 返回基于文档内容的回答。
6. 前端展示回答和必要的来源信息。

一期 RAG 边界：

- 优先实现单文件问答。
- 检索范围限定在当前文件。
- 不做全局知识库。
- 不做多文件联合问答。
- 不做复杂 Agent 推理。

## 5. 规划能力：AI 数据分析

AI 数据分析是规划能力，不属于当前一期核心闭环。

目标能力包括：

- 上传结构化数据。
- 数据分析。
- 自动生成图表。
- 自然语言解释。

### 5.1 结构化数据上传

规划支持：

- CSV。
- Excel。
- JSON。

基本目标：

- 用户上传结构化数据文件。
- 系统识别字段、行列、数据类型。
- 系统生成数据摘要。

### 5.2 数据分析

规划支持：

- 描述性统计。
- 数据筛选。
- 排序与聚合。
- 趋势分析。
- 异常值识别。

MVP 控制原则：

- 先支持只读分析。
- 不直接修改用户原始数据。
- 不执行高风险自动化操作。

### 5.3 自动生成图表

规划支持：

- 表格预览。
- 柱状图。
- 折线图。
- 饼图。
- 散点图。

MVP 控制原则：

- 先生成基础图表。
- 不追求复杂 BI 仪表盘。
- 图表生成应由结构化分析结果驱动，而不是只靠 LLM 自由生成。

### 5.4 自然语言解释

规划支持：

- 用自然语言解释数据概况。
- 总结主要趋势。
- 解释图表含义。
- 给出可验证的数据洞察。

MVP 控制原则：

- 回答必须基于实际数据结果。
- LLM 不应编造数据。
- 关键数值应来自程序计算结果，而不是模型猜测。

## 6. 非功能需求

### 6.1 简单可用

- 用户可以在本地或演示环境中快速启动系统。
- 普通聊天和文件问答流程应清晰可见。
- UI 不追求复杂配置，优先保证主流程顺畅。

### 6.2 可维护性

- 后端保持单体应用。
- 后端按 `api -> service -> repository` 思路演进。
- LLM 调用通过 Provider 抽象。
- 文档解析通过 Parser 抽象。
- RAG 检索通过 VectorStore 抽象。
- 不提前实现未进入一期的复杂能力。

### 6.3 可扩展性

当前 MVP 需要为后续能力保留边界：

- 新增 LLM Provider。
- 新增文件 Parser。
- 替换 Embedding 模型。
- 替换向量存储。
- 接入 AI 数据分析。
- 后续接入 Agent Workflow。

但这些扩展边界不等于一期全部实现。

### 6.4 可观测性

一期至少需要：

- 基础应用日志。
- LLM 调用成功和失败记录。
- 文件处理状态。
- RAG 检索失败原因。

一期不要求：

- 分布式链路追踪。
- 外部日志平台。
- 完整审计系统。

## 7. 验收标准

v1.0 MVP 验收以核心链路跑通为准。

必须满足：

1. 用户可以打开 Web 页面并进入聊天界面。
2. 用户可以发送普通问题。
3. 后端可以调用 LLM 并返回回答。
4. 用户可以上传文档。
5. 系统可以解析文档内容。
6. 系统可以基于文档内容建立可检索数据。
7. 用户可以围绕上传文档进行 RAG 问答。
8. 普通聊天和文档问答在交互上可以区分。
9. 文件未解析完成或解析失败时，前端有明确提示。

AI 数据分析的验收标准不进入当前核心 MVP 验收；后续启动该能力时，应另行定义结构化数据上传、分析结果、图表和自然语言解释的最小闭环。

## 8. 当前约束

- 当前项目已经存在前端 Mock 原型和后端基础聊天模块。
- 当前前端聊天尚未接入后端真实接口。
- 当前尚未实现数据库、文件上传、文档解析、Embedding 和 RAG。
- AI 数据分析当前只做规划，不进入代码实现。
- 当前不引入企业登录、企业权限、多租户、PPT 生成。
- 当前不引入微服务和复杂任务队列。

## 9. 范围控制原则

后续开发必须遵循：

- 先完成普通聊天闭环，再做文件和 RAG。
- 先实现单文件 RAG，再考虑多文件或知识库。
- 先实现基础数据分析，再考虑复杂 BI。
- 先保持单体架构，再根据真实复杂度扩展。
- 规划能力可以保留设计边界，但不能挤占一期核心闭环。
