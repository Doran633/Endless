# 企业内部 AI 助手 MVP 需求说明

## 1. 项目定位

本项目是一个企业内部 AI 助手平台的一期 MVP，目标不是一次性建设完整 AI 平台，而是优先跑通核心业务闭环。

一期核心链路：

1. 员工通过钉钉登录。
2. 进入 Web 聊天界面。
3. 上传单个文件。
4. 系统解析文件内容并建立向量索引。
5. 用户围绕该文件进行问答。
6. 系统支持基于文件内容生成 PPT。

## 2. MVP 范围

### 2.1 一期包含

- 钉钉 OAuth / 免登认证。
- JWT 登录态。
- 基础聊天页面。
- 普通 AI 对话。
- 单文件上传。
- 单文件解析。
- 单文件问答。
- 文件 chunk 切分与 embedding。
- 使用 pgvector 按 `file_id` 检索。
- PPT 生成任务。
- PPT 生成结果下载。
- 基础任务状态查询。

### 2.2 一期不包含

- 密码注册。
- 手机号登录。
- 多模型切换。
- 多 LLM Provider 实现。
- 企业级知识库。
- 全局知识检索。
- 多文件联合问答。
- 复杂权限管理后台。
- 微服务拆分。
- 微前端。
- Celery / Kafka / RabbitMQ 等消息队列。
- MinIO / OSS 等对象存储实现。
- PPT 大纲审批流程。
- 多租户商业化能力。

## 3. 用户角色

### 3.1 企业员工

企业员工是一期主要用户。

能力范围：

- 使用钉钉登录。
- 上传自己的文件。
- 围绕自己上传的文件提问。
- 查看自己的聊天记录。
- 生成并下载自己的 PPT。

### 3.2 管理员

一期不实现独立管理员后台。最小运维操作通过数据库直接管理。

（详见 `mvp_decision.md` 第 2.1 节）

## 4. 核心业务流程

### 4.1 登录流程

1. 前端通过钉钉获取 auth code。
2. 前端调用后端 `/api/v1/auth/dingtalk/login`。
3. 后端向钉钉换取用户信息。
4. 后端创建或更新本地用户。
5. 后端返回 JWT。
6. 前端进入聊天页面。

决策结果：

- 登录方式：**扫码登录**（不依赖钉钉内嵌环境），内嵌免登二期实现。
- JWT access_token 有效期：**24 小时**。
- refresh_token：**提供**，有效期 7 天。

（详见 `mvp_decision.md` 第 2.1 节）

### 4.2 文件问答流程

1. 用户上传文件。
2. 后端保存原始文件到本地存储（状态：uploaded）。
3. 后端 BackgroundTask 异步解析文本。
4. 后端切分 chunk。
5. 后端生成 embedding。
6. 后端将 chunk 和向量写入 PostgreSQL pgvector（状态：ready）。
7. 用户基于该文件提问。
8. 后端按 `file_id` 检索相关 chunk。
9. 后端调用 Claude API 生成回答。
10. 前端展示回答。

决策结果：

- 一期文件格式：**TXT、PDF、DOCX**。
- 单文件大小上限：**20 MB**。
- chunk 大小：**512 tokens**，overlap：**64 tokens**。
- embedding 模型：**BGE-M3**（本地部署），维度 1024。企业数据不出域。

（详见 `mvp_decision.md` 第 2.3-2.4 节）

### 4.3 PPT 生成流程

1. 用户选择已上传文件。
2. 用户触发生成 PPT。
3. 后端创建 PPT 生成任务。
4. 后端调用 LLM 生成结构化内容。
5. 后端生成 PPT 文件。
6. 前端查询任务状态。
7. 用户下载生成结果。

决策结果：

- 页数范围：**5-15 页**。
- 模板策略：**固定模板**（编码内统一风格）。
- 用户输入：**标题（必填）** + 主题要求（选填）。
- 重试策略：**失败后最多重试 1 次**。

（详见 `mvp_decision.md` 第 2.5 节）

## 5. 权限边界

一期采用最小权限原则：

- 用户只能访问自己的文件。
- 用户只能访问自己的聊天记录。
- 用户只能查看自己的任务。
- 用户只能下载自己生成的 PPT。
- 后端接口必须基于当前登录用户做数据隔离。

## 6. 非功能需求

### 6.1 可维护性

- 后端采用 `api -> service -> repository` 分层。
- LLM、Parser、FileService 保留接口抽象。
- 不提前实现未确认的扩展能力。

### 6.2 可部署性

- 使用 Docker Compose 保证团队开发环境一致。
- 一期服务按单体应用设计。

### 6.3 可观测性

一期至少需要：

- 应用日志。
- 任务状态。
- 关键错误信息。

决策结果：

- 外部日志系统：**一期不接入**。
- 请求链路追踪：**一期不实现**。
- 一期日志输出到 **stdout**，由 Docker 日志驱动收集。

（详见 `mvp_decision.md` 第 2.6 节）

## 7. 验收标准

MVP 验收以业务链路跑通为准：

1. 用户可以通过钉钉登录。
2. 登录后可以进入聊天页面。
3. 用户可以上传一个文件。
4. 系统可以解析该文件。
5. 用户可以围绕该文件提问并得到回答。
6. 用户可以基于该文件生成 PPT。
7. 用户可以下载生成的 PPT。

## 8. 当前约束

- 不创建 backend 和 frontend 工程代码。
- 当前阶段只维护设计文档。
- 后续开发必须先参考本目录文档。
