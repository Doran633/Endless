# v0.6.1 聊天侧文件接入体验优化报告

## 1. 本次完成内容

v0.6.1 完成了聊天侧文件接入体验优化。

用户现在可以在聊天输入区选择文件。前端会自动依次调用已有后端 API：

```text
上传文件
  -> 文档解析
  -> 文本切块
  -> mock 向量化
```

处理完成后，聊天输入区会展示简洁状态，文件中心仍然保留详细的文件状态、解析预览、chunk 预览和 embedding 预览。

本阶段没有实现 RAG、文件问答、向量数据库、真实 embedding API，也没有把文件内容拼进聊天 prompt。

## 2. 修改文件说明

### `frontend/src/types/index.ts`

新增聊天侧文件处理状态类型：

- `FileIngestionStatus`
- `FileIngestionState`

原因：

- 聊天侧需要展示上传、解析、切块、向量化、完成和失败状态。
- 这些状态属于用户体验层，不等同于文件中心里的 `FileItem.status`。

### `frontend/src/stores/fileStore.ts`

新增 `ingestion` 状态和 `ingestFile(file)` 动作。

`ingestFile()` 负责串联：

```text
uploadFileApi()
  -> parseFileApi()
  -> chunkFileApi()
  -> embedFileApi()
```

原因：

- 避免 `ChatInput` 直接知道四个 API 的细节。
- 保持文件中心原有的手动操作能力。
- 把“自动处理文件”的流程收敛在状态管理层，便于后续迁移到后端编排接口。

### `frontend/src/components/ChatInput.tsx`

新增聊天输入区附件按钮和文件处理状态提示。

用户选择文件后，组件只调用：

```text
useFileStore().ingestFile(file)
```

原因：

- 聊天窗口是用户最自然的文件上传入口。
- 用户不需要理解解析、切块、向量化三个工程步骤。
- 当前仍展示简洁状态，避免用户误以为系统卡住。

### `docs/status.md`

更新当前版本为 `v0.6.1`，并记录聊天侧文件自动接入能力。

### `docs/v0.6.1_chat_file_ingestion_report.md`

记录本次实现内容、调用链路、设计原因、测试结果和剩余问题。

## 3. 当前调用链路

聊天侧文件接入链路：

```text
ChatInput
  -> handleFileChange()
  -> fileStore.ingestFile(file)
  -> uploadFileApi(file)
  -> POST /api/v1/files
  -> parseFileApi(file_id, extension)
  -> POST /api/v1/files/{file_id}/parse
  -> chunkFileApi(file_id, extension)
  -> POST /api/v1/files/{file_id}/chunks
  -> embedFileApi(file_id, extension)
  -> POST /api/v1/files/{file_id}/embeddings
  -> 更新 FileItem 为 embedded
  -> 更新聊天侧 ingestion 状态为 completed
```

后端仍然复用 v0.6 已有能力：

- `FileService`
- `DocumentParserService`
- `ChunkService`
- `EmbeddingService`
- `MockEmbeddingProvider`

## 4. 设计原因

### 4.1 为什么放在聊天输入区

用户上传文件的真实意图通常是让 AI 助手准备理解这个文件，而不是进入文件中心手动执行工程步骤。

聊天输入区增加上传入口后，产品体验更接近真实 AI 助手。

### 4.2 为什么自动处理

当前已有完整后端处理链路，继续让用户手动点击解析、切块和向量化，会暴露过多技术细节。

自动处理可以把用户动作简化为：

```text
选择文件
  -> 等待准备完成
```

### 4.3 为什么仍保留文件中心

文件中心仍有价值：

- 查看文件列表。
- 查看解析预览。
- 查看 chunk 预览。
- 查看 embedding 预览。
- 调试失败状态。

聊天侧是高频入口，文件中心是管理和观察入口。

### 4.4 为什么不新增后端接口

v0.6.1 是体验优化，不是后端架构升级。

当前没有数据库、任务状态表和后台 job 系统，新增 `POST /files/ingest` 会提前引入后端编排复杂度。

因此本阶段由前端串联已有 API。后续有持久化和任务状态后，再迁移到后端统一编排更合适。

## 5. 当前能力边界

当前已经可以：

- 在聊天输入区上传文件。
- 自动保存文件到后端。
- 自动解析 TXT / DOCX / 可复制文本型 PDF。
- 自动生成 chunks。
- 自动生成稳定 mock embedding vectors。
- 在聊天侧看到处理状态。
- 在文件中心查看详细处理结果。

当前仍不能：

- 基于上传文件问答。
- 检索相关 chunks。
- 保存 vectors 到向量数据库。
- 使用真实 embedding API。
- 刷新页面后恢复文件处理结果。

### 6.1 本地 API 请求稳定性修复

本次收尾同时修复了聊天侧上传时出现的 `Failed to fetch` 问题。

错误位置：

- `frontend/src/api/fileApi.ts`
- `frontend/src/api/chatApi.ts`
- `frontend/vite.config.ts`
- `backend/app/main.py`

错误原因：

前端开发服务器由 Vite 启动，默认使用 `5173` 端口。但当 `5173`、`5174` 或其他端口被占用时，Vite 会自动切换到新的端口，例如 `5176`。

原前端代码默认直接请求：

```text
http://localhost:8000/api/v1/files
```

而浏览器页面实际来源可能是：

```text
http://127.0.0.1:5176
```

这会产生跨域请求。后端原本只允许 `5173` 和 `5174`，所以当页面运行在 `5176` 时，浏览器会在请求到达业务处理前拦截它，前端表现为 `Failed to fetch`。

修复方式：

- 前端默认 API 地址改为相对路径，让本地开发请求先进入 Vite dev server。
- Vite proxy 将 `/api` 转发到 `http://127.0.0.1:8000`。
- 后端 CORS 增加本地开发端口兜底，允许 `localhost` 和 `127.0.0.1` 的开发端口。

修复后的本地请求链路：

```text
Browser
  -> fetch('/api/v1/files')
  -> Vite dev server
  -> proxy http://127.0.0.1:8000/api/v1/files
  -> FastAPI
```

工程意义：

- 前端不再硬编码本地后端地址。
- Vite 自动换端口时，上传和聊天 API 仍能稳定工作。
- 本地开发与未来生产部署边界更清楚：开发环境走相对路径和代理，生产环境仍可用 `VITE_API_BASE_URL` 指向真实 API 地址。

已验证：

```text
通过 http://127.0.0.1:5176/api/v1/files 上传 TXT 成功
通过 http://127.0.0.1:5176/api/v1/files/{file_id}/parse 解析成功
通过 http://127.0.0.1:5176/api/v1/files/{file_id}/chunks 切块成功
通过 http://127.0.0.1:5176/api/v1/files/{file_id}/embeddings 向量化成功
```

## 7. 剩余问题

当前主要技术债：

- 自动处理流程暂时由前端编排。
- 文件、解析结果、chunks 和 embeddings 尚未持久化。
- 处理失败后不能从失败步骤继续。
- mock embedding 不代表真实语义。
- 当前没有 VectorStore，所以无法做检索。
- 当前没有 RetrievalService 和 RagService，所以无法做文件问答。

## 8. 下一阶段建议

v0.7 建议进入 VectorStore 设计与最小实现。

推荐目标：

```text
chunks + mock embeddings
  -> VectorStore

  -> 支持简单查询和读取
```

v0.7 仍然可以暂不做完整 RAG 问答，先把向量存储边界建稳。
