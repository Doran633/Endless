# v1.3.0 Basic Context Window 开发计划

## 1. 当前问题

当前项目已经完成 v1.2.5 Persistent Conversations UX：

- 会话列表可以持久化。
- 普通聊天消息可以写入 `chat_messages`。
- RAG 问答消息可以写入 `chat_messages`。
- 前端刷新后可以恢复会话和历史消息。
- 当前会话可以恢复绑定文件。
- 会话标题可以自动生成。
- 普通聊天身份提示已经统一为“北辰agent”。

但现在仍有一个明显体验问题：

用户虽然能看到历史消息，但 LLM 在生成新回答时并不会自动读取这些历史消息。

例如：

```text
用户：帮我写一个活动方案
AI：好的，方案如下...
用户：把第二部分改得更正式一点
```

当前模型可能不知道“第二部分”指的是上一轮回答里的哪一部分，因为后端仍只把当前这一条 message 传给 LLM。

这说明项目已经完成“历史保存”，但还没有完成“基础上下文理解”。

## 2. 为什么现在进入上下文窗口

现在进入 v1.3.0 是合理的，因为前置条件已经具备：

1. 消息已经持久化。
   后端已经有 `chat_messages` 表，可以按 session 查询历史消息。

2. 前端已经传递 `session_id`。
   普通聊天请求已经能告诉后端当前属于哪个会话。

3. ChatService 已有 LLMProvider 抽象。
   只需要让 ChatService 支持传入多条 messages，不需要改 Provider。

4. 用户体验收益明显。
   只带最近几轮消息，就能显著改善连续追问、改写、补充说明等普通聊天场景。

本阶段不做 RAG 上下文，是因为 RAG 已经有自己的文档检索上下文。先把普通聊天做好，边界更清楚。

## 3. 上下文窗口和长期记忆的区别

上下文窗口解决的是：

- 当前请求要带哪些最近历史消息给 LLM。
- 让模型理解“它”“上面那段”“继续”“第二点”等连续对话指代。
- 只在当前会话内生效。
- 通常取最近 N 条消息。

长期记忆解决的是：

- 跨会话保存用户偏好。
- 长期积累重要事实。
- 从大量历史中检索相关记忆。
- 需要摘要、embedding、权限和遗忘策略。

v1.3.0 只做上下文窗口，不做长期记忆。

## 4. 数据流设计

普通聊天新链路：

```text
Frontend ChatInput
-> POST /api/v1/chat { message, session_id }
-> API Router
-> ConversationService.answer_and_persist_chat()
-> ChatRepository.list_recent_messages(session_id, limit=6)
-> ConversationService 组装 history messages + 当前 user message
-> ChatService.answer_with_context(messages)
-> LLMService
-> LLMProvider
-> ChatRepository.create_message(user)
-> ChatRepository.create_message(assistant)
-> maybe_update_session_title()
-> 返回原 ChatResponse
```

设计要点：

- 前端 API 不需要变化。
- `session_id` 仍然是是否进入持久化聊天路径的开关。
- 历史消息只用于普通聊天。
- 当前用户输入不应重复保存后再进入上下文，应先读取历史，再把当前消息追加到 LLM messages 中。
- LLM 成功回答后，再写入 user 和 assistant 消息。

## 5. ChatRepository 需要增加的方法

建议新增：

```python
def list_recent_messages(self, session_id: str, limit: int) -> list[ChatMessageRecord]:
    ...
```

职责：

- 只从数据库读取最近 N 条消息。
- 按 `created_at desc` 查询，再在应用层反转为正序。
- 不拼 LLM prompt。
- 不判断哪些 role 可以进入上下文。
- 不处理 token 截断。

建议规则：

- 只读取当前 `session_id`。
- 默认 `limit=6`。
- 返回顺序应该是旧到新，方便直接转换成 LLM messages。

## 6. ConversationService 如何编排

`ConversationService.answer_and_persist_chat()` 需要扩展：

1. 校验 session 存在。
2. 读取最近 6 条历史消息。
3. 将数据库消息转换成 LLM `ChatMessage`。
4. 过滤不适合进入普通聊天上下文的内容。
5. 追加当前 user message。
6. 调用 `ChatService.answer_with_context()`。
7. 保存当前 user 消息。
8. 保存 assistant 消息。
9. 自动更新标题。
10. 返回原 ChatResponse。

过滤建议：

- 只带 `role in ["user", "assistant"]`。
- 跳过空 content。
- 暂不特殊处理 RAG metadata。
- 如果历史消息里包含 RAG 回答，也只把其可见文本作为普通上下文，不额外注入 used_chunks。

这样做的原因：

- 保持实现简单。
- 避免 RAG 引用片段和普通聊天上下文混在一起造成 prompt 过长。
- 后续可以单独设计 RAG 多轮追问。

## 7. ChatService 如何支持 messages 输入

当前 `ChatService.answer(content: str)` 只接收当前用户输入。

建议新增：

```python
def answer_with_context(self, messages: list[ChatMessage]) -> dict[str, object]:
    ...
```

职责：

- 接收已经组装好的 LLM messages。
- 在最前面加入北辰agent system prompt。
- 调用 `LLMService.chat()`。
- 返回现有 `answer/model/usage` 结构。

原有 `answer(content: str)` 保留，并改为复用 `answer_with_context()`：

```python
def answer(self, content: str) -> dict[str, object]:
    return self.answer_with_context([ChatMessage(role="user", content=content)])
```

这样可以保证：

- 无 `session_id` 的旧聊天行为不变。
- 有 `session_id` 的新聊天可以传入历史上下文。
- LLMProvider 不需要修改。

## 8. API 是否需要变化

本阶段 API 不需要变化。

继续使用：

```http
POST /api/v1/chat
```

请求仍是：

```json
{
  "message": "继续优化上一版",
  "session_id": "session_xxx"
}
```

行为变化：

- 无 `session_id`：保持单轮普通聊天。
- 有 `session_id`：读取最近 N 条消息作为上下文，再调用 LLM。

不新增参数 `context_limit`。

原因：

- MVP 阶段保持简单。
- 避免前端暴露工程参数。
- 默认 N=6 足够验证连续对话体验。

## 9. token 风险和截断策略

主要风险：

- 最近 6 条消息可能仍然很长。
- 如果其中包含长代码、长报告或 RAG 回答，可能增加 token 成本。
- 上下文过长会导致模型响应变慢，甚至触发模型上下文限制。

v1.3.0 最小截断策略：

- 默认最多读取最近 6 条消息。
- 每条历史消息最多保留 1200 个字符。
- 当前用户消息仍保留现有 `ChatRequest` 的最大长度限制。
- 截断历史消息时在末尾追加 `...`。

建议常量：

```python
DEFAULT_CONTEXT_MESSAGE_LIMIT = 6
MAX_CONTEXT_MESSAGE_CHARS = 1200
```

本阶段不做：

- tokenizer-aware 截断。
- 按 token 精确预算。
- 历史摘要。
- 语义检索。

这些都留到后续版本。

## 10. 测试方案

后端验证：

1. 创建会话。
2. 连续发送两轮普通聊天，第二轮使用代词或“继续”。
3. 验证 `ChatService.answer_with_context()` 收到 system + 历史 + 当前 user message。
4. 验证最近历史数量不超过 6。
5. 验证单条历史超过 1200 字符会被截断。
6. 验证无 `session_id` 的 `/api/v1/chat` 仍只走单轮聊天。
7. 验证 RAG API 行为不变。

必要命令：

```powershell
cd backend
python -m compileall app
```

```powershell
cd frontend
npm exec tsc -- --noEmit
```

手动验证：

- 第一轮问：“帮我写一个产品介绍。”
- 第二轮问：“把上面的语气改得更正式。”
- 预期：模型知道“上面”指上一轮产品介绍。

## 11. 不做范围

v1.3.0 不做：

- RAG 多轮追问。
- 多文件 RAG。
- 历史消息语义检索。
- 长期记忆。
- 用户画像。
- 跨会话记忆。
- 会话摘要。
- tokenizer-aware token 预算。
- 前端上下文开关。
- 新 API。
- Agent。
- 企业权限。

## 12. 后续如何扩展到摘要、历史检索和 Agent

### 12.1 会话摘要

当消息数量变多后，可以新增 `chat_session_summaries` 或在 `chat_sessions` 中增加 summary 字段。

后续链路：

```text
历史消息过长
-> SummaryService 生成会话摘要
-> 新请求携带 summary + 最近 N 条消息
```

### 12.2 历史消息语义检索

如果要让模型从更长历史中找相关内容，可以对 `chat_messages` 做 embedding。

后续链路：

```text
用户新问题
-> EmbeddingService 生成 query embedding
-> MessageVectorStore 检索相关历史消息
-> prompt = 摘要 + 最近消息 + 相关历史
```

这属于“记忆检索”，不是 v1.3 的范围。

### 12.3 Agent

Agent 需要更明确的状态和工具调用记录。

后续可扩展：

- `workflow_runs`
- `workflow_steps`
- `tool_calls`
- `human_confirmations`

当前 v1.3 的上下文窗口只解决普通聊天连续性，为未来 Agent 的“对话状态理解”打基础，但不引入 Agent 框架。
