# v0.4 文档解析计划

> 本计划用于 v0.4 开发阶段。
> 目标是实现 TXT / DOCX / PDF 的最小文档解析闭环。
> 本阶段不实现 RAG、Embedding、向量数据库、数据库、复杂任务队列、企业权限、Agent 或 PPT。

## 1. 当前问题

当前项目已经完成 v0.3 真实文件上传闭环：

```text
前端选择文件
  -> POST /api/v1/files
  -> FastAPI
  -> FileService
  -> 保存到 backend/uploads/
  -> 返回上传结果
  -> 前端展示真实上传结果
```

当前文件模块的能力边界是“能保存文件”，但系统还不能理解文件内容。

当前缺口：

- 后端没有文档解析服务。
- 后端不能从 `backend/uploads/` 中读取已上传文件并提取文本。
- 前端只能展示 `uploaded` 状态，不能触发解析。
- 文件问答入口仍不可用，因为 RAG 的前置条件“文档文本抽取”尚未完成。
- 当前没有数据库，文件元数据只存在于上传响应和前端状态中。

v0.4 的目标是先补齐 RAG 前置能力：

```text
已上传文件
  -> 前端触发解析
  -> POST /api/v1/files/{file_id}/parse
  -> DocumentParserService
  -> 根据 extension 解析 TXT / DOCX / PDF
  -> 返回 parsed、text_preview、char_count
  -> 前端展示解析结果
```

## 2. 修改文件列表

### 2.1 后端新增文件

#### `backend/app/services/document_parser_service.py`

职责：

- 定义文档解析业务边界。
- 根据文件扩展名分派解析逻辑。
- 读取 `backend/uploads/{file_id}.{extension}`。
- 提取纯文本。
- 生成 `text_preview` 和 `char_count`。

修改原因：

- 避免把 TXT / DOCX / PDF 解析逻辑写进 API 层或 `FileService`。
- 为后续 chunk、embedding 和 RAG 保留清晰入口。

### 2.2 后端修改文件

#### `backend/app/api/v1/files.py`

计划修改：

- 增加解析接口：`POST /api/v1/files/{file_id}/parse`。
- 接收 `extension` 参数，v0.4 暂时用于定位本地文件。
- 调用 `DocumentParserService`。
- 返回统一响应。

修改原因：

- 当前没有解析入口。
- 由于尚无数据库，后端无法仅凭 `file_id` 查询扩展名和原始文件名；v0.4 需要前端把 `extension` 一起传给解析接口。

#### `backend/app/schemas/file.py`

计划修改：

- 增加文档解析请求 Schema。
- 增加文档解析响应 Schema。

建议结构：

```text
ParseFileRequest
  extension: string

ParsedFileResponse
  file_id: string
  status: "parsed"
  extension: string
  text_preview: string
  char_count: int
```

修改原因：

- 保持 API 入参和出参可验证。
- 让前端拿到稳定字段用于展示。

#### `backend/app/core/errors.py`

计划修改：

- 增加文档解析相关错误。

建议错误：

- `DocumentParseError`
- `DocumentNotFoundError`

修改原因：

- 文件不存在、扩展名不支持、解析失败都需要返回稳定 JSON。

#### `backend/requirements.txt`

计划修改：

- 增加 `python-docx`。
- 增加 `pypdf`。

修改原因：

- DOCX 解析需要 `python-docx`。
- PDF 可复制文本解析需要 `pypdf`。

### 2.3 前端修改文件

#### `frontend/src/api/fileApi.ts`

计划修改：

- 增加 `parseFile(fileId, extension)`。
- 调用 `POST /api/v1/files/{file_id}/parse`。
- 解析统一响应结构。

修改原因：

- 当前前端只有上传 API，没有解析 API。

#### `frontend/src/stores/fileStore.ts`

计划修改：

- 增加 `parseFile(fileId)`。
- 从当前 `files` 中找到对应文件，取出 `extension`。
- 调用 `fileApi.parseFile(fileId, extension)`。
- 解析中将文件状态更新为 `processing`。
- 解析成功将文件状态更新为 `ready`。
- 解析失败将文件状态更新为 `failed`。
- 保存最小解析结果，例如 `text_preview` 和 `char_count`。

修改原因：

- 让解析状态成为前端文件状态的一部分。
- 为后续 RAG 问答按钮启用提供状态依据。

#### `frontend/src/types/index.ts`

计划修改：

- 扩展 `FileItem`。

建议新增字段：

```text
text_preview?: string
char_count?: number
parsed_at?: string
error_message?: string
```

修改原因：

- 前端需要展示解析预览和解析结果状态。

#### `frontend/src/components/FileCenter.tsx`

计划修改：

- 增加“解析”按钮。
- `uploaded` 文件允许点击解析。
- `processing` 文件显示解析中。
- `ready` 文件显示已解析，并展示文本预览入口或摘要区域。
- `failed` 文件显示失败提示。
- 问答按钮仍保持禁用或提示“RAG 将在下一阶段开放”。

修改原因：

- 让用户可以从文件中心触发并看到真实解析结果。
- 避免误导用户认为 v0.4 已经完成 RAG。

## 3. API 设计

### 3.1 解析文件

接口：

```text
POST /api/v1/files/{file_id}/parse
```

请求体：

```json
{
  "extension": "pdf"
}
```

说明：

- v0.4 暂无数据库，后端无法只通过 `file_id` 查出文件扩展名。
- 前端当前持有上传响应中的 `extension`，因此先把 `extension` 传给后端。
- 后续引入数据库后，应改为后端通过 `file_id` 查询文件元数据，前端不再传 `extension`。

成功响应：

```json
{
  "code": 0,
  "message": "ok",
  "data": {
    "file_id": "uuid",
    "status": "parsed",
    "extension": "pdf",
    "text_preview": "文档前若干字符...",
    "char_count": 8234
  }
}
```

文件不存在响应：

```json
{
  "code": 43001,
  "message": "Uploaded file not found",
  "data": null
}
```

解析失败响应：

```json
{
  "code": 43002,
  "message": "Failed to parse document",
  "data": null
}
```

### 3.2 状态定义

v0.4 使用现有前端状态：

- `uploaded`：文件已上传，尚未解析。
- `processing`：正在解析。
- `ready`：解析完成，可作为后续 RAG 输入。
- `failed`：解析失败。

说明：

- v0.4 的 `ready` 只表示文本解析已完成。
- `ready` 不代表 RAG 索引完成。
- 问答入口不应因为 `ready` 就直接进入 RAG，除非后续阶段完成 chunk、embedding 和检索。

## 4. DocumentParserService 设计

### 4.1 职责

`DocumentParserService` 负责文档解析的业务边界：

- 校验扩展名是否支持。
- 根据 `file_id` 和 `extension` 定位本地文件。
- 检查文件是否存在。
- 根据扩展名选择解析器。
- 返回纯文本。
- 生成文本预览。
- 统计字符数。

建议方法：

```text
parse(file_id: str, extension: str) -> ParsedFileResponse
```

内部方法：

```text
_parse_txt(path: Path) -> str
_parse_docx(path: Path) -> str
_parse_pdf(path: Path) -> str
_build_preview(text: str) -> str
```

### 4.2 不做职责

`DocumentParserService` v0.4 不做：

- 文件上传。
- 文件删除。
- 文件下载。
- 数据库存储。
- chunk。
- embedding。
- 向量写入。
- RAG 检索。
- LLM 总结。
- OCR。
- 权限校验。
- 后台任务编排。

### 4.3 与 FileService 的关系

`FileService`：

- 负责接收上传文件。
- 负责保存原始文件。
- 负责返回上传元数据。

`DocumentParserService`：

- 负责读取已保存文件。
- 负责提取文本。
- 负责返回解析结果。

二者关系：

```text
FileService 保存文件
  -> DocumentParserService 读取保存后的文件
  -> 后续 ChunkService / EmbeddingService / RagService 接解析结果
```

这种拆分可以避免 `FileService` 变成“上传 + 解析 + RAG”的大杂烩。

## 5. TXT / DOCX / PDF 解析方案

### 5.1 TXT

技术方案：

- 使用 Python 内置文件读取。
- 默认按 `utf-8` 读取。
- 如 `utf-8` 失败，可尝试 `utf-8-sig` 或 `gbk`。

MVP 建议：

- 先支持 `utf-8` 和 `utf-8-sig`。
- 如遇编码失败，返回解析错误。

不做：

- 复杂编码自动识别。
- 文本清洗规则系统。

### 5.2 DOCX

技术方案：

- 使用 `python-docx`。
- 读取段落文本。
- 可读取表格单元格文本，但 v0.4 可先只保证段落文本。

MVP 建议：

- 提取 `document.paragraphs`。
- 过滤空段落。
- 使用换行拼接。

不做：

- 页眉页脚完整提取。
- 批注提取。
- 修订痕迹处理。
- 图片 OCR。
- 复杂表格结构还原。

### 5.3 PDF

技术方案：

- 使用 `pypdf`。
- 遍历页面调用 `extract_text()`。
- 拼接每页文本。

MVP 建议：

- 只支持可复制文本型 PDF。
- 如果 `extract_text()` 返回空文本，则提示“当前 PDF 可能是扫描件，v0.4 暂不支持 OCR”。

不做：

- 扫描件 OCR。
- 复杂版式还原。
- 表格结构识别。
- 图片内容提取。
- PDF 加密解密。

## 6. 前端接入方案

### 6.1 当前前端状态

当前文件中心已经可以：

- 上传 TXT / PDF / DOCX。
- 展示上传结果。
- 展示 `uploaded` 状态。

当前前端还不能：

- 触发后端解析。
- 展示解析中。
- 展示解析完成。
- 展示文本预览。

### 6.2 v0.4 调整方案

新增前端链路：

```text
用户点击“解析”
  -> FileCenter.handleParse(file)
  -> fileStore.parseFile(file.id)
  -> fileApi.parseFile(file.id, file.extension)
  -> POST /api/v1/files/{file_id}/parse
  -> 后端返回 text_preview 和 char_count
  -> fileStore 更新文件状态为 ready
  -> FileCenter 展示解析结果
```

### 6.3 UI 行为建议

`uploaded`：

- 显示“已上传”。
- 显示“解析”按钮。
- 问答按钮禁用。

`processing`：

- 显示“解析中”。
- 禁用上传相关操作之外的解析按钮。

`ready`：

- 显示“已解析”。
- 展示 `char_count`。
- 提供“查看预览”或直接在文件列表下方展示 `text_preview`。
- 问答按钮仍不进入真实 RAG，可提示“RAG 将在下一阶段开放”。

`failed`：

- 显示“解析失败”。
- 展示 `error_message`。
- 允许重新解析。

### 6.4 前端状态注意点

由于 v0.4 仍没有数据库：

- 页面刷新后，真实上传文件列表仍不会从后端恢复。
- 解析结果只存在前端内存中。
- 这不是 bug，而是当前 MVP 阶段的明确限制。

后续引入数据库后：

- 上传记录应写入数据库。
- 解析结果应写入数据库或文档内容表。
- 前端应通过文件列表 API 获取真实文件状态。


## 9. 后续如何接入 RAG

v0.4 完成后，项目会具备 RAG 的第一块地基：文档纯文本。

后续建议按以下阶段推进：

### v0.5 文本切块

目标：

- 增加 `ChunkService`。
- 将解析出的全文切成稳定 chunk。
- 返回 chunk 数量和预览。

链路：

```text
Parsed text
  -> ChunkService
  -> chunks
```

### v0.6 Embedding 与向量存储

目标：

- 增加 `EmbeddingService`。
- 增加 `VectorStore` 抽象。
- MVP 可先选择简单本地向量存储或直接进入 PostgreSQL + pgvector。

链路：

```text
chunks
  -> EmbeddingService
  -> vectors
  -> VectorStore
```

### v0.7 RAG 问答

目标：

- 增加 `RagService`。
- 根据用户问题检索相关 chunk。
- 将检索结果拼接进 LLM 上下文。
- 返回基于文件内容的答案。

链路：

```text
User question
  -> RagService
  -> VectorStore search
  -> relevant chunks
  -> LLMService
  -> answer
```

### 当前设计对 RAG 的支持点

v0.4 的 `DocumentParserService` 将成为 RAG 的上游输入：

```text
FileService
  -> DocumentParserService
  -> ChunkService
  -> EmbeddingService
  -> VectorStore
  -> RagService
```

关键原则：

- v0.4 只负责“抽文本”。
- v0.5 再负责“切文本”。
- v0.6 再负责“向量化和存储”。
- v0.7 再负责“检索增强问答”。

这样可以保证 MVP 每个阶段都有清晰验收结果，也避免一次性把解析、检索、LLM 和数据库全部耦合在一起。
