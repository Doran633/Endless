# v0.5 文本切块计划

> 本计划用于 v0.5 开发阶段。
> 目标是在不实现 LLM 文件问答、不实现 Embedding、不实现向量数据库、不实现 RAG 的前提下，完成文档解析结果到 chunks 的工程设计。

## 1. 当前状态

当前项目已经完成：

- v0.2 真实 LLM 聊天闭环。
- v0.3 真实文件上传闭环。
- v0.4 TXT / DOCX / 可复制文本型 PDF 文档解析闭环。
- v0.4.1 DOCX 表格解析增强。
- v0.4.2 北辰agent UI 简化优化。

当前主链路：

```text
用户上传文件
  -> FileService 保存到 backend/uploads/
  -> DocumentParserService 读取文件
  -> 提取纯文本
  -> 返回 text_preview 和 char_count
  -> 前端展示解析预览
```

当前尚未完成：

- 解析全文持久化。
- 文本切块。
- Embedding。
- 向量存储。
- RAG 检索。
- 基于文件的问答。

v0.5 的任务是补上 RAG 前置链路中的“文本切块”层。

## 2. 为什么不做临时单文件问答

不做临时单文件问答，是为了保持真实 RAG 工程路线。

临时单文件问答的做法是：

```text
解析全文
  -> 直接塞进 prompt
  -> 调用 LLM
  -> 返回答案
```

这种方案短期能看到效果，但会带来几个问题：

- 容易绕开 chunk、embedding、retrieval 等真正的 RAG 核心能力。
- 长文档会遇到上下文长度限制。
- 每次提问都发送全文，token 成本高。
- 没有检索过程，无法验证召回质量。
- 后续接 RAG 时，临时问答链路大概率需要拆掉。

因此 v0.5 不追求“马上能问文件”，而是继续沿着真实 RAG 链路推进：

```text
DocumentParserService
  -> ChunkService
  -> EmbeddingService
  -> VectorStore
  -> RagService
```

## 3. 文本切块的目标

v0.5 的目标是把解析出的纯文本切成稳定、可追踪、适合后续 embedding 的 chunks。

核心目标：

- 新增 `ChunkService`。
- 接收完整解析文本。
- 按固定策略切成多个 chunk。
- 每个 chunk 包含顺序、内容、字符数。
- 返回 chunk 数量和预览。
- 前端可以看到文件已完成切块。

v0.5 不做：

- LLM 文件问答。
- Embedding。
- 向量数据库。
- RAG 检索。
- 数据库持久化。
- 多文件知识库。

## 4. ChunkService 设计

### 4.1 职责

`ChunkService` 负责文本切块的业务边界：

- 接收解析后的全文。
- 清洗多余空白。
- 按策略切分文本。
- 为每个 chunk 生成 `chunk_index`。
- 统计 chunk 字符数。
- 返回 chunk 列表。

建议文件：

```text
backend/app/services/chunk_service.py
```

建议方法：

```text
chunk_text(text: str) -> ChunkResult
```

### 4.2 不做职责

`ChunkService` 不负责：

- 文件上传。
- 文档解析。
- Embedding 调用。
- 向量写入。
- RAG 检索。
- LLM 调用。
- 数据库持久化。

### 4.3 与现有服务关系

```text
FileService
  -> 保存原文件

DocumentParserService
  -> 提取纯文本

ChunkService
  -> 切分纯文本
```

`DocumentParserService` 不应直接包含 chunk 逻辑，避免解析服务越来越重。

## 5. chunk 数据结构

建议新增 Schema：

```text
DocumentChunk
  chunk_id: string
  file_id: string
  chunk_index: int
  content: string
  char_count: int
```

建议响应结构：

```text
ChunkFileResponse
  file_id: string
  status: "chunked"
  chunk_count: int
  chunks: DocumentChunk[]
```

MVP 阶段可以先不返回全部 chunk，只返回前几个预览：

```text
ChunkFileResponse
  file_id: string
  status: "chunked"
  chunk_count: int
  chunk_preview: DocumentChunk[]
```

原因：

- 大文档 chunk 数量可能很多。
- 前端只需要验证切块结果，不需要展示全文所有 chunk。
- 后续进入 embedding 时，chunk 全量应进入数据库或向量存储，而不是依赖前端保存。

## 6. API 设计

### 6.1 切块接口

建议接口：

```text
POST /api/v1/files/{file_id}/chunks
```

请求体：

```json
{
  "extension": "docx"
}
```

说明：

- 当前尚无数据库，后端仍无法只通过 `file_id` 查扩展名。
- v0.5 可沿用 v0.4 的临时做法，让前端传 `extension`。
- 后续引入数据库后，前端只传 `file_id`。

成功响应：

```json
{
  "code": 0,
  "message": "ok",
  "data": {
    "file_id": "uuid",
    "status": "chunked",
    "chunk_count": 3,
    "chunk_preview": [
      {
        "chunk_id": "uuid-0",
        "file_id": "uuid",
        "chunk_index": 0,
        "content": "第一段 chunk 内容...",
        "char_count": 500
      }
    ]
  }
}
```

### 6.2 为什么不复用 parse 接口

不建议把 chunk 塞进 `POST /files/{file_id}/parse`。

原因：

- parse 表示“抽文本”。
- chunk 表示“为 embedding 和 retrieval 准备文本单元”。
- 两个阶段职责不同。
- 后续 embedding 会依赖 chunk 结果，而不是 parse 预览。

保持独立 API 更利于后续演进。

## 7. 前端展示方案

### 7.1 文件中心最小改动

文件中心可以在已解析文件上增加“切块”按钮。

状态建议：

- `uploaded`：已上传。
- `processing`：解析中或切块中。
- `ready`：已解析。
- `chunked`：已切块。
- `failed`：失败。

如果不想立即扩展 `FileItem.status`，也可以新增字段：

```text
chunk_count?: number
chunk_preview?: DocumentChunk[]
```

更推荐扩展状态为 `chunked`，因为这能让用户清楚知道文件已经进入 RAG 前置阶段。

### 7.2 UI 展示

已解析文件：

- 显示“切块”按钮。

切块完成后：

- 显示 `chunk_count`。
- 提供“查看 chunk 预览”。
- 预览前 3 个 chunk。

提示文案：

```text
已完成文本切块。Embedding 和 RAG 问答将在后续阶段开放。
```

### 7.3 暂不进入聊天区

v0.5 不在聊天输入框中加入文件问答入口。

原因：

- 还没有 embedding 和 retrieval。
- 用户看到聊天区文件问答入口会误以为 RAG 已完成。
- 当前更适合在文件中心展示 RAG 前置处理状态。

## 8. chunk 策略选择

### 8.1 MVP 推荐策略

推荐先使用字符数切块：

```text
chunk_size = 800 字符
chunk_overlap = 120 字符
```

原因：

- 实现简单。
- 可预测。
- 适合中文文档 MVP。
- 不依赖 tokenizer。
- 后续可以替换成 token-aware chunker。

### 8.2 切块流程

```text
normalize text
  -> 按段落合并
  -> 按 chunk_size 滑动切分
  -> 每个 chunk 保留 overlap
  -> 过滤空 chunk
```

### 8.3 为什么需要 overlap

没有 overlap 时，关键句子可能被切断。

例如：

```text
... 项目风险包括：
1. 数据缺失
2. 依赖未安装
```

如果刚好在“项目风险包括”后切断，后一个 chunk 会失去上下文。

overlap 可以让相邻 chunk 保留少量上下文，提高后续检索和回答质量。

### 8.4 表格文本如何切

v0.4.1 已把 DOCX 表格输出为：

```text
表格行1: 渠道 | 预算 | 转化率
表格行2: 抖音 | 10000 | 3.2%
```

v0.5 暂时可以按普通文本切。

后续优化：

- 避免把同一表格行切断。
- 按表格行作为 chunk 边界。
- 对表格增加 metadata。

## 9. 风险和技术债

### 9.1 没有数据库

当前 chunk 结果如果只返回前端，刷新后会丢失。

MVP 可接受，但后续 embedding 阶段必须决定 chunk 存储位置。

建议后续：

- `documents` 表保存文件元数据。
- `document_chunks` 表保存 chunk 文本。
- 向量库保存 chunk embedding。

### 9.2 当前仍需传 extension

因为没有数据库，chunk 接口仍需要前端传 `extension`。

这是延续 v0.4 的临时技术债。

后续应改为：

```text
POST /api/v1/files/{file_id}/chunks
```

后端自行查询文件元数据。

### 9.3 字符切块不是最终方案

字符数切块简单，但不是最优：

- 不理解 token。
- 可能切断句子。
- 可能切断表格行。
- 英文和中文 token 密度不同。

但对于当前教学型 MVP，它是合理起点。

### 9.4 前端状态会继续膨胀

如果把 parsed、chunked、embedding 状态都存在前端内存，状态会越来越复杂。

后续需要后端文件状态 API 承担真实状态管理。

### 9.5 不应过早抽象复杂策略

不要在 v0.5 就实现：

- 多种 chunk 策略配置 UI。
- tokenizer-based chunk。
- semantic chunk。
- heading-aware chunk。
- table-aware chunk。

这些可以等 RAG 基础链路跑通后再优化。

## 10. 测试方案

### 10.1 后端基础验证

运行：

```text
python -m compileall app
```

预期：

- Python 编译通过。

### 10.2 ChunkService 单元测试思路

测试短文本：

- 输入短于 `chunk_size` 的文本。
- 预期只生成 1 个 chunk。

测试长文本：

- 输入大于 `chunk_size` 的文本。
- 预期生成多个 chunk。
- 相邻 chunk 有 overlap。

测试空文本：

- 输入空字符串。
- 预期返回错误或空 chunk 结果。

测试中文文本：

- 输入中文段落。
- 预期 char_count 正确。

测试表格文本：

- 输入 v0.4.1 的表格行文本。
- 预期 chunk 内容保留表格行格式。

### 10.3 API 测试

流程：

```text
1. 上传 TXT / DOCX / PDF
2. 调用 parse 接口确认可解析
3. 调用 chunk 接口
4. 检查 chunk_count
5. 检查 chunk_preview
```

预期：

- `status=chunked`。
- `chunk_count > 0`。
- 每个 chunk 有 `chunk_id`、`chunk_index`、`content`、`char_count`。

### 10.4 前端验证

运行：

```text
npm exec tsc -- --noEmit
```

浏览器验证：

1. 打开文件中心。
2. 上传 TXT / DOCX / PDF。
3. 点击解析。
4. 点击切块。
5. 查看 chunk 数量。
6. 查看 chunk 预览。
7. 确认页面没有出现文件问答入口。

## 11. 后续如何接入 Embedding 和 RAG

v0.5 完成后，后续路线是：

```text
Parsed text
  -> ChunkService
  -> chunks
  -> EmbeddingService
  -> vectors
  -> VectorStore
  -> RagService
  -> LLMService
```

### v0.6 Embedding

目标：

- 增加 `EmbeddingService`。
- 接收 chunk content。
- 返回 embedding vector。
- 暂时可以先 mock embedding，再接真实 embedding API。

### v0.7 向量存储

目标：

- 增加 `VectorStore` 抽象。
- 决定使用本地简单存储、PostgreSQL + pgvector，或其他向量库。
- 保存 chunk 与 embedding 的关系。

### v0.8 RAG 检索

目标：

- 用户问题生成 query embedding。
- 检索相关 chunk。
- 返回 top_k chunk。

### v0.9 文件问答

目标：

- 将检索到的 chunk 拼入 LLM prompt。
- 返回基于文件内容的答案。
- 前端开放真正的文件问答入口。

关键原则：

- v0.5 只做 chunk。
- v0.6 再做 embedding。
- v0.7 再做存储。
- v0.8 再做检索。
- v0.9 再做问答。

这样可以保证每一步都有清晰工程边界，也能真正掌握 RAG 应用的完整链路。
