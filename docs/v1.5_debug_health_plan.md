# v1.5.5 Local Debug Health Plan

## 1. 当前问题

当前项目已经支持真实 LLM、真实 embedding、RAG、邀请码访问和 VPS 部署资产。但在本地调试中出现过一个非常典型的问题：

```text
.env 已经修改为新的 embedding 配置
-> 但 8000 上仍有旧后端进程
-> 前端默认请求 8000
-> 新上传文件仍然生成 mock-embedding / 16
```

这个问题的根源不是 RAG 逻辑错误，也不是 SiliconFlow API 配置错误，而是：

- 后端进程启动时读取 `.env`。
- 旧后端不会自动感知 `.env` 修改。
- 前端默认代理到 `127.0.0.1:8000`。
- Windows + `uvicorn --reload` 可能出现父子进程、端口残留、PID 不一致或权限不可见。
- 当前缺少一个简单接口来确认“正在响应请求的后端实际读到了什么配置”。

因此，v1.5.5 的重点不是继续加 AI 功能，而是提升本地调试和部署前验证能力。

## 2. 为什么需要 /health/config

当前已有：

```text
GET /health
```

它只能说明后端活着，但不能说明：

- 当前后端读到的是哪个 LLM model。
- 当前后端读到的是 `mock` 还是 `openai` embedding provider。
- 当前 embedding model 是不是 `BAAI/bge-m3`。
- 当前 embedding dimension 是不是 `1024`。
- 当前是否启用了邀请码。
- 当前是否仍在旧单口令兼容模式。
- 当前上传目录、vector_store 目录、SQLite 路径是否指向预期位置。

新增：

```text
GET /health/config
```

可以让开发者快速确认当前运行进程的非敏感配置，避免继续依赖：

- 手动读 `.env`
- 查旧 JSON 索引
- 猜测前端连的是哪个后端
- 反复杀端口

## 3. API 设计

新增接口：

```text
GET /health/config
```

建议不放在 `/api/v1/*` 下，原因：

- `/health` 已经是健康检查路径。
- 该接口用于调试当前后端运行状态。
- 不应该被邀请码保护挡住，否则邀请码配置错误时无法诊断。

但它必须只返回非敏感信息。

建议返回：

```json
{
  "app_name": "Beichen Agent Backend",
  "llm_provider": "openai",
  "llm_model": "deepseek-v4-flash",
  "embedding_provider": "openai",
  "embedding_model": "BAAI/bge-m3",
  "embedding_dimension": 1024,
  "database_path": "data/beichen.db",
  "upload_dir": "uploads",
  "vector_store_dir": "vector_store",
  "access_control": {
    "enabled": true,
    "mode": "invite_codes",
    "header": "X-Beichen-Access",
    "invite_code_count": 5
  }
}
```

## 4. 返回字段设计

建议字段：

- `app_name`
  - 用于确认旧 WorkBuddy 命名是否仍在运行。
- `llm_provider`
  - 例如 `mock` 或 `openai`。
- `llm_model`
  - 例如 `deepseek-v4-flash`。
- `embedding_provider`
  - 例如 `mock` 或 `openai`。
- `embedding_model`
  - 例如 `BAAI/bge-m3`。
- `embedding_dimension`
  - 例如 `1024`。
- `database_path`
  - 只返回路径，不返回数据内容。
- `upload_dir`
  - 只返回路径，不返回文件列表。
- `vector_store_dir`
  - 只返回路径，不返回 chunk 或向量内容。
- `access_control.enabled`
  - 是否启用访问保护。
- `access_control.mode`
  - `disabled`
  - `invite_codes`
  - `legacy_password`
- `access_control.header`
  - 当前请求头名称。
- `access_control.invite_code_count`
  - 邀请码数量，只返回数量，不返回真实邀请码。

不返回：

- `OPENAI_API_KEY`
- `EMBEDDING_API_KEY`
- `APP_ACCESS_PASSWORD`
- `APP_INVITE_CODES`
- 上传文件名列表
- 文档原文
- chunks
- embeddings
- 聊天消息
- SQLite 数据内容

## 5. 安全边界

`/health/config` 是调试辅助接口，不是管理后台。

它可以暴露：

- provider 类型
- model 名称
- embedding 维度
- 本地路径
- 邀请码数量

它不能暴露：

- API Key
- 真实邀请码
- 访问口令
- 用户上传内容
- 向量索引内容
- 聊天记录

部署到公网时，需要权衡是否保留该接口公开访问。

MVP 建议：

- 本地开发默认保留。
- 小范围部署时可以保留，因为不含敏感密钥。
- 如果未来公开服务，可以增加配置 `DEBUG_HEALTH_ENABLED=false` 来关闭。

v1.5.5 暂不新增关闭开关，先保持简单。

## 6. 前端是否需要展示

v1.5.5 不建议做复杂前端展示。

原因：

- 当前目标是本地调试和部署前验证。
- 开发者直接打开 `/health/config` 已经足够。
- 增加前端诊断页会扩大 UI 范围。

可选轻量方案：

- 暂不在前端展示。
- 文档中说明访问：

```text
http://127.0.0.1:8000/health/config
```

或当使用备用端口：

```text
http://127.0.0.1:8001/health/config
```

后续如果需要，可以在设置页或调试页展示，但不在 v1.5.5 做。

## 7. 测试方案

基础验证：

- `scripts/check-local.ps1`
- `python -m compileall app`
- `npm exec tsc -- --noEmit`

API 验证：

1. 启动后端。
2. 请求：

```powershell
Invoke-RestMethod http://127.0.0.1:8000/health/config
```

3. 确认返回：

```text
embedding_provider = openai
embedding_model = BAAI/bge-m3
embedding_dimension = 1024
access_control.mode = invite_codes
```

4. 修改 `.env` 后重启后端。
5. 再次访问 `/health/config`，确认配置变化已生效。

安全验证：

- 确认响应中不包含 `sk-`。
- 确认响应中不包含真实 `APP_INVITE_CODES`。
- 确认响应中不包含 `APP_ACCESS_PASSWORD`。
- 确认响应中不包含上传文件内容。

旧进程诊断验证：

- 如果 8000 返回旧配置，而 8001 返回新配置，说明浏览器连接到了旧后端。
- 这可以直接定位“旧进程仍在响应请求”的问题。

## 8. 后续如何辅助部署上线

上线前，可以通过：

```text
https://your-domain.com/health/config
```

确认生产后端实际配置：

- 是否使用真实 LLM。
- 是否使用真实 embedding。
- 是否开启邀请码保护。
- 是否指向生产 SQLite 路径。
- 是否指向生产 uploads 路径。
- 是否指向生产 vector_store 路径。

这比只看 `.env` 更可靠，因为 `.env` 只是文件，`/health/config` 反映的是“当前正在运行的后端进程实际读到的配置”。

## 9. 对未来监测进程有什么帮助

v1.5.5 不能直接避免端口占用。

它不能做到：

- 自动杀掉旧进程。
- 自动释放 8000。
- 自动判断哪个 PID 应该结束。
- 自动解决 Windows `TIME_WAIT` 或权限问题。

但它能有效降低调试混乱：

- 快速确认当前后端是否读到新 `.env`。
- 快速确认浏览器打到的端口对应哪套配置。
- 避免误以为 API Key、embedding provider 或 RAG 逻辑有问题。
- 当 8000 和 8001 同时存在时，可以分别访问 `/health/config` 判断哪个是旧后端。

真正要减少端口占用，还需要后续改进：

- 优化 `stop-local.ps1` 对 `uvicorn --reload` 父子进程的处理。
- `start-local.ps1` 启动前确认端口没有 `LISTENING`。
- 尽量在本地配置调试时不用 `--reload`。
- 增加脚本输出当前监听端口、PID 和后端配置摘要。

因此，v1.5.5 的价值是“让问题更容易被看见和定位”，不是“自动消灭进程占用”。
