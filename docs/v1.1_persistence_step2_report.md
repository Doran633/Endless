# v1.1.2 文件处理状态持久化报告

## 1. 本次完成内容

v1.1.2 在 v1.1.1 文件元数据持久化基础上，补齐了文件处理状态持久化。

本次实现：

- 解析成功后更新 SQLite `files` 表：
  - `status = ready`
  - `text_preview`
  - `char_count`
- 切块成功后更新 SQLite `files` 表：
  - `status = chunked`
  - `chunk_count`
- 向量化成功后更新 SQLite `files` 表：
  - `status = embedded`
  - `chunk_count`
  - `embedding_count`
  - `embedding_dimension`
  - `embedding_model`
- 本地 VectorStore 索引保存成功后更新 SQLite `files` 表：
  - `status = indexed`
  - `chunk_count`
  - `embedding_count`
  - `embedding_dimension`
  - `embedding_model`
  - `vector_store_path`
- 处理失败时尽量更新：
  - `status = failed`
  - `error_message`
- `GET /api/v1/files` 可以返回更完整的处理状态。

本次没有实现：

- PostgreSQL。
- pgvector。
- 文件删除 API。
- 聊天会话持久化。
- 聊天消息持久化。
- 多用户、企业权限、Agent。
- embeddings 入库。

## 2. 修改文件职责

### `backend/app/repositories/file_repository.py`

新增文件状态更新方法：

- `update_parsed()`
- `update_chunked()`
- `update_embedded()`
- `update_indexed()`
- `touch_failed()`

职责：

- 只负责 SQLite `files` 表的读写。
- 不解析文件。
- 不切块。
- 不调用 embedding。
- 不写 VectorStore JSON。

设计原因：

- Repository 层隔离数据库细节。
- Service 层只需要表达业务状态变化，不直接操作 ORM 字段。

### `backend/app/services/document_parser_service.py`

调整：

- `parse()` 成功后写入 parsed 状态。
- `parse_text()` 失败时记录 failed。

职责：

- 继续负责 TXT / DOCX / PDF 文本解析。
- 成功后把解析结果摘要同步给数据库。

设计原因：

- 文档解析结果的来源是 `DocumentParserService`，所以它最清楚何时可以标记为 parsed / ready。
- 数据库只保存预览和字符数，不保存完整文档文本。

### `backend/app/services/chunk_service.py`

调整：

- `chunk_text()` 成功后写入 chunked 状态。
- 新增 `create_file_chunks()`，用于复合流程中记录切块失败状态。

职责：

- 继续负责文本切块。
- 成功后保存 chunk 数量。

设计原因：

- chunk 内容仍不入库。
- 当前只需要数据库知道“这个文件已经切成多少块”。

### `backend/app/services/embedding_service.py`

调整：

- `embed_chunks()` 成功后写入 embedded 状态。
- 新增 `embed_file_vectors()`，用于复合流程中记录 embedding 失败状态。

职责：

- 继续负责 embedding provider 调用。
- 成功后保存 embedding 数量、维度和模型名。

设计原因：

- embeddings 本体仍保存在本地 JSON VectorStore 或运行时返回中，不进入 SQLite。
- SQLite 只保存可展示和可恢复的状态摘要。

### `backend/app/services/vector_store_service.py`

调整：

- `save_file_vectors()` 成功写入 JSON 索引后，更新 indexed 状态和索引路径。
- 写入 JSON 索引失败时记录 failed。

职责：

- 继续负责本地 JSON VectorStore。
- 成功后告诉数据库该文件已经 indexed。

设计原因：

- RAG 主链路仍从 `backend/vector_store/` 读取 chunks + embeddings。
- 数据库只负责记录索引是否存在以及索引路径。

### `backend/app/api/v1/files.py`

调整：

- embedding 和 vector-store 复合流程改用带 file_id 的 Service 编排方法：
  - `ChunkService.create_file_chunks()`
  - `EmbeddingService.embed_file_vectors()`

职责：

- API 层仍只编排 HTTP 请求和 Service 调用。
- 不直接读写数据库。

设计原因：

- 复合流程中的失败也需要落到数据库状态。
- 状态写入仍由 Service / Repository 负责。

### `docs/status.md`

更新当前版本为 `v1.1.2`。

新增说明：

- 文件处理状态持久化已完成。
- 文件删除、聊天会话和消息持久化仍未完成。

## 3. 状态写入数据库的调用链路

### 3.1 解析状态

```text
POST /api/v1/files/{file_id}/parse
  -> files.py parse_file()
  -> DocumentParserService.parse()
  -> DocumentParserService.parse_text()
  -> FileRepository.update_parsed()
  -> SQLite files 表
```

成功后数据库记录：

```text
status = ready
text_preview = 文本预览
char_count = 文档字符数
```

### 3.2 切块状态

```text
POST /api/v1/files/{file_id}/chunks
  -> files.py chunk_file()
  -> DocumentParserService.parse_text()
  -> ChunkService.chunk_text()
  -> FileRepository.update_chunked()
  -> SQLite files 表
```

成功后数据库记录：

```text
status = chunked
chunk_count = chunks 数量
```

### 3.3 向量化状态

```text
POST /api/v1/files/{file_id}/embeddings
  -> files.py embed_file()
  -> DocumentParserService.parse_text()
  -> ChunkService.create_file_chunks()
  -> EmbeddingService.embed_chunks()
  -> EmbeddingProvider.embed_texts()
  -> FileRepository.update_embedded()
  -> SQLite files 表
```

成功后数据库记录：

```text
status = embedded
chunk_count = chunks 数量
embedding_count = embeddings 数量
embedding_dimension = embedding 维度
embedding_model = 当前 embedding 模型
```

### 3.4 索引状态

```text
POST /api/v1/files/{file_id}/vector-store
  -> files.py store_file_vectors()
  -> DocumentParserService.parse_text()
  -> ChunkService.create_file_chunks()
  -> EmbeddingService.embed_file_vectors()
  -> VectorStoreService.save_file_vectors()
  -> backend/vector_store/{file_id}.json
  -> FileRepository.update_indexed()
  -> SQLite files 表
```

成功后数据库记录：

```text
status = indexed
chunk_count = chunks 数量
embedding_count = embeddings 数量
embedding_dimension = embedding 维度
embedding_model = 当前 embedding 模型
vector_store_path = 本地 JSON 索引路径
```

## 4. 刷新后状态恢复链路

```text
FileCenter 打开
  -> fileStore.loadFiles()
  -> fileApi.listFiles()
  -> GET /api/v1/files
  -> FileService.list_files()
  -> FileRepository.list_files()
  -> SQLite files 表
  -> 返回完整文件状态
  -> 前端展示 uploaded / ready / chunked / embedded / indexed / failed
```

v1.1.2 后，刷新文件中心可以恢复：

- 文件基础信息。
- 解析状态和字符数。
- 文本预览。
- 切块数量。
- embedding 数量和维度。
- embedding 模型。
- indexed 状态。
- 本地索引路径。
- failed 错误信息。

## 5. 错误处理方式

本次采用两类策略：

### 5.1 业务处理失败

例如：

- 文件不存在。
- PDF 没有可复制文本。
- 文本为空，无法切块。
- embedding provider 调用失败。
- 本地 JSON 索引写入失败。

处理方式：

```text
记录 failed 状态
  -> 保存 error_message
  -> 继续抛出原始错误
  -> 前端收到原有错误响应
```

这样做的原因：

- 数据库可以恢复失败状态。
- 前端仍能获得具体失败原因。
- 不会把原始错误吞掉。

### 5.2 failed 状态记录本身失败

如果记录 failed 时数据库也出错，本次选择不覆盖原始异常。

原因：

- 用户和调用方最需要知道的是原始业务错误。
- 数据库写失败是额外问题，不应该掩盖原始失败原因。

## 7. 剩余问题

当前仍未完成：

- 文件删除 API。
- 聊天会话持久化。
- 聊天消息持久化。
- 当前会话绑定文件持久化。
- 数据库 migration。
- 自动化测试目录。

当前仍保留的技术债：

- 仍使用 SQLite + create_all，不适合复杂生产迁移。
- `backend/vector_store/` JSON 与 SQLite 之间仍可能出现手动删除导致的不一致。
- 文件中心上传仍是手动处理流程，聊天侧上传才是自动处理流程。

建议下一步进入 v1.1.3：文件中心上传自动处理体验优化。

目标：

- 文件中心上传后自动执行：
  - 上传
  - 解析
  - 切块
  - embedding
  - vector-store
- 复用当前 `fileStore.ingestFile()`。
