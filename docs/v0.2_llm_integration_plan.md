# v0.2 LLM 聊天集成计划

> 本计划用于 v0.2 开发阶段。
> 目标是完成真实 LLM 聊天闭环。
> 本阶段保持现有架构，不增加复杂设计，不扩展企业功能。

## 1. 当前问题分析

当前项目已经具备基础后端聊天骨架：

- `LLMProvider`
- `MockLLMProvider`
- `OpenAIProvider`
- `LLMService`
- `ChatService`
- `POST /api/v1/chat`

但还没有形成完整的真实聊天闭环。

### 1.1 后端配置不够稳定

当前 `LLMService` 只判断：

```text
LLM_PROVIDER=openai -> OpenAIProvider
其他值 -> MockLLMProvider
```

问题：

- 如果配置写错，例如 `LLM_PROVIDER=opena`，系统会静默回退到 Mock。
- 演示时可能误以为已经接入真实模型。
- 当前缺少明确的配置检查和失败提示。

### 1.2 LLM 错误没有统一处理

当前 `OpenAIProvider` 在以下情况会抛出 `RuntimeError`：

- `OPENAI_API_KEY` 未配置。
- OpenAI-compatible API 请求失败。
- 上游返回结构异常。

问题：

- API 层没有捕获这些错误。
- 前端可能收到未规范化的 500。
- 不符合当前 `{ code, message, data }` 的响应约定。

### 1.3 前端仍然使用 Mock 回复

当前 `frontend/src/stores/chatStore.ts` 仍然调用：

```text
generateAIResponse()
```

问题：

- 用户在网页里聊天时没有经过后端。
- 当前真实链路只存在于后端接口层，产品界面没有联通。
- 后续文件问答和 RAG 如果继续沿用 Mock，会造成前后端业务来源分裂。

### 1.4 当前 v0.2 应控制范围

v0.2 只解决真实 LLM 聊天闭环：

```text
Frontend
  -> POST /api/v1/chat
  -> FastAPI
  -> ChatService
  -> LLMService
  -> OpenAIProvider / MockLLMProvider
  -> 返回 answer
  -> Frontend 展示回答
```

v0.2 不做：

- 文件上传。
- RAG。
- Agent。
- 企业登录。
- 企业权限。
- PPT。
- 多租户。
- 复杂任务队列。

## 2. 修改文件列表

### 2.1 后端计划修改

#### `backend/app/core/config.py`

修改原因：

- 稳定 LLM 配置来源。
- 明确 `LLM_PROVIDER`、`LLM_MODEL`、`OPENAI_API_KEY`、`OPENAI_BASE_URL` 等配置含义。

计划修改：

- 保留现有 settings 结构。
- 明确默认 provider 为 `mock`。
- 增加可配置 timeout，例如 `LLM_TIMEOUT_SECONDS`。

#### `backend/app/core/errors.py`

修改原因：

- 当前缺少应用级异常类型。

计划新增：

- `AppError`
- `LLMConfigError`
- `LLMProviderError`

保持简单：

- 不设计复杂错误继承树。
- 只覆盖 v0.2 需要的 LLM 配置和调用错误。

#### `backend/app/core/exception_handlers.py`

修改原因：

- 将应用错误统一转换为 `{ code, message, data }`。

计划新增：

- FastAPI exception handler。
- 将 LLM 配置错误和 LLM 调用错误转为稳定 JSON 响应。

#### `backend/app/main.py`

修改原因：

- 注册全局异常处理。

计划修改：

- 引入并注册 v0.2 所需 exception handlers。
- 不调整路由结构。

#### `backend/app/services/llm_service.py`

修改原因：

- 当前 provider 配置错误会静默回退到 Mock。

计划修改：

- 使用简单 provider registry：

```text
mock -> MockLLMProvider
openai -> OpenAIProvider
```

- 未知 provider 直接抛出 `LLMConfigError`。
- 保持 `ChatService` 不关心具体 provider。

#### `backend/app/llm/openai_provider.py`

修改原因：

- 当前错误处理粗糙，timeout 写死。

计划修改：

- 使用配置中的 timeout。
- API key 缺失时抛出 `LLMConfigError`。
- 请求失败时抛出 `LLMProviderError`。
- 上游响应结构异常时抛出 `LLMProviderError`。

#### `backend/app/api/v1/chat.py`

修改原因：

- 当前可继续使用，但需要确保错误由全局 handler 处理。

计划修改：

- 暂不做复杂依赖注入。
- 可保持 `ChatService().answer()`。
- v0.2 不扩展 `file_id`。

### 2.2 前端计划修改

#### `frontend/src/api/chatApi.ts`

修改原因：

- 当前没有真实聊天 API client。

计划新增：

- `sendChatMessage(message: string)`。
- 请求 `POST /api/v1/chat`。
- 解析 `{ code, message, data }`。
- 后端错误转为前端可展示错误。

#### `frontend/src/stores/chatStore.ts`

修改原因：

- 当前仍直接调用 Mock 回复。

计划修改：

- `sendMessage()` 改为调用 `chatApi.sendChatMessage()`。
- 成功时展示后端返回的 `answer`。
- 失败时追加一条 assistant 错误消息或设置错误状态。
- 保留会话标题更新和本地消息追加逻辑。
- Mock 数据可以继续用于初始化会话，不再作为默认 AI 回复来源。

#### `frontend/.env` 或 `frontend/.env.example`

修改原因：

- 前端需要知道后端 API Base URL。

计划新增或更新：

```text
VITE_API_BASE_URL=http://localhost:8000
```

如果当前项目暂不引入 `.env.example`，也可以先在 `chatApi.ts` 中使用默认值：

```text
import.meta.env.VITE_API_BASE_URL || "http://localhost:8000"
```

## 3. 配置方案

### 3.1 后端环境变量

建议 v0.2 使用以下配置：

```text
LLM_PROVIDER=mock
LLM_MODEL=gpt-4o-mini
LLM_TIMEOUT_SECONDS=30
OPENAI_API_KEY=
OPENAI_BASE_URL=https://api.openai.com/v1
```

真实 LLM 调用时：

```text
LLM_PROVIDER=openai
LLM_MODEL=gpt-4o-mini
OPENAI_API_KEY=your_api_key
OPENAI_BASE_URL=https://api.openai.com/v1
```

说明：

- 本地无 key 开发时使用 `mock`。
- 演示真实模型时显式配置 `openai`。
- 如果 `LLM_PROVIDER=openai` 但缺少 `OPENAI_API_KEY`，后端应返回明确错误，不应静默回退 Mock。

### 3.2 前端环境变量

建议：

```text
VITE_API_BASE_URL=http://localhost:8000
```

调用目标：

```text
POST ${VITE_API_BASE_URL}/api/v1/chat
```

### 3.3 配置原则

- provider 默认值可以是 `mock`，方便本地开发。
- 显式配置错误必须快速失败。
- API key 只存在后端环境变量。
- 前端不能保存或暴露 LLM API key。
- v0.2 不做前端模型选择 UI。

## 4. API 调用流程

### 4.1 普通聊天流程

```text
用户输入消息
  -> frontend/src/stores/chatStore.ts
  -> frontend/src/api/chatApi.ts
  -> POST /api/v1/chat
  -> backend/app/api/v1/chat.py
  -> ChatService.answer()
  -> LLMService.chat()
  -> OpenAIProvider.chat() 或 MockLLMProvider.chat()
  -> 返回 LLMResponse
  -> ChatService 返回 { answer }
  -> API 返回 { code, message, data }
  -> 前端展示 assistant 消息
```

### 4.2 请求格式

```json
{
  "message": "你好，介绍一下你自己"
}
```

### 4.3 成功响应

```json
{
  "code": 0,
  "message": "ok",
  "data": {
    "answer": "你好，我是你的 AI 助手..."
  }
}
```

### 4.4 前端展示策略

- 用户发送消息后，立即追加 user message。
- 请求进行中，保持 `isStreaming=true`。
- 请求成功，追加 assistant message。
- 请求失败，追加一条 assistant 错误消息，提示用户稍后重试或检查配置。
- 请求结束后，设置 `isStreaming=false`。

v0.2 不实现真正 streaming，只沿用当前 loading 状态命名。

## 5. 错误处理方案

### 5.1 错误类型

v0.2 只需要三类错误：

| 错误 | 场景 | 建议 code |
| --- | --- | --- |
| `LLMConfigError` | provider 未知、API key 缺失 | `43001` |
| `LLMProviderError` | 上游 API 请求失败、响应异常 | `43002` |
| `ValidationError` | 用户请求参数不合法 | FastAPI 默认 422 |

### 5.2 后端错误响应

配置错误示例：

```json
{
  "code": 43001,
  "message": "OPENAI_API_KEY is not configured",
  "data": null
}
```

调用错误示例：

```json
{
  "code": 43002,
  "message": "LLM provider request failed",
  "data": null
}
```

### 5.3 前端错误展示

前端不要展示堆栈信息。

建议展示：

```text
AI 回复失败，请稍后重试或检查后端 LLM 配置。
```

如果后端返回明确业务错误，可以追加：

```text
错误原因：OPENAI_API_KEY is not configured
```

### 5.4 不做的错误处理

v0.2 暂不做：

- 自动重试。
- 熔断。
- 多 provider fallback。
- 请求队列。
- 分布式 tracing。

## 6. 测试方案

### 6.1 后端手动验证

Mock Provider：

```text
LLM_PROVIDER=mock
POST /api/v1/chat
```

预期：

- 返回 `code=0`。
- `data.answer` 有内容。

OpenAI Provider 配置缺失：

```text
LLM_PROVIDER=openai
OPENAI_API_KEY=
POST /api/v1/chat
```

预期：

- 返回稳定错误响应。
- 不出现未处理 500。
- 不静默回退 Mock。

OpenAI Provider 真实调用：

```text
LLM_PROVIDER=openai
OPENAI_API_KEY=有效 key
POST /api/v1/chat
```

预期：

- 返回真实模型回答。
- `data.answer` 可以在前端展示。

### 6.2 后端自动化测试

建议新增最小测试：

- `GET /health` 返回正常。
- `POST /api/v1/chat` 在 mock provider 下返回成功。
- 未知 `LLM_PROVIDER` 返回配置错误。
- `LLM_PROVIDER=openai` 且缺少 key 返回配置错误。

测试原则：

- 不在自动化测试中真实调用 OpenAI。
- OpenAIProvider 的网络请求可以用 mock 替代。
- v0.2 测试只覆盖聊天闭环，不覆盖文件/RAG。

### 6.3 前端验证

本地启动前端和后端后：

1. 打开 Web 页面。
2. 输入一条普通问题。
3. 确认浏览器 Network 出现 `POST /api/v1/chat`。
4. 确认后端收到请求。
5. 确认页面展示后端返回的 answer。
6. 关闭后端或配置错误时，确认前端展示错误消息。

### 6.4 类型检查

前端完成修改后运行：

```text
npm exec tsc -- --noEmit
```

后端完成修改后运行：

```text
python -m compileall app
```

如果后续加入 pytest，再运行：

```text
pytest
```

## 7. v0.2 完成标准

v0.2 完成后应满足：

- 后端支持稳定的 `mock` 和 `openai` provider 配置。
- 配置错误不会静默回退。
- LLM 调用错误返回统一 JSON。
- 前端聊天不再默认使用 Mock AI 回复。
- 用户在网页输入问题后，可以经过后端获得 AI 回答。
- 无 API key 时仍可通过 `mock` provider 本地开发。
- 不引入企业功能、RAG、文件上传或复杂架构。
