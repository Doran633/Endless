# v1.7.5 Semi-Automated VPS Deploy Plan

## 1. 当前问题

当前服务器部署已经跑通，但每次更新仍然依赖手动执行多条命令：

```text
SSH 登录服务器
-> cd /opt/beichen-agent/app
-> git pull
-> 安装后端依赖
-> 后端 compileall
-> 安装前端依赖
-> 前端 build
-> 拷贝 dist 到 frontend_dist
-> 重启 beichen-agent
-> nginx -t / reload
-> health 检查
```

这个流程对学习阶段很有价值，但上线试用后会带来几个风险：

- 步骤多，容易漏掉前端 build 或后端 restart。
- 出错时不知道停在哪一步。
- 更新前可能忘记备份 runtime 数据。
- 每次都手敲命令，容易复制错目录或权限。
- 服务器和 GitHub 代码版本不容易快速确认。

## 2. 为什么选择半自动

当前项目最多 1-5 人可信试用，不需要马上引入完整 CI/CD。

更合理的下一步是：

```text
本地开发和测试
-> git push 到 GitHub
-> SSH 登录 VPS
-> 在服务器执行一条 deploy 脚本
-> 脚本自动完成拉取、构建、重启、检查
```

这种方案仍然保留人工确认，但把重复步骤交给脚本，适合当前项目阶段。

## 3. 不选择全自动 CI/CD 的原因

暂不做 GitHub Actions 自动部署、webhook 或 Docker，是因为：

- 当前服务器只有一个小型 VPS，架构简单。
- 生产环境变量、SQLite、uploads、vector_store 都在服务器本地，需要谨慎处理。
- 自动部署一旦配置不当，可能在错误代码 push 后直接影响线上。
- 现在更需要“可理解、可手动干预”的部署流程，而不是复杂自动化。

后续项目更稳定后，可以再升级到 GitHub Actions + SSH deploy。

## 4. 目标状态

v1.7.5 目标是新增一个 Ubuntu VPS 脚本模板：

```text
deploy/scripts/deploy-vps.sh.example
```

执行后自动完成：

1. 检查当前目录是否为 `/opt/beichen-agent/app`。
2. 检查 Git 工作区是否干净。
3. 显示当前 commit。
4. 可选执行 runtime 备份。
5. 拉取 GitHub `main`。
6. 安装后端依赖。
7. 运行后端 `compileall`。
8. 安装前端依赖。
9. 运行前端 build。
10. 同步 `frontend/dist` 到 `/opt/beichen-agent/frontend_dist`。
11. 修正文件权限。
12. 重启 `beichen-agent` systemd 服务。
13. 检查 `systemctl status`。
14. 检查 `/health`。
15. 检查 `/health/config`。
16. 检查 `nginx -t`。
17. reload Nginx。
18. 输出部署前后 commit。

## 7. 脚本设计

建议命令：

```bash
cd /opt/beichen-agent/app
sudo bash deploy/scripts/deploy-vps.sh.example
```

脚本可以支持参数：

```bash
sudo bash deploy/scripts/deploy-vps.sh.example --skip-backup
```

默认行为建议：

- 默认先备份 runtime。
- 如果备份脚本不存在，则给出明确错误并停止。
- 如果用户指定 `--skip-backup`，则跳过备份，但输出醒目提醒。

## 8. 推荐部署流程

本地：

```powershell
git status
git add .
git commit -m "..."
git push origin main
```

服务器：

```bash
ssh root@your-server-ip
cd /opt/beichen-agent/app
sudo bash deploy/scripts/deploy-vps.sh.example
```

浏览器：

```text
打开公网 IP 或域名
输入邀请码
测试普通聊天、文件上传、RAG 问答
```

## 9. 安全边界

脚本不应该做：

- 不提交真实 API Key。
- 不提交真实邀请码。
- 不删除 `/opt/beichen-agent/runtime`。
- 不删除 `/opt/beichen-agent/backups`。
- 不执行数据库迁移。
- 不自动修改 Nginx 域名配置。
- 不自动申请 HTTPS。
- 不把日志、上传文件、数据库打包进 Git。

## 10. 失败处理策略

建议脚本启用：

```bash
set -euo pipefail
```

含义：

- 任一步失败，脚本立刻停止。
- 避免前端 build 失败后仍然覆盖线上 dist。
- 避免后端编译失败后仍然重启服务。

关键检查点：

- `git pull` 失败：停止，提示检查网络或 GitHub。
- `pip install` 失败：停止，提示检查 Python venv。
- `compileall` 失败：停止，不重启后端。
- `npm install` / `npm run build` 失败：停止，不覆盖 `frontend_dist`。
- `systemctl restart` 失败：停止，提示查看 `journalctl`。
- `/health` 失败：停止，提示后端异常。
- `nginx -t` 失败：停止，不 reload Nginx。

## 11. 回滚策略

半自动部署不替代回滚。

如果部署后发现问题：

```bash
cd /opt/beichen-agent/app
git log --oneline -5
sudo -u www-data git checkout <previous-stable-commit>
sudo bash deploy/scripts/deploy-vps.sh.example --skip-backup
```

如果运行时数据也出问题，再使用：

```bash
sudo bash deploy/scripts/restore-runtime.sh.example /opt/beichen-agent/backups/<backup>.tar.gz
```

## 12. 与 Docker / CI/CD 的关系

半自动部署是当前阶段的最小健康演进。

它解决：

- 少敲命令。
- 少漏步骤。
- 更新前自动备份。
- 更新后自动检查。
- 失败位置更明确。

它不解决：

- 多环境发布。
- 自动测试后自动上线。
- 容器隔离。
- 零停机部署。
- 多服务器部署。

等项目进入更公开的试用或多人协作后，再考虑：

- GitHub Actions 自动 SSH 部署。
- Docker Compose。
- PostgreSQL 迁移。
- 对象存储。
- 更完整监控。

## 13. 测试方案

本地检查：

```powershell
python -m compileall app
python -m pytest
npm exec tsc -- --noEmit
```

服务器测试：

```bash
cd /opt/beichen-agent/app
sudo bash deploy/scripts/deploy-vps.sh.example
curl http://127.0.0.1:8000/health
curl http://127.0.0.1:8000/health/config
sudo systemctl status beichen-agent
sudo nginx -t
```

浏览器验证：

- 能打开前端页面。
- 邀请码能进入。
- 普通聊天可用。
- 文件上传、解析、切块、embedding、索引可用。
- RAG 文件问答可用。
- 不同浏览器历史记录隔离仍正常。
