# v0.3 文件上传计划

> 本计划用于 v0.3 开发阶段。
> 目标是实现最小文件上传闭环。
> 本阶段不实现 RAG、Embedding、数据库、复杂任务队列或企业权限。

## 1. 当前问题

当前项目已经完成 v0.2 真实 LLM 聊天闭环，但文件模块仍停留在前端 Mock 阶段。

当前已有：

- `frontend/src/components/FileCenter.tsx`
- `frontend/src/stores/fileStore.ts`
- `frontend/src/api/mock.ts`
- `FileItem` 类型
- 前端文件列表 UI
- 前端上传区域 UI

当前问题：

- 前端选择文件后，只在浏览器内模拟上传。
- 文件不会发送到 FastAPI 后端。
- 后端没有文件上传 API。
- 后端没有 `FileService`。
- 后端没有本地 `uploads/` 文件保存逻辑。
- 前端文件列表展示的是 Mock 数据和本地临时状态。

v0.3 目标是先跑通最小闭环：

```text
前端选择文件
  -> POST /api/v1/files
  -> FastAPI
  -> FileService
  -> 保存到 backend/uploads/
  -> 返回 file_id、original_name、status
  -> 前端展示真实上传结果
```

v0.3 不解决：

- 文档解析。
- RAG。
- Embedding。
- 向量检索。
- 数据库持久化。
- 用户权限。

## 2. 修改文件列表

### 2.1 后端新增文件

#### `backend/app/api/v1/files.py`

职责：

- 定义文件上传 API。
- 接收 `multipart/form-data`。
- 调用 `FileService`。
- 返回统一响应。

修改原因：

- 当前后端没有文件上传入口。

#### `backend/app/schemas/file.py`

职责：

- 定义文件上传响应结构。
- 保持前后端字段一致。

建议字段：

- `id`
- `original_name`
- `status`
- `size_bytes`
- `extension`
- `created_at`

修改原因：

- 前端已有 `FileItem` 类型，需要后端返回相近结构。

#### `backend/app/services/file_service.py`

职责：

- 校验文件类型。
- 校验文件大小。
- 生成 `file_id`。
- 保存文件到本地 `uploads/`。
- 返回文件元数据。

修改原因：

- 保留 FileService 边界，避免 API 层直接处理文件存储细节。

### 2.2 后端修改文件

#### `backend/app/main.py`

计划修改：

- 注册 `files_router`。

修改原因：

- 暴露 `/api/v1/files` 上传接口。

#### `backend/app/core/config.py`

计划修改：

- 增加上传目录配置。
- 增加文件大小限制配置。
- 增加允许扩展名配置。

建议配置：

```text
UPLOAD_DIR=uploads
MAX_UPLOAD_SIZE_MB=20
ALLOWED_UPLOAD_EXTENSIONS=txt,pdf,docx
```

修改原因：

- 避免文件大小和路径散落在业务代码中。

#### `backend/app/core/errors.py`

计划修改：

- 增加文件相关错误。

建议错误：

- `FileValidationError`
- `FileStorageError`

修改原因：

- 上传失败需要返回稳定 JSON，而不是未处理异常。

### 2.3 前端新增文件

#### `frontend/src/api/fileApi.ts`

职责：

- 封装文件上传请求。
- 使用 `FormData`。
- 调用 `POST /api/v1/files`。

修改原因：

### 2.4 前端修改文件

#### `frontend/src/stores/fileStore.ts`

计划修改：

- 上传失败时抛出错误给 UI。
- 保留 `removeFile` 本地删除逻辑，v0.3 暂不做后端删除。

修改原因：

- 让前端文件中心展示真实上传结果。

#### `frontend/src/components/FileCenter.tsx`

计划修改：

  - 从“正在后台解析”改为“上传成功”。

- 问答按钮仍不可用，避免误导用户以为 RAG 已完成。

修改原因：

- UI 文案需要匹配 v0.3 真实能力。

## 3. API 设计

### 3.1 上传文件

接口：

```text
POST /api/v1/files
```

请求格式：

```text
multipart/form-data
field: file
```

成功响应：

```json
{
  "code": 0,
  "message": "ok",
  "data": {
    "id": "uuid",
    "original_name": "example.txt",
    "status": "uploaded",
    "size_bytes": 1234,
    "extension": "txt",
    "created_at": "2026-07-23T00:00:00Z"
  }
}
```

错误响应：

```json
{
  "code": 42001,
  "message": "Unsupported file type",
  "data": null
}
```

### 3.2 状态定义

v0.3 只使用：

- `uploaded`
- `failed`

暂不使用：

- `processing`
- `ready`

原因：

- v0.3 不做文档解析。
- `processing` 和 `ready` 应留到 v0.4 文档解析阶段。

### 3.3 文件限制

v0.3 建议：

- 支持扩展名：`txt`、`pdf`、`docx`。
- 最大文件大小：20 MB。
- 保存目录：`backend/uploads/`。

暂不做：

- MIME 深度识别。
- 病毒扫描。
- 文件内容解析。
- 重名文件覆盖。

## 4. FileService 设计

### 4.1 职责

`FileService` 负责文件上传的业务边界：

- 校验文件是否存在。
- 校验文件名。
- 校验扩展名。
- 校验文件大小。
- 创建上传目录。
- 生成内部文件名。
- 保存文件。
- 返回文件元数据。

### 4.2 不做职责

`FileService` v0.3 不做：

- 文档解析。
- chunk。
- embedding。
- RAG 索引。
- 数据库存储。
- 权限校验。
- 后端删除 API。

### 4.3 保存策略

建议保存路径：

```text
backend/uploads/{file_id}.{extension}
```

原因：

- 避免原始文件名冲突。
- 不在路径中直接使用用户上传文件名。
- 后续可以通过 metadata 保留 `original_name`。

### 4.4 返回结构

`FileService.upload()` 返回：

```text
UploadedFile
  id: string
  original_name: string
  status: "uploaded"
  size_bytes: int
  extension: string
  created_at: string
```

说明：

- `storage_path` 不返回给前端。
- v0.3 不保存到数据库，因此服务重启后文件列表不会恢复。

## 5. 前端接入方案

### 5.1 当前前端状态

当前 `fileStore.uploadFile()` 做的是：

```text
生成本地 file id
  -> 插入 processing 状态
  -> setTimeout 模拟解析
  -> 改成 ready
```

这与 v0.3 真实能力不一致。

### 5.2 v0.3 调整方案

调整后：

```text
FileCenter 选择文件
  -> fileStore.uploadFile(file)
  -> fileApi.uploadFile(file)
  -> POST /api/v1/files
  -> 后端返回 uploaded 文件记录
  -> fileStore 插入 files 列表
  -> FileCenter 展示 uploaded 状态
```

### 5.3 UI 行为

上传成功：

- 展示 `上传成功`。
- 文件状态为 `uploaded`。

上传失败：

- 展示后端返回错误。
- 不向文件列表插入失败文件，或插入 `failed` 状态。

问答按钮：

- v0.3 继续禁用。
- 文案保持“请等待文件解析完成”可以暂时接受，但更建议改为“文件解析功能将在下一阶段开放”。

PPT 按钮：

- 当前属于历史 Mock UI。
- v0.3 不改业务功能。
- 如做文案调整，只标记为暂不可用。

### 5.4 Mock 数据处理

建议：

- v0.3 可以继续用 `mockFiles` 初始化文件列表，方便展示 UI。
- 真实上传的新文件追加到列表顶部。
- 后续 v0.4 或 v0.5 再考虑真实文件列表 API。

## 6. 测试方案

### 6.1 后端手动测试

健康检查：

```text
GET /health
```

上传 TXT：

```text
POST /api/v1/files
multipart/form-data file=@example.txt
```

预期：

- 返回 `code=0`。
- `data.status=uploaded`。
- `backend/uploads/` 下出现保存文件。

上传不支持格式：

```text
file=@example.exe
```

预期：

- 返回文件类型错误。
- 不保存文件。

上传超过大小限制：

预期：

- 返回文件大小错误。
- 不保存文件。

### 6.2 后端基础验证

完成代码后运行：

```text
python -m compileall app
```

如加入最小测试，再运行：

```text
pytest
```

### 6.3 前端验证

完成代码后运行：

```text
npm exec tsc -- --noEmit
```

浏览器验证：

1. 启动 FastAPI。
2. 启动 Vite。
3. 打开文件中心。
4. 选择 TXT/PDF/DOCX 文件。
5. 确认 Network 出现 `POST /api/v1/files`。
6. 确认前端文件列表新增真实返回文件。
7. 确认后端 `uploads/` 下保存了文件。

### 6.4 不需要测试

v0.3 不测试：

- 文档解析。
- RAG 问答。
- embedding。
- 数据库写入。
- 企业权限。
- PPT 生成。

## 7. 不做范围

v0.3 明确不做：

- RAG。
- Embedding。
- 文档解析。
- 数据库。
- 复杂任务队列。
- 企业权限。
- 企业登录。
- 多租户。
- PPT 生成。
- 文件下载。
- 文件删除后端 API。
- 文件列表后端 API。
- OCR。
- 病毒扫描。
- 对象存储。

v0.3 的完成标准只有一个：

```text
用户能从前端选择文件，文件能上传到 FastAPI，后端能保存到本地 uploads/，前端能展示后端返回的上传结果。
```
