# v1.8.0 RAG Quality and Observability 规划

## 1. 当前 RAG 状态

当前项目已经具备完整的单文件 RAG 工程闭环：

```text
上传文件
-> 文档解析
-> 文本切块
-> embedding
-> 本地 JSON VectorStore
-> RetrievalService cosine similarity 检索
-> RagService 组装 prompt
-> LLMProvider 生成回答
-> 前端展示回答和引用 chunks
```

当前已实现能力：

- TXT / DOCX / 可复制文本型 PDF 解析。
- DOCX 表格文本解析。
- 固定字符切块：`chunk_size = 800`，`chunk_overlap = 120`。
- OpenAI-compatible embedding。
- 本地 JSON VectorStore。
- 单文件 top_k 检索。
- RAG prompt 基础约束：只根据文档片段回答。
- RAG 连续追问：携带当前会话最近消息作为对话上下文。
- `client_id` 隔离，防止不同浏览器共享文件和会话。
- request_id 日志和前端错误提示。

当前不足：

- 没有 RAG 质量评估基线。
- 没有固定测试集，无法判断改动是否真的提升准确率。
- 没有 score threshold，低相关片段也可能进入 prompt。
- 没有检索分布观测，例如最高分、最低分、平均分、score gap。
- 没有记录本次 RAG 的完整 debug trace。
- 引用展示偏工程化，用户不容易判断答案依据是否可信。
- 无答案场景仍主要依赖 prompt 约束，缺少检索层判断。

## 2. 为什么现在优先做 RAG 质量而不是登录

当前目标未来是支持 20-50 人使用。登录系统确实重要，但现在不是最高优先级。

原因：

1. RAG 是项目核心能力

   用户使用北辰agent，核心价值不是“能登录”，而是“能否基于文档准确回答”。如果 RAG 不准，即使登录系统完整，产品价值仍然不足。

2. 登录会固化数据归属模型

   正式账号系统会影响 files、chat_sessions、chat_messages、未来知识库和权限边界。如果 RAG 数据结构还在快速变化，过早做登录会增加后续调整成本。

3. RAG 质量更能体现 AI 工程能力

   RAG 质量涉及解析、切块、embedding、检索、prompt、引用、无答案判断和可观测性，比单纯接入手机号或微信登录更能体现 AI 应用工程能力。

4. 当前已有临时访问控制

   邀请码 + 匿名 `client_id` 足够支撑当前小范围可信试用。正式账号密码登录可以放到 v2.0。

结论：

```text
v1.8 优先做 RAG 质量和可观测性
v1.9 再考虑多文件 RAG
v2.0 再做账号密码 + 邀请码注册登录
```

## 3. RAG 准确性问题来源

RAG 回答不准通常不是单点问题，而是链路中多个环节共同造成。

### 3.1 文档解析问题

可能表现：

- PDF 文本顺序混乱。
- DOCX 表格转换后上下文缺失。
- 标题、段落、表格之间结构关系丢失。
- 扫描件 PDF 无法解析。

影响：

即使 embedding 和 LLM 都正常，如果解析文本本身错误，RAG 也会回答不准。

### 3.2 Chunk 策略问题

当前是固定字符切块：

```text
chunk_size = 800
chunk_overlap = 120
```

可能问题：

- 切块打断标题和正文关系。
- 表格行被切断。
- chunk 太大导致噪声过多。
- chunk 太小导致上下文不完整。
- overlap 不足导致跨段信息丢失。

### 3.3 Embedding 问题

可能问题：

- embedding 模型对中文、表格、专业术语的表达能力不足。
- query 和 chunk 的语义空间不匹配。
- 真实 embedding 维度配置和索引维度不一致。

当前项目已经支持真实 embedding，这一步比 Mock embedding 更适合继续调优。

### 3.4 Retrieval 问题

当前 RetrievalService：

```text
query -> embedding -> cosine similarity -> sort -> top_k
```

可能问题：

- 没有 score threshold。
- top_k 固定，不能按问题复杂度调整。
- 没有 score gap 分析。
- 没有 rerank。
- 没有 query rewrite。
- 连续追问时，检索仍只基于当前 query，省略句可能检索不准。

### 3.5 Prompt 问题

当前 prompt 已经要求只基于资料回答，但还可以更严格：

- 明确“没有依据时不要猜测”。
- 明确“引用片段编号”。
- 明确“资料不足时输出固定格式”。
- 明确“不要使用模型常识补全资料中没有的信息”。

### 3.6 引用展示问题

当前前端已经展示引用 chunks，但用户仍可能不知道：

- 哪个片段最关键。
- 分数高低意味着什么。
- 回答的哪句话对应哪个片段。
- 文档中是否真的有答案。

## 4. RAG 可观测性目标

v1.8 的关键目标是让每次 RAG 问答可以被复盘。

每次问答至少应该能看见：

```text
query
file_id
top_k
retrieved_chunks
score list
used_chunks
answer
model
token usage
request_id
```

建议新增一个轻量 Debug Trace 结构，用于开发和排查：

```text
RagDebugTrace
- trace_id
- request_id
- file_id
- query
- top_k
- chunk_count_total
- retrieved_count
- max_score
- min_score
- average_score
- score_threshold
- below_threshold_count
- used_chunk_ids
- model
- input_tokens
- output_tokens
- no_answer_detected
- created_at
```

当前阶段可以先不入数据库，优先返回到开发模式 API 或写入本地日志。是否落库留到后续根据真实使用再决定。

## 5. 质量评估指标

RAG 质量不能只看“回答顺不顺”，需要拆成检索质量、回答质量和用户可验证性。

### 5.1 Retrieval Hit Rate

定义：

测试问题有标准依据 chunk 时，top_k 检索结果中是否包含正确依据。

示例：

```text
10 个问题中，8 个问题 top_3 找到了正确片段
Retrieval Hit Rate@3 = 80%
```

作用：

判断检索有没有把正确资料送进 prompt。

### 5.2 Top-1 Accuracy

定义：

正确依据是否排在第 1 个检索结果。

作用：

判断排序质量。如果正确片段总在第 3 或第 5，说明 embedding 或排序策略仍有提升空间。

### 5.3 Answer Groundedness

定义：

回答是否能被 retrieved chunks 支撑。

可用人工标注：

```text
2 = 完全有依据
1 = 部分有依据
0 = 无依据或编造
```

作用：

判断模型是否忠于资料。

### 5.4 No-answer Accuracy

定义：

当文档中没有答案时，系统是否明确说“根据当前文档内容无法确认”，而不是编造答案。

作用：

这是 RAG 系统可信度的核心指标之一。

### 5.5 Citation Precision

定义：

展示的引用片段是否真的支持答案。

作用：

判断引用是不是“有用引用”，而不是把无关 chunk 一起展示出来。

### 5.6 Score Distribution

记录：

```text
max_score
min_score
average_score
score_gap = top1_score - top2_score
```

作用：

帮助判断问题是否有明确匹配结果。比如所有 score 都很低，应该触发无答案或低置信提示。

### 5.7 Latency

记录：

```text
retrieval_ms
llm_ms
total_ms
```

作用：

20-50 人使用时，响应速度会成为体验和成本问题。

### 5.8 Token Usage

记录：

```text
input_tokens
output_tokens
```

作用：

帮助控制 prompt 长度、成本和响应速度。

## 6. Debug Trace 设计

建议分两层做。

### 6.1 v1.8.1 最小实现

不改数据库。

在 RAG response 中新增可选字段：

```json
{
  "debug_trace": {
    "trace_id": "...",
    "retrieved_count": 3,
    "max_score": 0.72,
    "min_score": 0.41,
    "average_score": 0.56,
    "score_threshold": 0.35,
    "used_chunk_ids": ["file-1-3", "file-1-4"]
  }
}
```

前端默认不大面积展示，只在文件中心问答结果或开发信息区域展示摘要。

### 6.2 后续增强

如果真实试用中需要追踪历史质量，再考虑：

- 写入 `backend/logs/rag_trace.log`。
- 或新增 SQLite 表 `rag_traces`。

当前不建议立刻入库，因为这会增加数据增长、隐私和清理策略问题。

## 7. Chunk 策略优化方案

### 7.1 当前策略

```text
固定字符切块
chunk_size = 800
chunk_overlap = 120
```

优点：

- 简单稳定。
- 容易理解和调试。
- 不依赖复杂库。

缺点：

- 不理解标题和段落结构。
- 不理解表格边界。
- 可能打断语义。

### 7.2 v1.8 可做优化

建议先做低风险配置化：

```env
CHUNK_SIZE=800
CHUNK_OVERLAP=120
```

然后用测试集比较：

```text
600 / 100
800 / 120
1000 / 160
1200 / 200
```

判断标准：

- Retrieval Hit Rate 是否提升。
- No-answer Accuracy 是否下降。
- token usage 是否明显增加。

### 7.3 暂不做

暂缓：

- 复杂语义切块。
- Markdown AST 切块。
- 表格专用 chunker。
- LLM 辅助切块。

原因：

当前还没有质量基线，直接做复杂切块容易变成凭感觉优化。

## 8. Retrieval 策略优化方案

### 8.1 Score Threshold

建议新增：

```env
RAG_SCORE_THRESHOLD=0.35
```

流程：

```text
retrieve top_k candidates
-> 过滤 score < threshold 的 chunks
-> 如果全部低于 threshold，则进入无答案策略
```

注意：

不同 embedding 模型的 cosine 分数分布不一样，阈值必须通过测试集校准。

### 8.2 top_k 策略

当前：

```text
默认 top_k = 3
```

建议：

- 保留用户请求 top_k。
- 默认仍为 3。
- 上限仍控制在 8 或 10。
- Debug trace 记录实际 retrieved_count 和 used_chunk_count。

### 8.3 Score Gap

记录：

```text
score_gap = top1_score - top2_score
```

如果 top1 明显高于 top2，说明匹配更集中。

如果 top1、top2、top3 都很接近，说明问题可能需要多个片段综合，或者检索区分度不足。

### 8.4 暂不做复杂 rerank

不引入 rerank 的原因：

- 会增加模型调用成本。
- 会增加延迟。
- 当前还没有评估基线，无法证明 rerank 带来的提升。

后续如果测试集显示“相关 chunk 进了 top_k 但排序不好”，再考虑轻量 rerank。

## 9. Prompt 优化方案

当前 prompt 已有基础约束。v1.8 建议改成更明确的回答规则：

```text
你是北辰agent的文档问答助手。
你只能根据提供的文档片段回答。
如果片段中没有答案，请回答：根据当前文档内容无法确认。
不要使用外部常识补全文档中不存在的信息。
如果答案来自多个片段，请综合回答并标注片段编号。
回答后给出“依据片段”列表。
```

回答格式建议：

```text
回答：
...

依据：
- 片段 1：...
- 片段 3：...

如果资料不足：
根据当前文档内容无法确认。
```

这样可以提升：

- groundedness。
- no-answer accuracy。
- citation precision。

## 10. 无答案处理方案

无答案不能只依赖 LLM 自觉。

建议双层处理：

### 10.1 检索层

如果：

```text
retrieved_chunks 为空
或 max_score < RAG_SCORE_THRESHOLD
```

则不调用 LLM，直接返回：

```text
根据当前文档内容无法确认。建议换一种问法，或确认文件是否包含相关内容。
```

优点：

- 降低幻觉。
- 降低 LLM 成本。
- 响应更稳定。

风险：

- 阈值过高会误杀真实答案。

因此必须通过测试集校准。

### 10.2 Prompt 层

即使有 chunks，也要求模型：

```text
如果片段信息不足，请明确说明无法确认。
```

## 11. 引用展示优化方案

前端引用片段建议从“工程调试信息”优化成“可验证依据”。

展示字段：

```text
片段编号
chunk_index
score
内容摘要
```

用户看到：

```text
参考片段
1. 相关度较高 · 片段 4
   ...
2. 相关度中等 · 片段 8
   ...
```

不建议向普通用户突出太多工程字段。

开发调试时可以显示：

```text
score
chunk_id
trace_id
request_id
```

## 12. 是否需要新增 API 或字段

### 12.1 v1.8.1 建议新增字段

可以在现有 `AskFileResponse` 上新增：

```text
debug_trace?: RagDebugTrace
no_answer?: boolean
confidence?: "high" | "medium" | "low"
```

这不需要修改数据库。

### 12.2 RetrievalResponse 可新增字段

可以新增：

```text
max_score
min_score
average_score
score_threshold
filtered_count
```

这也不需要修改数据库。

### 12.3 暂不新增数据库表

当前不建议新增 `rag_traces` 表。

理由：

- 质量基线阶段更适合低侵入。
- trace 可能包含用户问题和文档片段摘要，需要隐私策略。
- SQLite 数据增长需要清理机制。

如果后续真实试用确实需要长期追踪，再进入 v1.8.x 或 v2.x 增加持久化 trace。

## 13. 风险和技术债

### 13.1 阈值误判

score threshold 太高会导致明明有答案却返回“无法确认”。

缓解：

- 用测试集校准。
- 先设置保守阈值。
- 前端展示低置信而不是直接失败。

### 13.2 指标需要人工标注

Answer Groundedness、Citation Precision 不能完全自动判断。

缓解：

- 先用小测试集人工评分。
- 每次调参后比较结果。

### 13.3 Trace 隐私风险

query 和 chunks 可能包含用户文档内容。

缓解：

- 默认不持久化完整 trace。
- 不写入 Git。
- 如果写日志，只写摘要和 score。

### 13.4 仍是本地 JSON VectorStore

文件较多或 chunks 较多时，检索效率会下降。

缓解：

- 当前只支持小范围单文件 RAG。
- PostgreSQL / pgvector 暂缓到 v3.0 或需求明确后。

### 13.5 连续追问检索仍可能不准

当前 retrieval 仍基于当前 query，不做 query rewrite。

例如：

```text
“继续解释第二点”
```

可能没有足够语义用于检索。

缓解：

- 先通过 debug trace 观察问题。
- 后续再考虑 query rewrite。

## 14. 分阶段开发顺序

### v1.8.1 RAG Debug Trace

目标：

- 新增 RAG debug trace 数据结构。
- RAG 返回 score 摘要、used_chunk_ids、confidence、no_answer。
- 不改数据库。
- 前端文件问答和聊天侧 RAG 展示 trace 摘要。

验收：

- 每次 RAG 问答能看到 retrieved_count、max_score、min_score、average_score。
- 回答中可以看到 request_id / trace_id。
- 不泄露 API Key、完整 prompt、完整 embeddings。

### v1.8.2 Retrieval Threshold and No-answer

目标：

- 增加 `RAG_SCORE_THRESHOLD` 配置。
- 低于阈值时触发无答案处理。
- 记录 filtered_count。
- 优化无答案前端文案。

验收：

- 无关问题不会强行编造。
- 有关问题不会被过度过滤。
- 测试集能对比阈值前后效果。

### v1.8.3 Chunk Strategy Tuning

目标：

- 将 chunk_size / chunk_overlap 配置化。
- 建立小型 RAG 测试样例。
- 比较不同 chunk 参数下的命中率和 token 成本。

验收：

- 能说明当前默认参数为什么合理。
- 能用指标解释调整效果，而不是凭感觉。

### v1.8.4 Citation UX Polish

目标：

- 引用展示从工程字段变成用户可读依据。
- 区分高/中/低相关度。
- 降低 score 视觉权重，但保留调试入口。

验收：

- 用户能判断回答依据来自哪些片段。
- 开发者仍能查看 score 和 chunk_index。
